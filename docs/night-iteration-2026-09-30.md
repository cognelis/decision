  - 重新评审后可以复核之前评审的问题在新提交里还在不在；各次评审的报告一一配对，发布、复核和撤销都作用在对应的那一条上。

## 第 1 轮：首页的开始使用引导（`6b96014`）

还没有任何决策时，首页原本是四个 0、三张“目前没有……”的空卡片和一大块空白的“最近决策”；只有没接入客户端时才多一条“还没有接入任何客户端”的提示，接入之后连这条也没有，新用户看不出下一步做什么。

先在 Claude Design 画布（“Decision 首次使用首页”）出稿，再按稿实现：

- 没有决策、候选和待补理由时，首页只显示“开始使用 Decision”：一句话说明它做什么，下面是四步清单和逐段对应的进度条。
- 四步：接入 Claude Code 或 Codex（按接入状态打勾，显示接入了哪一个）、记下第一条决策（按钮直接打开与 ⌘N 相同的主动记录弹窗）、选择回答模型（可选，有可用模型即打勾）、连接代码平台（可选，有 PR 链接即打勾）；每步都能直接跳到对应页面。
- 第一个未完成的必做步骤用主按钮，其余为次按钮；完成的步骤换成绿色状态和“管理”入口。
- 第一条决策记下后换回平常的首页；首页从组件拿到的回调改为通用的页面跳转与“打开主动记录”，外壳用一个计数接收这个请求。
- 几条测试的数据原本“有到期复盘却没有任何决策”，按真实情况补上决策数，避免把它们当成首次使用。

## 第 2 轮：模型后端的两个开关各自说清（`5aa3826`）

模型页每一行原本有两个紧挨着的开关：左边写着“失败后切换”，右边那个没有任何文字（只有悬停提示），看不出它才是这个后端的启停；停用的后端和启用的看起来一样，停用后“失败后切换”也还能点。

- 列顺序改为：状态、启用、失败后切换、操作；启用开关旁边写明“启用”。
- 停用的后端整行变淡，它的“失败后切换”不可用（对停用的后端没有意义）。
- 开关的可访问名称不变（“启用 某后端”“某后端 失败后切换”），窄窗口下的列宽同步调整。

## 第 3 轮：PR 列表标出“之后有更新”（`146f3bc`）

评审页的 PR 列表只显示“未评审 / 评审完成 / PR 概览”，看不出哪些评审过的 PR 后来又动了。现在平台给出的更新时间晚于最近一条评审或问答记录时，状态后面加“· 之后有更新”，用强调色标出，悬停说明“之后又有新提交或新评论”。已合并的 PR 不标。

评审记录的“更多”菜单多了“复制为 Markdown”，内容与导出文件相同（报告、过程与追问），方便直接贴进 PR 或聊天；导出与复制共用同一段拼装。

## 第 6 轮：回答可以发布为 PR 普通评论（`2a03960`）

前一晚给回答加了“复制”，贴进 PR 还要切到平台。现在每条追问 / 问答回答旁多了“发布到 PR”：

- 复用“转为评论”的确认弹窗：正文预填回答、可以改，显示源 / 目标分支和提交，以当前平台账号发布一条不绑定代码行的普通评论。
- 与行内评论相同的保护：只针对这条记录的提交，PR 有新提交、已合并或已关闭时拒绝；平台响应无法确认时提示先去核对，避免重复发布；和其它平台写操作共用互斥。
- 三个平台各自的接口：GitHub 用 PR 对应 issue 的评论，GitLab 用 MR notes，Bitbucket Server 用 PR comments（`text` 字段）。
- 发布过的回答记下时间，显示“已发布到 PR”，不再提供第二次发布；旧的历史记录照常读取。

## 第 7 轮：评审历史存满时不再整份失败（`15ecada`）

评审历史保存在本机存储里，条数没有上限；一旦写满，整份历史都不再保存。现在写不下时从最早的记录开始让位（每次让出五分之一），其余照常保存，并提示“最早的 N 条评审记录不再保存（这次打开期间仍可查看）”；连最新的记录都存不下时才报保存失败。

## 第 8 轮：接入页显示最近一次记录（`85b1c09`）

接入卡片只有“已连接”，看不出 Hook 是否真在工作。现在每张卡片多一行“最近一次记录：时间 · 问题”（按来源取最新一条决策）；已连接却还没有记录时，提示在对话里做一次选择后会出现在这里。

## 第 9 轮：评审问题直达 diff 所在行（`c4beba8`）

评审结果里每条问题都写着 `文件:行号`，但只是文字；要看代码得打开 PR 详情、找文件、再翻到那一行。

- `文件:行号` 变成按钮：打开 PR 详情时直接选中该文件，用 diff 组件的选中行高亮那一行并滚动到中间，工具栏写明“已定位到第 N 行”。
- 模型读的是完整文件，指出的行可能不在 diff 里：这时工具栏提示“第 N 行不在 diff 中，可切到‘文件内容’查看”，切过去同样高亮并滚动到这一行（按行号自动展开到那一行）。
- 选中行的颜色改用主题的强调底色；库默认的浅黄在深色模式下很刺眼。
- 截图脚本新增 `pr-finding-diff` 动作，便于以后核对这一界面。

## 第 10 轮：一眼看出评审发现了什么（`1e1a895`）

评审结果的统计行只写“完成评审 N 个文件 · 读取 … · 模型调用 …”，要往下翻才知道发现了几个问题、严重程度如何。现在统计行以“3 个问题（P1 ×1 · P2 ×2）”开头，没有问题时写“没有发现问题”；「历史评审」列表的状态也带上问题数（“评审完成 · 3 个问题”）。

## 第 11 轮：在平台打开 PR（`2c75c38`）

评审时经常要回平台看 CI、讨论或直接在网页上操作，此前只能自己去找。准备页和评审记录的标题行里，“PR 讨论”旁边多了“在平台打开”：主进程按连接的网页地址拼出 PR 页面（GitHub `/{repo}/pull/{n}`、GitLab `/{repo}/-/merge_requests/{n}`、Bitbucket Server `/projects/{key}/repos/{slug}/pull-requests/{n}/overview`，与评论链接同一套拼法），用系统浏览器打开；渲染进程只传连接 ID 和 PR 引用，不能借此打开任意网址。

## 第 12 轮：评审在后台结束时发系统通知（`f52a498`）

评审一个大 PR 要好几分钟，期间常会切到别的窗口，回来才知道结束没有。现在窗口不在前台时，评审结束会发一条系统通知：标题是“PR 评审 · 评审完成”（或停止、失败等状态），正文是 PR 引用和问题统计，如“2 个问题（P1 ×1 · P2 ×1）”；失败时提示检查模型与平台连接。窗口在前台时不打扰；系统拒绝通知权限时静默跳过。

## 复查今晚的改动（`4ac05b3`）

让一个评审代理只读复查了 `ee4b98c..f52a498` 的全部代码改动。IPC 入参校验、“在平台打开”的地址拼接（渲染进程不能借此打开任意网址）、发布评论前的提交核对、异步读取在卸载后的保护、历史让位的先后顺序都没有问题；只确认了一处缺陷：指向旧版本（被删除一侧）的问题，切到“文件内容”时仍按源提交打开，行号对不上，也不高亮。现在按问题所在的一侧选择提交版本，并补了回归测试。

## 第 13 轮：评审跳过锁定文件与压缩产物（`c159070`）

升级依赖的 PR 里，`package-lock.json` 一改就是上千行。按 60 行一批切下去，几十批都在让模型读锁定文件。PR 概览、改进建议和问答所带的 diff 上限是 2 万字，锁定文件排在前面时还会把真正的代码挤出去。

- 常见锁定文件（npm、yarn、pnpm、bun、Cargo、Bundler、Poetry、Pipenv、Composer、Go、uv、CocoaPods、Nix）和 `*.min.js`、`*.min.css`、`*.js.map`、`*.css.map` 不再切批，也不放进回答所带的 diff。回答时会告诉模型省略了哪些文件，需要时它会说明。
- 准备页在“这次会带上”下方列出这些文件，批次数随之减少。报告摘要写“另有 N 个锁定或生成文件未送模型”，这些文件不算作未完成。

## 第 14 轮：链接页检查令牌（`67dc228`）

链接页每条连接只有名称、平台和地址。令牌过期或填错了，要等评审页读 PR 列表失败才发现，而那里的报错还带着 “Error invoking remote method 'decision:pr-list': PrPlatformError:” 这样的前缀。

- 打开链接页、保存或移除链接后，用每个链接自己的令牌向平台确认一次身份：GitHub、GitLab 读当前用户；Bitbucket Server 读任意 REST 响应头里的登录账号，返回 `anonymous` 视为未认证。
- 成功显示绿色的“已连接 · 账号 octo”，失败直接显示平台给出的原因（HTTP 401、403、地址无法访问、令牌不在钥匙串里等）。每条都有“检查”按钮可以重新确认；同一条连接以最新一次检查为准。
- 主进程只返回账号名，IPC 用 zod 限定入参为连接 ID、出参只有 `account`，令牌不会经过渲染进程。
- 评审页和它的弹窗里有 9 处直接显示 IPC 错误原文，统一改为去掉 Electron 的前缀，只保留平台自己的说明。

## 第 15 轮：日期统一用中文格式（`0f90cdf`）

应用里的日期大多写成“7月30日 16:30”“2026年7月31日 18:30:00”，评审页和接入页却跟随系统区域，在英文区域的系统里显示成 “9/30/2026, 3:40:37 AM”“9/21/2026 更新”“7/30, 04:30 PM”，同一屏里两种写法混着用。现在评审页（PR 列表、历史评审、标题行、过程与问答的时间）、PR 讨论和接入页都固定用 `zh-CN`：完整时间写“2026年9月30日 03:43”，列表写“9月30日 03:43”；PR 的更新日期当年的不写年份（“9月21日 更新”），往年的才带上。

## 第 16 轮：评审报告显示 token 用量与费用（`4c8e3b5`）

问答的每轮回答都写着“本轮 19.6k tokens ≈ ¥0.42”，评审却只写“N 次模型调用”，而大 PR 的一轮评审会调用几十次模型。

- 主进程逐次累计模型调用报告的输入、输出 token；失败的调用和没报告用量的调用单独计数，这时总数写作“至少”。
- 在模型页给所选后端填了单价时，按这个价格折算金额，和问答的算法相同；没填单价就只写 token 数。
- 报告统计行写作“12 次模型调用（38.2k tokens ≈ ¥0.3056）”，导出和复制的 Markdown 在“覆盖”一节写同样的内容。以前的历史记录没有这项数据，照常显示。

## 第 17 轮：单条问题可复制，PR 问答显示每次回答的用量（`5e342b4`）

- 评审找到问题后，常见的下一步是交给 Claude Code 或 Codex 去修，但只能手抄标题、说明、文件和行号。现在每条问题的操作里多了“复制”：内容和“转为评论”的起稿相同（标题加说明，取代过的问题用替代文本），后面附上 `文件:行号`、新旧版本，以及 PR 与提交（如“sample/app#123 @ aaaaaaaaaaaa”），可以直接粘贴。
- 追问、PR 概览和改进建议的每条回答，时间旁边写明这次调用的 token 数，填了单价时附折算金额，与问答页一致。用量随历史保存，导出的 Markdown 也带上。PR 问答的返回改为“模型输出 + 用量”的单独 schema，模型本身的输出 schema 不变。

## 第 18 轮：评审问题显示在 diff 对应行下面（`2304a63`）

第 9 轮让“点问题 → 定位到那一行”可以用了，但 PR 详情里一次只高亮点开的那一条，其余问题在 diff 里看不到，要在报告和详情之间来回切换。

先在 Claude Design 出稿（画布“Decision PR 详情 · 行内问题”，浅色、深色各一张），再按稿实现：

- 有评审记录时，这份报告的每条问题像平台上的行内评论一样，放在它指向的那一行下面：优先级标签（P1 强调色、P2 琥珀、P3 灰）、标题、“第 N 行 · 新版本/旧版本”和说明。那一行的行号加粗标出。复评改写过的问题显示替代文本，撤销的不显示。
- 变更目录里每个有问题的文件后面标“N 个问题”（读屏名称也带上）。工具栏写“本文件 N 个问题，M 个在 diff 之外”。
- diff 显示不到的问题列在代码上方，每条都有“在文件内容中查看”：切到“文件内容”、选对新旧版本，并高亮滚动到那一行。
- Unified 和 Side-by-Side 都支持：用 diff 组件自带的 widgets 放卡片，用行 class 标行号。

## 第 19 轮：评审进行中限制历史写入频率（`254e1d5`）

评审历史整份保存在本机存储里，常用之后接近几 MB。评审进行中，每个进度事件（每次模型调用、每个工具动作的开始和结束）都会让整份历史重新序列化、同步写一遍，大 PR 评审时窗口会一顿一顿的，追问框打字也会卡。现在评审进行中最多每秒写一次，写入的是最新状态；评审一结束（完成、停止或失败）立即写入最终结果。测试确认连续 30 个进度事件最多触发一次写入，结束后的记录包含全部事件。

## 第 20 轮：评审可以只选部分文件（`8d23d4c`）

大 PR 里常有测试、文档或迁移脚本，只想先看核心代码。第 13 轮自动跳过了锁定和生成文件，其余文件仍然只能全评。

先在“Decision 评审准备页”画布上加一张“选择评审文件”的稿，再按稿实现：

- 读取 PR 时，主进程把每个文件会切成几批一并交给准备页。“这次会带上”的文件卡片里多了“选择文件”。
- 弹窗按目录分组，目录复选框可以整组勾选（部分选中时显示半选），可以筛选路径，有全选、全不选；每个文件标出批次数。锁定、生成文件和没有文本 diff 的文件不能勾选，并写明原因。底部实时显示“已选 M / N 个文件 · 约 K 批”。
- 确定后卡片变成“M / N 个文件将评审”，批次数和“完整评审”方式里的批数随之更新。评审请求带上所选路径，主进程只评审这些文件；没选的不计为未完成，摘要写“另有 N 个文件未选入这次评审”。
- 选择按 PR 记住，PR 有新提交后，仍在其中的文件保持选中。全选等同于不限定。PR 概览和改进建议仍看整个 PR。
- 截图脚本新增 `pr-scope` 动作。

## 第 21 轮：侧边栏的评审入口显示状态（`bd8c5c8`）

第 12 轮的系统通知只在窗口不在前台时发出。人在应用里、切到别的页面时，评审什么时候结束完全没有提示，只能回评审页去看。

- 评审进行中，侧边栏“评审”入口带一个跳动的强调色圆点（减少动态效果时不跳动）。评审在别的页面结束后，换成绿色圆点表示有新结果，回到评审页后消失。侧边栏收起和展开时都有，悬停提示和读屏描述写明“评审进行中”或“有新的评审结果”。
- 状态由评审页自己判断（它知道评审何时开始、结束，以及当时是否在前台），只把“进行中 / 有新结果 / 无”交给外壳。

## 第二次复查（`86b587b`）

又让评审代理只读复查了第 13–20 轮（`f52a498` 之后）的代码。令牌用量与计价、链接检查（令牌不会到渲染进程）、IPC 错误前缀、行内问题定位、中文日期、历史写入限频、部分文件评审都走查过，没有问题。确认了两处需要修的：

- 锁定或生成文件如果平台没给出可解析的 diff（例如服务端截断了一个超大的锁定文件），原来不算“跳过”，又分不到批次，就被当成“未评审”，整轮评审会被误标为“部分完成”。现在只要是锁定或生成文件就算跳过，也不再为它报“没有可解析的文本 diff”。
- 很长的 diff 默认只显示前 2000 行变更，落在后面的问题原来被说成“diff 之外”。现在这类问题标为“后面尚未显示”，并提供“显示到这一行”；从报告点进来定位时，也会自动展开到那一行再高亮。

## 第 22 轮：评审进行中显示批次进度（`8c67ed2`）

评审进行中，列表和标题只写“评审中”，看不出大 PR 还要多久。现在按最近一个批次事件写成“评审中 · 3/12 批”（批次事件的文字由主进程写出，那里加了注释说明评审页会读它）。

## 第 23 轮：快速跳转可以打开 PR 评审记录（`b300d13`）

⌘K 快速跳转能搜决策、偏好想法、笔记和原则，但搜不到评审过的 PR。现在本机保存的评审与问答记录出现在最下方的“评审”分组：按 PR 标题或 `仓库#编号` 匹配，没输入时列最近 5 条，行内写明引用、“评审/问答”和日期。打开后跳到评审页的“历史评审”并选中这条。历史在打开弹窗时读一次，不会每次按键都读。

## 第 24 轮：模型调用记录写明来源功能（`a6c6374`）

日志页的模型调用记录可以按用途筛选，但每一行不写用途，选“全部”时分不清哪条是评审、哪条是问答或识别。现在每行第二行写成“PR 评审 · 模型名”“语义识别 · 模型名”这样的格式。

## 第 25 轮：批量发布评审问题（`3a6dcbc`）

每条问题都要单独点“转为评论”、各确认一次，一份十条问题的评审要走十遍。

- 问题有两条以上还没发布时，问题列表上方出现“批量发布为 PR 评论（N）”。弹窗列出未发布、未被撤销的问题（取代过的用替代文本），默认全选，可以取消个别条目。
- 先核对平台状态（PR 已合并、已关闭时不能发布），再逐条调用与单条发布相同的接口：只针对这次评审的提交，PR 有新提交就拒绝，平台写操作互斥。
- 任何一条失败就停下，写明是哪一条、失败原因，以及前面已发布几条。已发布的条目标“已发布”，不会再次提供；关闭后单条的“转为评论”也会显示“已发布为 PR 评论”。
- 弹窗打开时固定列表，发布过程中不会跳动。截图脚本新增 `pr-batch` 动作；因为同优先级的 CSS 规则覆盖，复选框曾经跑到文字上方，已调高选择器权重修好。

## 第 26 轮：重新评审时只看上次之后有变化的文件（`2a3ead8`）

PR 在评审后又推了几个提交，重新评审就得把没变的文件再评一遍，花时间也花 token。真正的增量评审要用各平台的 compare 接口，还要处理 rebase，今晚没法在真实平台上验证，所以先做一个不依赖平台接口、偏保守的版本：

- 读取 PR 时，主进程给每个文件的 diff 算一个 16 位摘要（含行号），随快照交给评审页。
- 从评审记录点“重新评审最新提交”进入准备页时，找到这个 PR 最近一次有结果的评审。它若评的是别的提交，就逐个文件比较摘要，提示“上次评审（时间 · 提交）之后，有 N 个文件的改动变了或尚未评审：……”，并提供“只评审这些”，一键套用第 20 轮的文件选择。上次没评审到的文件（没选上或没完成）也算在内；各文件都没变时写“各文件的改动没有变化”。
- 目标分支变动会让行号变化，这时所有文件都算变了，不出提示，照常整份评审，宁可多评不漏评。以前的评审记录没有摘要，也不出提示。

## 第 27 轮：PR 列表可以按状态搜索（`c1adf55`）

“历史评审”的搜索本来就能匹配状态文字（例如搜“概览”），PR 列表的搜索却只匹配编号、标题、仓库和作者。待我评审的 PR 多了以后，想先看还没处理的得一条条找。现在 PR 列表的搜索也匹配每条显示的状态，输入“未评审”或“之后有更新”就只剩还要看的 PR。状态文字抽成一个函数，列表显示和搜索共用，两边不会说法不一致。截图脚本另加了 `methodology-practice` 动作，用来检查“技能与流程”标签页。

## 第 28 轮：评审问题按优先级筛选（`530fd9f`）

问题多的报告要从头往下翻，才能先处理严重的。现在问题超过 3 条、且优先级不止一种时，问题列表上方有“全部 N / P1 n / P2 n / P3 n”的切换（按钮带按下状态，读屏可知）。筛选时每条问题保留原来的序号，复评、复制、转为评论、批量发布都仍对应正确的那一条；换一份记录时回到“全部”。

## 第 29 轮：两处小补充（`f882957`、`54ab7a9`）

- 批量发布弹窗和单条“转为评论”一样，核对平台后显示源分支、目标分支和各自的提交，发之前能确认发到哪里。
- 单条问题“复制”出的内容，如果这条问题引用了决策证据，末尾附“相关决策”，逐条写 `[编号] 来源/ID 标题`。接了 Decision 的 Claude Code 或 Codex 可以按来源和 ID 直接读到那条决策，修的时候不会违背以前定下的做法。

## 第三次复查（`93cbc85`）

让评审代理只读复查了第 22–25 轮，重点是批量发布这种会写到平台上的操作。双击、重入、发布中途关闭、弹窗开着时切换记录都挡住了（按钮禁用、同步锁、发布中不可关闭、遮罩和全局快捷键都进不去），没有找到会重复发布或发错 PR 的路径。确认并修了三处：

- 失败后重试，最后的提示只数了重试这一轮，发了 3 条只说“已发布 2 条”。现在从累计的已发布条数算起，失败提示也写累计数。
- 复选框的读屏名称只有标题：两条问题标题相同时读屏分不开，也听不到文件和行号。现在名称是“标题（文件:行号）”。
- 部分发布成功后，用 Esc 或右上角关闭，不会提示“已发布 N 条评论”。现在不论怎么关，都会说明已经发出去的条数。

## 第 30 轮：点通知直接打开评审（`42ad27c`）

第 12 轮的系统通知点了只会把窗口带到前面，停在原来的页面，还得自己去评审页找这份记录。现在点“PR 评审 · 评审完成 / 评审失败”的通知，会切到评审页的“历史评审”，并选中这份评审。

## 第 31 轮：评审记录里提示 PR 之后有更新（`c5ad9b2`）

第 26 轮的“只评审变化的文件”，要从评审记录标题栏那个没有文字的刷新图标（“重新评审最新提交”）进去才看得到，不容易发现。现在，如果 PR 列表显示这个 PR 在这份记录之后又有更新，记录顶部会写“这份评审之后，PR 又有新提交或新评论。”，并给出“评审最新提交”的文字按钮，点了直接到准备页（在那里会看到哪些文件变了）。已合并的范围和评审进行中的记录不提示。

## 第 32 轮：⌘F 页面内查找（`1712d7f`）

Electron 没有浏览器自带的查找栏，评审报告、问答回答、决策详情这些长内容里找一个词，只能靠眼睛扫。现在任何页面按 ⌘F（Windows 为 Ctrl+F）会在右上角打开查找栏：

- 在当前页面里找；有弹窗时（比如 PR 详情的 diff）只在最上层的弹窗里找。隐藏着的页面（评审页切走后仍保留在后台）和折叠的内容不计入。
- 所有命中用荧光底色标出，当前一处用强调色，并滚动到页面中间。显示“2 / 16”，↩ / ⇧↩ 或箭头按钮切换，Esc 或 × 关闭。新输入的词从第一处开始。
- 标记用应用已在用的 CSS Custom Highlight API，不改动页面 DOM，也不经过主进程。快捷键帮助里加了这一条，截图脚本新增 `find` 动作。

## 第 33 轮：全部复评（`a790409`）

复评是筛掉误报的主要手段，但只能逐条点、逐条等模型。有了批量发布以后，常见做法是先把所有问题复评一遍，再把保留下来的一起发，一条条点太慢。

- 还没复评的问题有两条以上时，问题列表上方出现“全部复评（N）”（和“批量发布为 PR 评论”并排）。点了以后逐条复评，显示“正在复评 i / N”，每条问题下照常出现“复评中…”和结论。
- 复用单条复评的逻辑，它现在会返回是否成功；任何一条失败就停下。“停止复评”既中断正在进行的那条，也不再继续后面的。已经得出的结论保留，剩下的下次还能接着“全部复评”。

插曲：这一轮合入 main 后，构建前的类型检查失败了：新测试里模拟的复评结果少了 `replacement` 字段。这一轮只跑了 vitest，没有跑 tsc。构建失败时没有安装，本机仍是上一轮的版本；补上字段（`9b12a22`）后重新构建、冒烟、安装。之后每次改测试都连同 tsc 一起跑。

## 第 34 轮：评审摘要发布为 PR 评论（`08b309a`，另有小重构 `7e98b11`）

逐条发完行内评论后，通常还要在 PR 上留一条总评，说明这次看了什么、有几个问题。现在评审记录“更多”菜单里有“发布评审摘要到 PR”：按复评后的结果起草（撤销的不列，取代的用替代文本），首行是问题统计和提交，下面每条问题写优先级、标题和 `文件:行号`。沿用第 6 轮的普通评论弹窗，起稿可以修改，同样只针对这次评审的提交；PR 已变化、合并或关闭时拒绝发布。普通评论弹窗的说明从“回答只是草稿”改成“内容只是草稿”，回答和摘要都适用。

顺带把单条发布和批量发布里重复的“标记为已发布”合成一个函数。

## 第 35 轮：PR 列表读取失败时直达链接检查（`977c3c6`）

PR 列表读不出来，最常见的原因是令牌过期或失去权限。以前只显示错误，要自己想到去设置里的“链接”页。现在错误后面跟一个“检查链接”，点了直接到链接页，那里会用每个链接的令牌确认一次身份（第 14 轮）。测试顺便确认了错误文字已去掉 Electron 的前缀。截图脚本另加了方法论“分析”“图谱”两个动作。

## 第 36 轮：评审问题可以记为决策（`cf0af2b`）

PR 讨论里的评论早就能“记为决策”，评审发现的问题却不能。有些问题本身就是一条团队做法（比如“超时必须把取消信号传给底层请求”），记进决策库之后，以后的评审和 Claude Code 就能检索到它。现在每条问题的操作里多了“记为决策”：打开主动记录，标题起稿为“<问题>：以后怎么处理？”，正文是问题说明（复评取代过的用替代文本），项目取 PR 所在仓库，背景里写明 PR、`文件:行号` 和提交。保存后的提示也分开了：只有真的保留了评论链接时才说“并保留了评论链接”。

## 第 37 轮：日志页合计模型调用（`6e5215b`，另有小修 `eae51d9`）

问答和评审各自显示一次调用的用量，却没有地方看这几天一共用了多少。现在日志页“模型调用记录”的用途筛选旁边有一行合计，跟着筛选变：调用次数、未成功次数（有才显示）、token 总数、平均耗时；在模型页给后端填了单价的调用再折算成金额，其余的注明“N 次未计价”。没报告 token 的调用不计入，只要有这种调用就写“至少 … tokens”，与评审报告的写法一致。价格按调用记录里的后端 ID 查，读不到后端列表时只显示 token。

小修：评审记录“更多”菜单的宽度原先固定 160px，“发布评审摘要到 PR”会折成两行；改为按最长一项撑开。

## 第四次复查（`dd19a2a`、`354c0e6`）

复查第 26–34 轮，确认三处问题并修复：

- 第 26 轮的“只评审变化的文件”：源提交相同就不比较了。但有的平台按目标分支重算 diff，只有目标分支前进时改动也可能变，这时提示不出现。现在两个提交都相同才跳过。
- 第 32 轮的 ⌘F：打开查找条后，内容在原位被替换（切到另一条评审记录、回答还在生成），计数和高亮仍停在旧内容上。现在页面文字一变（查找条自身的计数除外），停 150ms 后原地重新查找，保留当前位置，不滚动。
- 同一个查找条：关闭后焦点落在页面开头，键盘用户得从头 Tab。现在和弹窗一样，把焦点还给打开前的元素。顺带：输入法候选框开着时按 Esc 只取消候选，不再关掉查找条。

复查核对过、没有问题的点：发布都要显式确认并先检查 PR 仍开着；“全部复评”没有并发丢更新；按优先级筛选后下标仍对应原问题；“PR 有更新”只在当前连接内判断。

## 第 38 轮：PR 详情里逐个跳问题（`8693f06`）

问题多、分散在几个文件里时，在 PR 详情里看完一个，要回到报告点下一个的位置，或在目录里自己找。现在工具栏多了“‹ 问题 i / N ›”：按变更目录的顺序（每层目录在前、再按名称，同一文件按行号）跳到上一个或下一个问题，跨文件时自动切换文件并定位到那一行，首尾循环。顺序跟左边目录一致，所以跳的方向和眼睛看的方向相同。停在“文件内容”视图时也照样跳，提交版本跟着问题所在的一侧切换。没有定位到某个问题时显示“N 个问题”，下一个从第一个开始。

## 第 39 轮：每批评审知道 PR 还改了哪些文件（`9dd0097`）

评审按文件分批，每批只看到当前文件的 diff 和前三批的摘要。一个文件调用了同一 PR 里另一个文件新加的函数，模型看不到那边，容易报“未定义”“签名不一致”这类误报。现在每批的上下文多了 `otherChangedFiles`：PR 其它变更文件的状态与路径。系统提示说明它的用途：怀疑缺失或不一致时先用 `read_file` 读那边的源码核对，不要只因本批看不到就报缺陷。

上下文有 12,000 字符的预算，文件清单排在最后，只占评审规则和已有评论剩下的空间，最多 800 字符。列不完时最后一项写“…另有 N 个文件”，不会挤掉规则和评论，也不会让批次因超长失败。提示词版本从 `pr-review-v6` 升到 `pr-review-v7`，调用记录里能分辨新旧。没有用真实模型跑对比（会动用你配置的 API 额度），只用测试确认了上下文内容和长度上限。

## 第 40 轮：评审问题卡片（`9992bec`，Claude Design 画布）

问题多的时候，报告里“P2 · 标题”是一整行同样的粗体，扫一眼分不出轻重。操作按钮靠右排、间隔很大，离说明文字很远。在 Claude Design 里用应用的配色画了三种排法（画布“Decision 评审报告 · 问题卡片”）：

- A：标签头。优先级做成彩色标签，和标题同一行；操作紧跟在说明下面。
- B：表头卡片。每条一张卡片，表头放优先级、标题和位置。
- C：两栏。左栏只放优先级，位置跟在标题后。

选了 A。B 的卡片边框在十几条问题时太重；C 的左栏在窄窗口里挤占正文。A 的操作仍用原来的文字按钮，没有照画稿做描边按钮，也是为了在问题多时不显得重。标签复用 PR 详情行内问题的样式（P1 强调色、P2 警示色、P3 灰），两处看起来是同一个东西。操作行靠左与正文对齐，“已发布为 PR 评论”挪到最右。顺带收紧了正文段落和操作行上下的空白。撤销的问题照旧划线（选择器随结构改了）。读屏时标签先念优先级，标题仍是独立的标题。复制和发布出去的 Markdown 仍写“**P2 · 标题**”，没有变。

## 第 41 轮：统一优先级口径（`c6541cf`）

评审提示词原来只写了 `priority(P1/P2/P3)`，没说三档各指什么。模型只能自己定标准，分批评审时前后几批的标准也可能不一样，而“全部 / P1 / P2 / P3”筛选、问题统计和彩色标签都依赖这个值。现在系统提示写明：P1 是合并后会直接造成安全漏洞、数据丢失或损坏、崩溃或主要功能不可用；P2 是特定条件下出错（边界输入、并发、失败路径、资源泄漏、明显的性能退化）；P3 是影响小或触发条件苛刻的缺陷，以及让后续修改容易出错的隐患。还要求拿不准时取较低一级，不为引起注意而拔高。提示词版本升到 `pr-review-v8`。README 写明了同样的口径，读报告的人和模型用同一套标准。

## 第 42 轮：两处小修（`a53491e`、`d8de6bb`）

- 决策详情的“同一问题的其它决定”只列前三次，后面写“另有 N 次”，却没有办法看到。同一个问题被反复决定，正是要回头比较的时候。现在它是“另有 N 次，全部显示”按钮，点开就在原处列出全部；换到另一条决策时收回。
- “完成复盘”弹窗里“当初选择”和“实际结果”两块摘要之间的空隙是其它地方的两倍：表单网格已经有 12px 间距，摘要自己还带 14px 下外边距。在这个表单里去掉那段外边距，两块摘要读起来是一组。

## 第 43 轮：快速跳转找得到问答会话（`6932c96`）

⌘K 已经能跳到决策、偏好想法、笔记、原则和评审记录，唯独问答页的会话不行。想找“上次问过灰度发布的那段对话”，只能去问答页自己搜。现在快速跳转多了“问答”分组，按会话名称和其中问过的每一个问题匹配：会话名只是截短的第一个问题，后面的追问也要能搜到。行尾写几个问题和最后更新日期，空会话不列。打开时照第 23 轮评审记录的做法，由 App 记下目标会话、切到问答页，问答页像从列表里点一样换过去。回答还在生成时不切换，免得打断进行中的回答。会话历史读不出来时，这一组只是没有结果，报错仍由问答页自己说明。

## 第 44 轮：快速跳转的说明跟上内容（`0c69d20`）

快速跳转已经能搜六类内容，但弹窗说明、输入框名称和快捷键帮助还写着“决策、偏好想法、笔记与原则”“四类记录一起搜”。现在三处都写明也搜问答和评审，README 的对应说明和 ↑↓ 那一行同步更新。输入框的可访问名称随之改为“搜索决策、想法、笔记、原则、问答与评审”，测试里的 6 处同步改。

## 第 45 轮：复核上次评审的问题（`25d4a83`）

作者按评论改完推了新提交，重新评审之后，最想知道的是上次那些问题改掉了没有。新报告只列这次找到的问题，看不出旧问题的去向。现在重新评审完成后，报告里多一个可展开的“上次评审的 N 个问题”：同一 PR 上一次在别的提交上的评审找到的问题（撤销的不列，取代的用替代文本），每条写明放到这次提交上的情况。

- 所在文件的改动摘要（第 26 轮）没变：写“应当还在”，不花模型调用。
- 文件已不在这次的变更里：直接写明。
- 文件有改动：点“复核有改动的 N 个”逐条复核。

复核沿用复评的调用，请求里多了可选的 `earlierCommit`，告诉模型这条来自较早的提交、行号可能已经移动。模型只判断问题在当前提交里还在不在，不因为平台上已有评论指出过它就判撤销：还在是“仍然存在”；修好了是“已不存在”，并说明是哪处改动修的；还在但位置或说法变了，给出按当前代码改写的说明。复评提示词版本升到 `pr-review-reevaluate-v2`。当时已发布为 PR 评论的问题会标出来，复核后知道哪些评论可以去平台上关掉。复核逐条进行，沿用复评的停止按钮，结果存在这次评审的记录里（新增 `rechecks`，旧记录读出来是空的）。这一节默认收起，新问题仍排在最前面。

## 第 46 轮：历史列表换行（`f969560`，另有截图动作 `1a1a17f`）

历史评审列表里，状态写成“评审完成 · 3 个问题 · 已发布 1”这么长时，同一行的“sample/app#123”会被挤成两行。现在这一行放不下时状态整体换到下一行，PR 编号保持完整。截图脚本加了 `pr-previous` 动作：先写入同一 PR 的两份评审，再打开新的那份并展开“上次评审的问题”，第 45 轮的界面就是用它核对的。

## 第五次复查（`cf8f703`、`622e443`、`1fcb133`、`ef06e84`）

复查第 35–42 轮，确认六处问题并修复：

- 第 38 轮“‹ 问题 i / N ›”：同一行有两个问题时，“下一个”永远停在第一个上。当前位置原来每次按“文件 + 行号”重新查找，同一行只能找到第一个。现在记住走到第几个，同一行的问题也能逐个经过。

## 第 47 轮：评审摘要带上上次问题的去向（`d28717e`）

第 45 轮复核出上次的问题哪些已不存在，但这个结论只留在本机。重新评审后从“更多”菜单起草评审摘要（第 34 轮），现在末尾会多一段“**上次评审的问题**（提交 …）：已不存在 a 个，仍然存在 b 个”，并逐条列出，作者在 PR 上就能看到哪些评论已经解决。只写有结论的：复核过的，或所在文件没改动、问题应当还在的；没复核的和文件已不在变更里的不写，免得误导。草稿照旧可以改，确认后才发布。

## 第 48 轮：模型调用记录只看未成功（`3993ffd`）

打开日志页的模型调用记录，多半是某次调用出了问题。可记录最多保留 1,000 条，按用途筛选后失败的仍混在成功的中间。现在有未成功的调用时，合计行旁边多一个“只看未成功（N）”开关，勾上后列表和合计都只算失败、超时、取消等未成功的调用。它跟用途筛选叠加；失败的记录都删掉后开关自动消失，不会留下一个空列表。预览数据里有一条调用改成了超时（真实使用里本来就会有），截图和版式检查能画出这个开关。

## 第 49 轮：PR 讨论弹窗（`ae8c2d2`，另有截图动作 `446fa87`）

PR 讨论弹窗复用评审问题的卡片样式，第 40 轮的改版也作用到了这里。截图核对后，操作靠左排在评论下面，没有问题；只有第一条评论上方的分隔线紧贴弹窗标题栏，显得多余，已去掉。截图脚本加了 `pr-discussion` 动作，以后可以直接截这个弹窗。

## 第 50 轮：批准或合并前的 P1 提醒（`19481ea`）

评审报告和“批准 / 合并”按钮在同一页，看完报告直接点批准时，很容易忘了还有没处理的 P1。现在从评审记录里点“批准”或“合并”，如果这份评审还有没撤销的 P1 问题，确认弹窗会先说一句“这份评审还有 N 个 P1 问题没有撤销；确认后照样批准”。只是提醒，不拦着操作：有些 P1 已在平台上讨论过，或者评审人判断可以先合。“需要修改”不需要这句提醒。

## 第 51 轮：沿用上次的关注点（`2e86af2`）

重新评审一个 PR 时，想看的往往和上次一样（比如“重点看超时后的资源释放”），却要重新打一遍。现在准备页的关注点输入框是空的，而同一连接下这个 PR 上次的评审或问答填过关注点时，输入框上方会写出“上次对这个 PR 的关注点：…”（过长的截短显示），点“沿用”就填进输入框，这句提示随之消失。不自动填入，免得把上次的要求悄悄带进这次。

## 第 52 轮：导出也带上上次问题的去向（`4c9704b`）

第 47 轮让评审摘要写上上次问题的结论，但导出报告和“复制为 Markdown”里还没有这一节，本机以外就看不到复核的结果。现在导出和复制的评审记录里多了“## 上次评审的问题（提交 …）”一节，逐条写优先级、标题、位置、当前状态；复核过的附理由或改写后的说明，发布过的注明“已发布为 PR 评论”。跟摘要不同，这里没复核的也列出来，因为它是完整记录。

## 第六次复查（`35ae6e4`、`d011c97`、`ad28faa`）

复查第 43–47 轮，确认五处问题并修复：

- 第 43 轮快速跳转：结果按来源依次放入列表（评审在前、问答在后），显示时却是问答分组在上。高亮、↑↓ 和回车按列表顺序走，于是搜出两组时，回车打开的是下面那组的评审。现在放入后按分组顺序排一次，键盘和屏幕一致。
- 第 45 轮“上次评审”：会选中被停止或失败的评审。这种评审没有问题，整节因此消失，更早那次完整评审的问题就看不到了。现在只认完成或未完成（incomplete）的评审。另一种情况同根：上一次只评审了部分文件（第 26 轮就是这样引导的），更早那次在其它文件上的问题也会丢。现在逐次往前找：最近一次评审看过的文件以它为准，它没看过的文件沿用更早那次的结论。来源不止一次时标题写“之前评审的问题”，每条注明提交；复核按问题所属的那次评审记账，评审摘要和导出同样注明提交。
- 第 43 轮打开会话：开发模式（StrictMode）会把 effect 跑两遍，原来的会话被写进列表两次。现在换会话时顺手去重。生产包原本就不受影响。
- 第 45 轮复核按钮：点了以后按钮换成进度文字，焦点掉到页面上。现在先把焦点移到这一节的标题上。“全部复评”按钮有同样的写法，这次没改，记作已知问题。
- 孤儿复核记录：上次评审删掉后，它的复核记录不会清理，累计超过 200 条会让整份评审历史读不出来。现在每次复核时，只保留当前还在显示的那几次评审的记录，并最多留 200 条。

## 第 53 轮：全部复评的焦点（`c923546`）

第六次复查记下的已知问题：点“全部复评”后按钮换成“正在复评 i / N”，焦点掉到页面上。现在点击时先把焦点移到报告标题（“评审完成”）上，不滚动页面；键盘用户可以从那里继续 Tab，复评结束后焦点也还在报告里。

## 第 54 轮：进度只属于自己那份记录（`bc4374a`）

第六次复查提到的另一个小问题：“正在复评 i / N”“正在复核 i / N”的进度是整个评审页共用的。复核进行中用快速跳转换到另一份评审，那一份也会显示这边的进度，看起来像它自己在跑。现在进度记下属于哪份记录，只在那份记录里显示；别的记录照常显示，按钮因为评审页忙着而禁用。顺带修了一个老问题：全部复评跑到只剩最后一条时，那一行的显示条件（还没复评的超过 1 条）不再成立，进度提示提前消失。现在正在跑的那份记录始终显示这一行。

## 第 55 轮：PR 详情里用 N / P 跳问题（`f8ab3eb`）

第 38 轮的“‹ 问题 i / N ›”要用鼠标点。逐个看问题时手在键盘上，现在 PR 详情里按 N / P 也能跳到下一个或上一个问题，和点箭头一样（跨文件切换、首尾循环）。在文件路径搜索框或提交版本下拉框里操作时不触发，免得输入字母被当成跳转。两个箭头按钮带上 `aria-keyshortcuts`，读屏能知道快捷键；快捷键帮助的“搜索”组多了一行说明。

## 第 56 轮：模型页每个后端的用量（`9e43ca1`）

模型页按优先级排着好几个后端（本机 Qwen、DeepSeek、Codex CLI……），每个后端实际用了多少，只能去日志页一条条看。现在每个后端名字下面多一行“调用记录：N 次 · X tokens”，按本机保留的模型调用记录（默认最近 7 天）汇总；没被调用过的后端不写，不显示“0 次”。排失败后切换的顺序、决定要不要给某个后端填单价时，可以直接看这一行。只读已有的调用记录，不多发请求。

## 第 57 轮：全部复评和复核结束时通知（`fc3c8b3`）

第 12 轮让评审结束时发系统通知，但“全部复评”和“复核之前评审的问题”也要一条条调用模型，问题多时同样要好几分钟，人往往去做别的了。现在这两件事跑完或停下时，窗口不在前台就发一条通知，写明是哪个 PR、复评或复核了几条（如“sample/app#123 · 已复评 2 / 2 条”），点通知回到这份评审记录。窗口在前台时不打扰。评审结束的通知也改用同一个“回到这份记录”的函数，少了一段重复代码。

## 第 58 轮：摘要里不重复列旧问题（`701f71b`）

第六次复查提到：一条旧问题这次评审又报出来时，评审摘要会先在这次的问题里列一遍，末尾“上次评审的问题”的“仍然存在”下再列一遍。现在同一文件、同一标题的旧问题，在摘要末尾不再重复。只按标题完全相同来判断，不做模糊匹配，宁可偶尔重复，也不误删。导出和“上次评审的问题”一节不变，那里仍列出全部，因为它们是完整记录。

## 第 59 轮：之前也报过（`38c10e7`，另有 `c588d82`、`1bc2333`）

同一个问题经过一轮修改还在，比新问题更值得注意：可能作者漏看了评论，也可能改法没改到点上。现在这次评审的问题，如果之前的评审也报过（同一文件、同一标题，且当时没被撤销），标题后面多一个小标签“之前也报过”，读屏按标题跳读也能听到。顺带修了一个老问题：“全部复评”和“批量发布为 PR 评论”两个按钮贴在一起，中间没有间距。截图数据里最新那次评审也报了一条旧问题，能截到这个标签。

## 第七次复查（`677e8b1`、`222dbe6`）

复查第 48–55 轮，确认七处问题并修复：

- **第六次复查修错了方向**：停止、失败的评审并不是“没有问题”，服务端会保留已完成批次的问题和已评审文件。现在它们照常参与，只对自己评完的文件说话。原来的测试用了一个没有问题的停止评审，是因为错误的理由才通过的，已按真实数据重写。
- **覆盖集合**：原来把“有问题的文件”也算作评审过，结果一个文件只评了几批，就会挡住更早评审在这个文件其它位置的问题。现在只算完整评审过的文件，同一文件同一标题的旧问题去重。
- **已发布的问题会丢**：评审提示词要求不重复已有评论，所以中间那次评审即使看了这个文件，也不会再报已发布的问题，链上就把它当成被覆盖而隐藏了，而这正是最想跟进的问题。现在已发布的问题一直跟下去，直到某次中间评审把它复核为已不存在。
- **“上次评审”写错来源**：最近一次评审什么也没报、问题都来自更早那次时，标题仍写“上次评审（更早那次的日期和提交）”。现在“上次”指真正的最近一次评审，问题不全来自它时改写“之前评审的问题”，每条注明提交。
- **点“沿用”后焦点掉到页面上**：现在焦点移到关注点输入框。
- **PR 详情刚打开时 N / P 没反应**：弹窗初始焦点在标题栏的关闭按钮上，不在内容区里，按键到不了处理函数。现在按键处理挂到弹窗本身（`ModalDialog` 新增可选的 `onKeyDown`），焦点在哪都能用；测试改成从关闭按钮上按键。
- **单条“复评中…”也会串到别的记录**：第 54 轮只修了进度那一行。现在这个状态也带上记录 id。

另外，这一轮发现之前核对类型的命令一直没起作用：tsc 带颜色输出时，`grep "error TS"` 匹配不到错误行。这次正好把一个变量重名漏过去，被 vitest 抓到。之前各轮构建时都跑了类型检查（`npm run build` 会先跑 typecheck），而且都通过了，所以已安装的版本没有受影响。以后改用 `--pretty false` 并看退出码。

## 第 62 轮：发布评论前预览 Markdown（`43bfdb8`，另有 `65bf9a3`）

“发布为 PR 评论”的弹窗只有一个 Markdown 文本框，改完措辞后看不出发到平台上排出来是什么样。现在评论框上方有“编辑 / 预览”切换（沿用 PR 详情里“变更 / 文件内容”那种分段按钮）：预览用问答和报告同一套 Markdown 渲染，粗体、行内代码、列表、引用、表格都照样显示，下面注明“预览只是近似效果，发布后以平台显示为准”。切到预览时文本框只是隐藏，切回编辑后草稿、手动拉伸的高度和撤销记录都还在，焦点回到文本框；评论为空时“预览”不可点。单条问题、回答和评审摘要三处共用这个弹窗，所以都有预览。

做这个时发现一个所有弹窗都有的问题：弹窗里的输入框带 `autoFocus` 时，关闭后焦点落到页面上，回不到打开它的按钮（应用里有 23 处 `autoFocus`）。原因是 `ModalDialog` 在 effect 里才记“打开前的焦点”，而 `autoFocus` 在更早的提交阶段就把焦点给了输入框，记下的其实是输入框本身。现在改在渲染时记录；开发模式下 StrictMode 会先演练一次卸载，这时弹窗还在页面上，不能提前把焦点还回去，所以只在弹窗真正离开页面时才还。新测试在 StrictMode 下打开带 `autoFocus` 的弹窗再关闭，去掉任一处修改都会失败。

## 第八次复查（`b46bf6f`、`bc317b0`）

复查第 56–59 轮及第七次复查的修复，确认七处问题并修复：

- **同一个问题被报了几次时，复核结果和发布标记对不上**（中）：旧问题按“文件+标题”去重，只留最近的一份，但复核结果和“已发布”仍记在各自那份上。例如 c1 报了“重试没有上限”并发布为评论，c2 又报了一次；到 c3 只列 c2 那份，“已发布为 PR 评论”标记没了。用户把它复核为已不存在，到 c4 c2 那份不再显示，c1 那份因为发布过又冒了出来，还带着复核按钮。现在按问题跟踪：任何一次发布过，这个问题的每一份都算已发布；被复核为已不存在或被复评撤销时，更早的同名问题一起不再列出。
- **同一次评审里同文件、同标题的两条问题被合成一条**（中低）：服务端只去掉完全相同的问题，不同行的同名问题都会保留，列表却只显示一条。现在只和更新的评审去重，同一次评审内部不去重。
- **复评改写过标题的问题认不出来**（低）：“之前也报过”用旧问题的原标题，摘要去重用替代后的标题，两边口径不一致，摘要里又重复写了一遍“仍然存在”。现在原标题和替代标题两个都算。
- **同一提交上重跑评审时，前一次的复核不算数**（低）：之前评审的链只取别的提交上的评审，同一提交上重跑（比如上次被停止）时，前一次复核出的“已不存在”就丢了。现在复核结果取自这个 PR 所有更早的评审。
- **括注文案过时**：“之前几次评审的问题”后面的括注只说了“最近一次没看过的文件沿用更早的结论”，没提到发布过评论的问题会一直跟着。现在两种原因都写上。
- **“之前也报过”标签对比度不够**：浅色主题下是 4.13:1，不到 AA 的 4.5:1。改用 `--text-soft`，现在是 8.23:1。
- **模型页用量把没上报的 token 算成 0**：Apple 的系统模型从不上报 token，失败的调用也没有，结果显示“调用记录：2 次 · 0 tokens”，看着像没怎么用。现在和日志页一样：一次都没上报时只写次数，部分没上报时写“至少 X tokens”。

四个新测试逐一对应前四条，用修复前的代码跑都会失败；全量 2295 个测试通过。

## 第九次复查（`ff179dd`、`5f44c07`、`7f915e6`、`f6cea85`、`187fecc`）

复查第 60–63 轮及第八次复查的修复，确认下列问题并修复：

    - “之前也报过”改按配对判断。

- **复盘提醒的文案偏乐观**：提醒只在应用启动和数据刷新时检查，没有定时器，所以改成“到期后，应用运行时会发一条系统通知”。

## 第十次复查（`44fed45`、`2ffc84c`）

  - 原因：主进程的 `PrReviewService.load()` 在评审运行期间会直接拒绝读取（“已有评审或读取任务正在运行”）。界面预览的假接口没有模拟这个守卫，测试也只点了历史记录，所以没发现。

  - 修复：去掉读取上的这道守卫。评审开始时就拿到了自己的快照，之后不再去查快照表，并发读取别的 PR 不会影响它。追问、复评和预读的守卫保持不变。补了一个服务测试（评审进行中读取另一个 PR 成功，正在跑的评审照常被停止）。
- **读取中显示成“重试读取 PR”**（低）：评审期间读取不设全局的“读取中”状态，没有缓存的 PR 在读取时会出现“重试读取 PR”按钮。现在单独记一个“正在从平台读取”的状态，读取中显示“正在读取变更内容…”。
- **刚开始的评审被还没回来的读取拉走**（低）：评审结束后立即开始下一次，此前打开的另一个 PR 如果还在读取缓存，读完会把页面切过去。现在开始评审（以及直接生成 PR 概览或改进建议）时作废在途的读取。
- **评审结束时人在别处，页面没有任何提示**（低）：现在输入框上方写“「某 PR」评审完成 · N 个问题”，点“查看结果”回到那份评审，看过后提示消失。
- **同一提交的提示措辞过满，也没照顾到部分评审**（低）：
  - 核对还没完成或失败时，原来仍说“之后 PR 没有新改动”，现在只说“就是这个提交”。
  - 上次只评审了部分文件时，改为写明“但有 N 个文件没评审”，并给出“只评审这些”。
- **报告头的优先级计数包含已撤销的问题**（低）：和列表状态的口径对不上，现在只算没撤销的。
- **统计小字没有变小**（低）：被评审对话里更具体的段落样式盖住了，提高了选择器优先级。

## 第十一次复查（`ee56066`）

复查第 70 轮和第九、第十次复查的修复，确认下列问题并修复（都在“之前评审的问题”和准备页提示上）：

- **同一提交上重跑的评审被忽略**（中）：“之前评审的问题”只取别的提交上的评审，同一提交上重跑的评审只采信了它的复核。重跑已经判为误报的问题会以“文件有改动，尚未复核”再次出现，还要花一次调用去复核；摘要里也可能写“仍然存在”；重跑发布过评论的也不标“已发布”。现在当前评审和同一提交的重跑（读的是同一份代码）一起参与配对，从新到旧：配上且被撤销的旧问题不再列出，重跑发布过的算已发布。
- **配对按下标先来先得**（中）：一条报告可能抢走另一条报告更近的配对，结果隐藏了错的问题、“已发布”记错了对象，或者把一个问题拆成两条。现在每次评审的所有报告一起按行距从近到远分配，每条报告、每个问题最多配一次。
- **又报出的旧问题写“文件有改动，尚未复核”**（低）：它不会再给复核按钮，却仍这样写，也计入“N 个所在文件有改动”。现在写“这次评审又报了”，不计入“有改动”，导出也一样。

- **数字口径**（低）：报告头只算没撤销的问题，统计行却写全部问题数。现在统计行写“4 个问题（1 个已撤销）”。
- **“同一提交的上次评审已发布”要求同一行**（低）：同一份代码上，同一个问题报在相邻一两行也算已发布，放宽到相差 3 行以内。

## 第十二次复查（`a28a112`）

只复查第十一次复查的配对改动（限时 25 分钟），确认下列问题并修复：

- **重跑被“剩下的问题”误配**（高）：当前评审先配走最近的问题，同一提交的重跑只能在剩下的问题里找，而配对没有距离上限，结果会配到离得很远的另一个同名问题：已发布的问题被它的撤销隐藏，或者“已发布”记到错的问题上。现在当前评审和每次重跑各自和全部问题配对，同一个问题以较新的那次为准。
- **只被重跑配上的问题也写“这次评审又报了”**（中）：这类问题从摘要和复核里消失了，但这次评审其实没报它。现在只有这次评审自己配上的才算，重跑配上的按普通问题处理。
- **发布自己的问题让已被覆盖的旧问题重新出现**（低）：“已发布”能让问题越过“后来的评审已完整看过这个文件”这条规则，但这次或重跑的发布发生在那之后，不该让它重新出现。现在这种情况下不再标为已发布。
- **距离相同时看数组顺序**（低）：同样的数据，只因为旧评审里问题的排列顺序不同，结果就不同。现在距离相同时，优先保持两边在文件里的先后顺序。
- **一条已发布的评论对应多条问题**（低）：放宽到 3 行以内后，重跑发布过的一条评论会让这次评审里附近的几条都显示“已发布”。现在一一对应，只算最近的那一条。

只复查第十二次复查的修复（限时 20 分钟）。这次复查代理的命令被 worktree 隔离拦住，没能跑测试，结论是按代码逐步推演出来的，每条都给了具体数据；修复后我补了回归测试，修复前的代码上都会失败。确认下列问题并修复：
