## 第 2 轮：接入 code-meeseeks 的评审能力

用户要求把本机 `code-meeseeks` 仓库的代码评审能力加进“评审”。先由只读代理梳理 code-meeseeks 的评审链路（规则、指令、草稿发布、复评），再按 Decision 现有的 pi 评审与平台层逐项移植。

### 发布为 PR 行内评论（`f7dba7d`）

code-meeseeks 的核心立场是“AI 只做草稿，评审者确认后才发布”。Decision 原本明确不发评论，评审结论只能导出。

- 每条评审问题可以“转为评论”：弹窗先重新读取平台上的 PR 状态、源/目标分支与提交，评审者编辑 Markdown 措辞后发布到问题所在的变更行。
- 平台请求与 code-meeseeks 一致：GitHub `POST pulls/{n}/comments`（`side` 为 LEFT/RIGHT），GitLab `POST merge_requests/{iid}/discussions`（带 base/start/head SHA 的 position），Bitbucket Server `POST pull-requests/{id}/comments`（`anchor` 带 lineType/fileType，`diffType: EFFECTIVE`）。
- 发布前在主进程再核对一次提交与 PR 状态；与 Approve/Merge 共用“一次只允许一个平台写操作”的互斥。
- 平台返回 400/422（行已不在 diff 中、GitLab 重命名文件）时明确说明，保留草稿，不改发为普通评论；响应无法确认时提示先到平台核对，避免重复发布。
- 发布成功的问题记入本机评审历史（`published`），显示“已发布为 PR 评论”，不再提供第二次发布。

### 个人评审规则（`3714987`）

- 规则格式与 code-meeseeks 相同：一条规则一个 Markdown 文件，frontmatter `applies_to.project / repo / target_branch`（无锚点、区分大小写的正则）、`tools`、`priority`、`enabled`，正文是附加检查要求。
- 读取 `~/Library/Application Support/Decision/review-rules/` 与已有的 `~/.code-meeseeks/agent/rules/`，每次读取 PR 时重新加载；命中的规则最多 20 条、合计 3000 字，按“Ruleset N”分段放进每批评审的上下文，并在系统提示中说明规则不能突破只读与证据约束。
- 与 code-meeseeks 的一处有意差异：正则写错时 code-meeseeks 会把该字段当作“匹配全部”，这里改为跳过该规则并提示，避免一条写错的规则套用到所有仓库。
- 为了 `target_branch`，平台客户端读取 PR 时顺带取目标分支名（GitHub `base.ref`、GitLab `target_branch`、Bitbucket `toRef.displayId`）；缺失时只影响按分支限定的规则。
- 解析放在 `packages/storage`（已依赖 `yaml`），没有改动依赖或锁文件。

### 复评（`41f380d`）

对应 code-meeseeks 的复评闭环（keep / replace / drop）。每条问题可以“复评”：模型只针对这一条，结合它所在文件的 diff、PR 描述与命中的规则重新判断，给出保留、取代或撤销及理由。

- 结构化输出，而不是像 code-meeseeks 那样解析 `<verdict>` 标签；取代却缺少替代评论时报错，保留/撤销时丢弃模型多给的替代文本。
- 取代：显示替代评论，“转为评论”以替代文本起稿。撤销：问题划线、收起发布入口，可以再次复评改判。
- 较早的评审没有内存快照时，按原提交重新读取 diff；PR 已更新则明确拒绝。

### `/describe` 与 `/improve` 指令（`3c01abb`）

code-meeseeks 用斜杠指令驱动 pr-agent。追问框现在识别同名指令：`/describe` 展开为 PR 概览（类型、摘要、逐文件说明、评审关注点），`/improve` 展开为最多 4 条带 diff 代码块的改进建议；指令后可跟补充要求，未知指令按原文发送。复用现有追问链路（带本次提交、评审报告与缓存中的 diff），聊天记录里显示用户输入的原始指令。

### 规则的上下文预算（`ddf387f`）

每批评审的上下文有 12000 字上限，超出时整批失败。加入最多 3000 字的规则后，引号很多的 diff（JSON 转义让长度翻倍）加上较长的描述与关注点会越界。规则改为按每批剩余空间截取并提示，回归用例用引号密集的 diff 复现了原来的失败。

### 已有 PR 评论作为上下文

code-meeseeks 把 PR 上最近的评论交给 pr-agent，避免重复提出别人已经指出的问题。这里读取最近 20 条（GitHub 行内评审评论、GitLab 非系统备注、Bitbucket 评论动态，每条 300 字以内），每批只带当前文件的行内评论和普通评论，并与规则一样按剩余空间截取；读取失败只提示。和“发布为 PR 评论”配合：发布过的问题，重新评审时不会再被当作新问题提出。

### 规则入口与报告导出（`15cab97`、`1b50ac3`）

- 规则原本只写在 README 里。准备区现在总会列出命中情况（“同时按 N 条评审规则检查” 或 “没有命中的评审规则”），旁边的“添加规则 / 管理规则”打开 Decision 的规则目录；目录为空时先放入一条未启用的中文示例，写入用 `wx`，不会覆盖已有文件。
- 导出的评审报告在每条问题下写明复评结论（含替代评论）和“已发布为 PR 评论”，导出物反映问题的最终状态，而不只是模型最初的说法。

### 快捷按钮（`8a56434`）

`/describe`、`/improve` 只写在占位文字里不容易被发现。追问框工具栏加了“PR 概览”“改进建议”两个按钮，直接发送对应指令，不清空正在输入的问题。
