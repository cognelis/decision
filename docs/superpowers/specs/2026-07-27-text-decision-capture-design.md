# Decision 文本决策识别与上下文采集设计

日期：2026-07-27
状态：已确认

## 1. 背景

Decision 当前可以被动记录 Claude Code 和 Codex 原生提问工具产生的决策，
也有一个保守的纯文本兜底：

- assistant 的最后一段必须像明确问题；
- 通常需要以 `?` 或 `？` 结尾；
- 下一条同会话用户输入被视为回答。

实际使用中，LLM 经常不用原生提问工具，而是通过普通文本请用户选择，例如：

- “接下来我可以先补测试，再改实现”
- “推荐方案 3，也可以先做 1 再做 3”
- “这里有两种处理方式……”后直接停下来等待

这些表达不一定带问号，选项和背景也可能分散在多段文本中。现有兜底因此触达率很低。
此外，当前记录通常只有问题和答案，缺少任务目标、约束和权衡，后续很难复盘为什么做出
这个选择。

本阶段需要在不改变 Claude Code、Codex 原生行为的前提下，提高这类
“LLM 通过文本请求人类决策”的采集率，并把有限、相关的上下文写入最终 Markdown。

## 2. 已确认的产品边界

### 2.1 记录什么

只记录符合以下顺序的人工决策：

1. LLM 在普通文本中把一个选择、批准或方向判断交给用户；
2. LLM 停止并等待；
3. 用户在下一轮作出相关回答。

典型回答包括：

- 选择某个编号或命名选项；
- 同意或拒绝；
- 提供“先 1 后 3”一类组合方案；
- 给出一个与候选项不同的自定义选择。

### 2.2 不记录什么

- LLM 自己作出的实现决策；
- 进度汇报、解释、教程或反问；
- 代码、日志、引用材料中的问句；
- 用户没有回答、而是开启了无关新任务的文本；
- 完整会话、完整 transcript 或模型内部推理过程；
- 被用户标记为“不记录”的决策。

### 2.3 不改变宿主行为

- 不劫持、替换或包装 Claude Code、Codex 的原生提问工具；
- 不向 LLM 注入“必须调用某个工具”的提示；
- 不阻塞宿主，不改变用户回答回到宿主的路径；
- hooks 只做旁路观察，任何错误都静默放行；
- MCP 不是该功能的必需路径。

### 2.4 数据原则

- 已接受的决策以 Obsidian Markdown 为唯一事实来源；
- SQLite 只保存可重建的检索字段、状态和派生索引；
- 未确认候选只是短期本地缓冲，不是正式决策记录；
- 不引入 DuckDB；
- 不调用云端分类服务。

## 3. 方案选择

采用“本地轮次级评分识别器”，并保留替换为本地模型的接口。

本阶段实现规则评分器。相比继续堆叠单个正则，它会同时观察：

- 最近一条用户任务；
- 当前 assistant 轮次；
- assistant 末尾的决策请求块；
- 下一条用户回答；
- 问答之间的关联性。

识别结果分为高、中、低三档：

| 置信度 | 处理方式 |
| --- | --- |
| 高 | 立即进入现有理由采集流程 |
| 中 | 静默进入“待确认候选”队列，不打断当前工作 |
| 低 | 丢弃 |

未来可以用 `LocalModelClassifier` 替换规则分类器，但输入输出契约、队列和持久化流程保持
不变。本阶段不下载、不捆绑也不运行本地模型。

## 4. 核心流程

### 4.1 Stop：发现待回答请求

Claude Code 或 Codex 的 Stop hook 运行时：

1. 优先读取 hook 直接提供的 assistant 文本；
2. 缺失时，只读取 transcript 尾部最多 64 KiB；
3. 规范化为“最近用户任务 + 当前 assistant 轮次”；
4. 从 assistant 轮次中定位最后一个决策请求块；
5. 提取问题、选项、任务背景和决策前提；
6. 计算回答前分数；
7. 将结果保存为同客户端、同会话的待回答请求。

一个 assistant 轮次只保存最后一个决策请求块。一个请求块里如果有多个编号子问题，
本阶段保留为一个组合决策，不把它们拆成多个记录，避免把下一条回答错误映射到其中一项。

待回答请求最多保留 24 小时。新的同会话请求替换旧请求，避免陈旧问题与新回答配对。

### 4.2 UserPromptSubmit：完成问答配对

下一次同客户端、同会话的 UserPromptSubmit hook 运行时：

1. 读取待回答请求；
2. 判断新用户输入是否像该请求的回答；
3. 加入回答关联信号，计算最终分数；
4. 根据分档路由；
5. 删除待回答请求。

以下回答即使很短也应被识别：

- `1`、`2`
- `可以`、`不要`
- `方案 3`
- `先 1 后 3`
- `按你的建议`

如果新输入明显是无关的新任务，则丢弃旧请求，不产生正式记录或候选。

### 4.3 高置信度

高置信度事件沿用现有理由采集流程：

- 展示问题、选择结果和简短上下文预览；
- 用户可选预设理由因素或自由输入；
- 可跳过理由；
- 可选择稍后处理，进入现有待补理由队列；
- 可选择“不记录此次决策”。

只有用户完成、跳过或选择稍后处理后，决策才写入 Markdown。选择“不记录”时，不写
Markdown 和 SQLite。

### 4.4 中置信度

中置信度事件不立即弹岛，只写入私有的“待确认候选”缓冲。

菜单栏显示“待确认候选 N”。用户打开后按时间从旧到新查看，每项提供：

- `是，记录并补充理由`
- `不是，忽略`

关闭窗口或按 Escape 等价于暂不处理，候选保留。

选择“是”后，该候选提升为正常理由采集项，并沿用高置信度流程。选择“不是”后删除
正文，只保留不含内容的去重收据，防止同一轮被重复采集。

候选缓冲规则：

- 最多 100 项；
- 默认保留 7 天；
- 超限时先删除过期项，再删除最旧项；
- App 未运行时只静默落盘，不为中置信度候选主动启动 App；
- 未被提升前，不写入 Markdown 或 SQLite。

“待确认候选”不是完整的决策历史中心。本阶段只提供数量入口和逐项确认。

## 5. 识别模型

### 5.1 输出契约

文本分析器返回：

```ts
interface TextDecisionAnalysis {
  request: {
    question: string;
    options: Array<{
      id: string;
      label: string;
      description?: string;
    }>;
  };
  context: {
    taskBackground?: string;
    decisionFraming?: string;
  };
  score: number;
  signals: string[];
  detectorVersion: string;
}
```

`signals` 只保存枚举标识，例如 `has_choice_prompt`，不复制额外原文。

分类器接口只负责语义判断：

```ts
interface TextDecisionClassifier {
  classify(input: DecisionTurnExcerpt): ClassificationResult;
}
```

当前实现为 `RuleBasedClassifier`，版本为 `rules-v1`。未来
`LocalModelClassifier` 必须遵循同一接口。

### 5.2 正向信号

- 明确邀请用户决定：`你希望`、`请选择`、`是否`、`要不要`、`哪种方案`；
- 出现两个或以上并列选项、编号列表或“方案 A / 方案 B”；
- 出现 `权衡`、`风险`、`建议`、`取舍`、`优先级` 等决策语义；
- assistant 在给出请求后结束，没有继续自行执行；
- 下一条用户输入命中选项编号、标签、肯定/否定或组合顺序；
- 下一条用户输入与问题、选项存在明显词汇关联。

### 5.3 负向信号

- 反问、教程示例、FAQ、引用或转述；
- 代码块、日志、报错、diff 中的问号；
- 仅汇报“是否通过”等运行状态；
- assistant 已经明确自行决定并继续执行；
- 下一条用户输入开启无关任务；
- 文本只是请求用户补充客观资料，不涉及选择、批准或方向判断。

最后一项用于区分“请提供 API key”与“是否现在配置 API key”。前者是信息收集，后者才是
决策。

### 5.4 分数与硬性护栏

分数范围为 0–100：

- 高：`>= 75`
- 中：`50–74`
- 低：`< 50`

回答前和回答后分别评分，最终分数包含问答关联度。

以下护栏优先于分数：

- 请求内容完全位于代码、日志或引用中时直接拒绝；
- 同时缺少“请求用户回应”与“存在备选方案”时，不得进入高置信度；
- 下一条输入被判定为明显无关新任务时直接丢弃；
- 不能可靠恢复同一客户端和会话标识时不做配对。

阈值作为版本化配置保存在分析模块内部，不放入面向用户的设置页。本阶段先通过固定语料
校准，避免把调参责任交给用户。

## 6. 上下文采集

### 6.1 最终记录包含的内容

每条正式文本决策保存：

- 任务背景：触发本轮工作的最近用户目标或请求摘录；
- 决策前提：assistant 在问题前给出的约束、风险、权衡或建议；
- 原始决策问题；
- 候选选项及其简短说明；
- 用户选择或自定义回答；
- 用户补充理由和预设理由因素；
- 来源客户端、项目、会话、轮次和时间；
- 捕获模式、识别器版本和置信度档位。

### 6.2 提取原则

- 使用原文摘录，不在当前阶段调用模型生成摘要；
- 只从最近用户任务与当前 assistant 轮次提取；
- 删除代码块、日志块、工具输出和明显重复段落；
- 问题、选项、答案使用独立字段，不重复塞入背景；
- 上下文正文合计最多 6,000 字符；
- 优先保留离问题最近的约束与权衡；
- 超限时按段落边界截断，并在展示中标记为已截断；
- 不保存完整 transcript 路径或 transcript 副本。

### 6.3 界面呈现

理由页以问题和选择结果为主。上下文默认显示最多两行预览，并提供“展开上下文”。
展开后在有最大高度的滚动区展示任务背景和决策前提，避免理由页无限增高。

待确认候选页使用相同的上下文组件，保证用户能根据当时条件判断它是不是值得记录的
决策。

## 7. 数据模型与事实来源

### 7.1 协议演进

`CapturedDecisionEvent` 增加可选的结构化上下文和识别元数据：

```ts
interface CapturedDecisionContext {
  taskBackground?: string;
  decisionFraming?: string;
  truncated?: boolean;
}

interface CaptureDetection {
  band: "high" | "medium";
  score: number;
  detectorVersion: string;
  signals: string[];
}
```

新增字段必须可选，保证旧 spool 和旧事件仍可读取。原生工具捕获可以没有 detection。

### 7.2 正式记录

`DecisionRecord` 保留现有 `contextSummary` 兼容旧 Markdown，同时增加结构化上下文。
新文本决策优先写结构化字段；读取旧笔记时仍将 `## 当时上下文` 解析为
`contextSummary`。

新 Markdown 的上下文区域为：

```md
## 当时上下文

### 任务背景

……

### 约束与考虑

……
```

问题、候选方案、结果和理由继续使用各自现有区域。识别器版本和置信度档位写入
frontmatter；详细 signal 不进入可读正文。

用户可以直接编辑 Markdown。重建索引必须以 Markdown 当前内容为准，不能用临时候选或
旧 SQLite 覆盖用户修改。

### 7.3 两类临时状态

待回答请求和待确认候选使用不同的数据结构和目录：

- 待回答请求：尚未获得用户回答，24 小时过期；
- 待确认候选：已经形成问答对，但置信度为中，7 天过期。

两者都采用原子写入、私有目录权限和稳定去重键。文件名使用哈希，不含问题或项目原文。
消费成功后先记录不含正文的收据，再删除正文，保证崩溃恢复时既不重复弹出，也不永久
保留用户已忽略的内容。

## 8. 模块边界

桥接层新增或调整以下职责：

- `TranscriptTurnReader`
  - 读取 hook 直接字段或 bounded transcript tail；
  - 恢复最近用户任务和当前 assistant 轮次；
  - 不持久化原始 transcript。

- `TextDecisionAnalyzer`
  - 定位请求块；
  - 提取选项与结构化上下文；
  - 调用分类器并返回版本化分析结果。

- `TextDecisionClassifier`
  - 当前使用规则评分；
  - 为未来本地模型保留替换接口。

- `TextDecisionCaptureCoordinator`
  - 在 Stop 保存待回答请求；
  - 在 UserPromptSubmit 配对、复评和路由；
  - 不负责 Markdown 写入。

- `CandidateSpool`
  - 管理中置信度候选、过期、容量、收据和去重；
  - 与正式 capture spool 隔离。

桌面端负责：

- 高置信度事件的现有理由队列；
- 待确认候选数量与审核入口；
- 候选提升或忽略；
- 正式 Markdown 写入和 SQLite 派生索引。

这样可以把“如何判断”与“如何保存正式决策”分开。未来接入本地模型时，不改 hooks、
桌面交互或 Markdown 事实模型。

## 9. 失败与隐私策略

- 所有 hooks 固定 fail-open；异常、超时或格式变化不能影响 Claude Code/Codex；
- hooks 不向 stdout 输出产品内容，避免污染宿主协议；
- 不读取 transcript 尾部以外的历史；
- 解析失败时宁可不捕获，也不保存无法证明相关的大段文本；
- 私有临时目录使用 `0700`，文件使用 `0600`；
- 中置信度候选不会主动唤醒 App；
- App 崩溃后可从 spool 恢复，但已消费收据阻止重复；
- 所有正文都受长度上限约束；
- 不采集模型隐藏推理、系统提示或未出现在用户可见对话中的信息。

## 10. 测试与验收

### 10.1 固定语料

建立匿名化的中英文轮次对语料，至少覆盖：

- 带问号的明确选择；
- 不带问号的选择邀请；
- 多段说明后给出选项；
- 编号、命名、是/否和组合顺序；
- 用户自定义答案；
- 反问、教程、FAQ、引用；
- 代码、日志和错误输出；
- 仅请求客观信息；
- assistant 已自行决定；
- 下一条用户输入开启新任务；
- Claude Code 与 Codex 当前 transcript 形状。

语料必须同时包含正例、难负例和预期置信度档位。

### 10.2 目标

在固定语料上：

- 高置信度 precision 不低于 95%；
- 高 + 中置信度 recall 不低于 90%；
- 明显无关新任务不得与旧请求配对；
- 持久化正文不得包含被剔除的代码、日志或无关 transcript；
- 同一轮重放不得产生重复正式记录或候选；
- 64 KiB 输入的本地分析 p95 不高于 150 ms。

这些指标是合并门槛，不是对真实世界绝对准确率的承诺。新增误判样本必须先加入语料，
再调整规则。

### 10.3 TDD 顺序

1. 先为请求块、选项、上下文和正负信号建立失败测试；
2. 实现最小规则分析器；
3. 先测 Stop/UserPromptSubmit 配对，再实现协调器；
4. 先测候选过期、容量、去重和崩溃恢复，再实现候选 spool；
5. 先测协议向后兼容和 Markdown round-trip，再扩展数据模型；
6. 先测候选 UI 状态，再接桌面入口；
7. 运行完整单元、集成、类型检查和安装包 smoke test。

### 10.4 手工验收

使用 Claude Code 和 Codex 分别验证：

1. 原生提问工具仍按宿主原样工作；
2. 普通文本“方案 1 还是方案 2”并回答后，能出现理由岛；
3. 普通文本不带问号也能识别；
4. `先 1 后 3` 能作为完整选择保存；
5. 中置信度项不打断工作，并出现在菜单栏候选入口；
6. 忽略候选后不再重复出现；
7. 选择稍后处理后进入现有待补理由队列；
8. Markdown 同时包含任务背景、约束与考虑、问题、选项、选择和理由；
9. 删除 SQLite 后重建，正式记录仍完整；
10. hooks 或 App 不可用时，Claude Code/Codex 行为不受影响。

## 11. 本阶段范围

### 包含

- 规则评分式文本决策分析；
- 问答关联与三档路由；
- 任务背景、决策前提和选项提取；
- 中置信度待确认候选队列；
- 候选确认、忽略和现有理由流程复用；
- Markdown 结构化上下文与 SQLite 派生索引；
- 本地模型分类器扩展接口。

### 不包含

- 本地模型的实际集成；
- 云端 AI 分类或摘要；
- LLM 自主决策采集；
- 完整决策历史、统计、聚类或知识图谱；
- 自动生成 Skills 或工作流；
- 完整会话归档；
- 对 Claude Code、Codex 原生交互的任何替换。

## 12. 成功标准

该阶段成功的判断不是“所有问句都能弹岛”，而是：

- 对真正交给用户的文本决策，明显提高覆盖率；
- 高置信度弹岛保持低误报；
- 不确定项可以稍后确认，不打断当前开发；
- 最终 Markdown 足以解释当时在什么任务、什么约束下做了什么选择；
- 整个系统仍然是旁路、可失败、可删除 SQLite 后重建的；
- 未来升级本地模型时无需重写采集、队列和事实存储。
