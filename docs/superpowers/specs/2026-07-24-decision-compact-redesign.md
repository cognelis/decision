# 决策浮岛交互重设计

## 问题

当前紧凑态使用 420×72 窗口，把来源、项目、问题、2–4 个选项、“其它”
入口和“不记录此次决策”同时塞进一行。真实中文选项会被截断，来源信息和
问题的字号关系失衡，按钮又窄又薄，记录复选框悬浮在底部，整个界面更像
压缩过度的工具条，而不是一个可读、可操作的决策界面。

选择完成后的理由页仍使用 560×640 大面板，与选择页不是同一套视觉语言。
理由因素虽然可以勾选，但“保存理由”只检查文本框；只选预设因素时按钮
仍然不可用，用户的选择也不会被提交。

Renderer 和窗口管理器还分别实现了一套紧凑态判定。两份规则一旦不同步，
窗口会按一种模式调整尺寸，而页面按另一种模式渲染。

## 目标

- 简短决策以顶部浮岛完成，问题和所有选项无需截断；
- 选择页与理由页使用同一套外壳、字号、间距、按钮和磨砂语言；
- 选项具有足够的视觉重量和点击面积；
- 允许预设选择、自定义选择、记录开关、队列提示和键盘操作；
- 只选择预设理由也可以完成，并真实写入 Markdown 与 SQLite；
- 复杂内容自动使用现有大面板；
- 深色、浅色和跟随系统主题都保持清晰。

## 非目标

- 不重做设置页；
- 不改变 MCP、Hooks、决策队列或 Obsidian 目录结构；
- 不增加动画框架、图标库或新的持久化数据库；
- 不把选项描述和详细取舍塞进浮岛；
- 不在本轮加入决策知识图谱或 DuckDB 分析层。

## 方案

采用“顶部任务条 + 下拉主体”的单体浮岛。两层属于同一个窗口和同一个
视觉表面，不使用两个独立悬浮卡片。

### 尺寸与比例

- 选择状态窗口宽 560px，高约 286px；
- 理由状态宽 560px，高约 372px；
- 顶部任务条宽 360px，高 44px，水平居中；
- 下方主体占满 560px，顶部与任务条只保留 2px 视觉接缝；
- 主体圆角 22px，继续使用现有主题 token、透明度、模糊和阴影；
- 窗口切换尺寸时保持顶部中心点不变，不能因为宽度变化向右偏移；
- 小尺寸显示器上限制在工作区宽度内，但最小左右安全边距为 12px。

### 顶部任务条

顶部任务条只显示：

1. 状态点；
2. `来源 · 项目名`；
3. `N 个待处理`。

来源和项目使用与问题相同的基础字号，不再缩成辅助小字。项目过长时才
省略；队列数量保持次要色，不添加图标、Logo 或额外标签。

### 选择主体

主体第一行显示完整问题，右侧以次要文字显示“选择”。问题使用基础字号和
中等字重，不再用大标题制造失衡。

预设选项纵向排列：

- 每个选项占满主体宽度；
- 每行高度 50px；
- 左侧显示 A、B 等简短序号，中间显示完整标签；
- 推荐项在右侧显示“推荐”，但不增加额外胶囊；
- 允许自定义时，“其它方式…”作为最后一行，与预设选项等高；
- hover、键盘焦点和提交中禁用状态沿用主题系统。

主体底部左侧保留原生复选框“不记录此次决策”，不改成 switch，也不放到
标题栏。右侧显示“选择后继续填写理由”的次要提示。勾选“不记录”后提交
选择会直接完成，不进入理由页。

### 自定义选择

点击“其它方式…”后，选项区域原位替换为：

- 单行输入框；
- 主操作“提交”；
- 次操作“返回”。

问题、顶部任务条和“不记录此次决策”保持可见。空输入不能提交；返回时
保留已经输入的文字。

## 理由主体

记录型选择完成后，窗口在同一位置平滑调整为理由尺寸，顶部任务条不变。
主体第一行显示：

`为什么选择「已选方案」？`

右侧显示次要文字“理由”。不再重复大号“为什么这样选？”标题、来源或
项目。

理由区域按顺序显示：

1. “判断依据（可多选）”因素按钮；
2. “补充说明（可选）”文本框；
3. “返回”、“完成”、“稍后补充”和“跳过理由”操作。

因素按钮使用现有六个稳定 ID：

- `goal-fit`：目标匹配；
- `maintainability`：可维护性；
- `risk`：风险；
- `implementation-cost`：实现成本；
- `time`：时间；
- `reversibility`：可逆性。

只要选择至少一个因素，或补充说明包含非空文本，“完成”就可用。

提交规则：

- 有补充说明时，`rationale` 原样使用用户文本；
- 只有因素时，按界面顺序生成可读文本，例如
  `选择依据：目标匹配、可维护性。`；
- 只要存在因素，就同时提交稳定的 `reasonFactors` ID；
- 因此现有 protocol 的 `captured` 状态仍然总有 rationale 文本，
  不需要放宽 schema；
- Markdown 理由正文和 SQLite `rationale` 都能直接阅读，因素 ID 仍用于
  后续统计和技能提炼。

“稍后补充”和“跳过理由”保留，但使用较低视觉层级。提交期间所有输入与
操作禁用，防止重复提交。

## 紧凑资格

新增共享纯函数，供 Renderer 和窗口管理器共同使用。只有同时满足以下条件
才使用浮岛：

- 当前状态为 `awaiting_choice`；
- 恰好有两个预设选项；
- 问题按 Unicode 字符计数不超过 36；
- 两个选项标签各不超过 18；
- 上下文摘要不超过 180。

`allowCustom` 不影响资格；它只决定是否出现第三行“其它方式…”。
任一条件不满足时继续使用现有 560×640 大面板。

共享函数放在 desktop shared 层，不依赖 DOM 或 Electron。`App` 与
`WindowManager` 都调用它，删除当前两份重复判定。

## 组件边界

- `shared/decision-layout.ts`：紧凑资格和窗口模式的共享纯函数；
- `App`：根据共享函数选择浮岛或大面板，并保留错误边界；
- `DecisionHeader`：顶部任务条，选择页和理由页共用；
- `ChoiceStep`：纵向选项、自定义模式和“不记录”复选框；
- `RationaleStep`：因素、可选文本和提交规则；
- `WindowManager`：选择、理由、大面板和设置四种尺寸，并保持顶部中心点；
- `styles.css`：统一浮岛外壳、50px 选项行与两种状态的响应式样式。

不为纯样式拆出过多组件；只有同时被选择页和理由页复用的任务条需要独立。

## 状态与异常

- Escape 在选择状态继续取消当前决策；
- 提交失败后保留当前选择、复选框、因素和文本，错误在主体底部显示；
- 提交期间禁用所有会改变状态的控件；
- 自定义输入返回时不清空；
- “不记录”选择不创建 Markdown 或 SQLite 记录；
- 理由因素与生成文本通过现有 IPC、core 和 storage 流程保存；
- 窗口关闭行为、always-on-top、安全策略和菜单栏行为不变。

## 验证

### 自动化

- 共享紧凑资格覆盖两个选项、三个选项、长问题、长标签和长上下文；
- `App` 断言真实中文文案使用浮岛，并完整显示 A、B 和“其它方式…”；
- 选项行具备 50px 最小高度且没有横向溢出；
- 普通复选框更新 `DecisionChoice.record`，没有 switch 语义；
- 选择后理由状态仍使用浮岛布局；
- 只选一个因素时“完成”可用，并提交生成文本与稳定因素 ID；
- 文本与因素同时存在时，文本原样保存；
- 没有因素且文本为空时“完成”禁用；
- `WindowManager` 断言选择和理由尺寸，并验证调整宽度时顶部中心不移动；
- 现有 deferred、skipped、持久化、设置和无障碍测试继续通过。

### 真实应用

打包安装后分别检查深色、浅色和 auto 主题：

- 顶部任务条与主体比例协调；
- 来源、项目、问题和队列文字层级清楚；
- 50px 选项行不再显得单薄；
- 选项和“其它方式…”均无省略号；
- “不记录此次决策”是普通复选框；
- 选择页和理由页外壳一致；
- 只选择预设理由即可完成；
- Markdown 与 SQLite 同时包含所选方案和理由；
- 浮岛始终位于当前显示器顶部中央。
