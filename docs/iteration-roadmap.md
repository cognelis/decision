事前核对按 IMP-081 落地。隔离同样做在结构和措辞上而不是做在「不召回」上：偏好想法走 `signals` 而不是 `matches`，否则 MCP 文本、桌面预览和任何后续消费方都会失去区分能力；让 signals 去翻转 `status`，则会让「没有相关原则」这个结论本身变得不可信。协议里 `signals` 与 `noPreferencePromoted` 都带默认值，旧载荷仍然可解析。

下拉框的根因是全应用没有一处设过 `appearance: none`：系统在应用自己画的边框里面再画一套控件，主题变量一个都进不去。改完之后靠实测又翻出两个只看截图发现不了的问题。一是 `appearance: none` 把系统焦点环也一并去掉了，而 `select` 不在全局 `:focus-visible` 规则里、工具栏两个筛选框还各自写了 `outline: 0`，键盘聚焦后没有任何指示；二是 `.glass-input` 用 `background:` 简写，会把刚设上的箭头图像清掉——问答页的「对话」「回答模型」和日志页的「用途」三个下拉框都挂着这个 class，所以都留了箭头位却没有箭头。

日志页的「用途」筛选此前从没被任何截图或布局检查画出来过：面板在用途种类少于 2 时整个隐藏它，而预览里 9 条调用记录的 purpose 全是同一个。这和上一轮「偏好与想法视图从没被渲染过」是同一类问题——样本单薄到某个分支永远不执行，检查全绿但什么也没检查。预览样本已改为轮换三种用途，并由 `preview-fidelity.test.ts` 守住。四个调色板块的色标一致性也补了守卫：新增一个色标只写进其中几块，界面在另一半主题下就会静默缺东西。

确认闸门的移除做了实跑验证，不只是跑测试：在已安装的应用里向远端模型发真实问题，没有出现确认横幅，回答带引用正常返回。其中一条问题连续失败，为排除是这次改动造成的，回退 `658c722` 重新构建做了同问题对照——两个构建各跑 3 次都是 2 次失败、1 次完成，完成的那次回答内容也一致，失败跟问题和模型的空响应走，与闸门无关。

问答页和首页也进了 `check-settings-layout.cjs`。这两页都自己管滚动（问答滚消息流、首页滚自己那一栏），没有 `.desktop-page-scroll`，容器顶上之后页面相关的数字就不与其它界面可比，所以只断言可比的那部分——外壳尺寸、标题、控件全部有名字、原生控件用应用强调色、卡片不重叠。这一步之前，新加的两条守卫只覆盖八个主界面里的六个。仍未覆盖的：整屏巡检只跑浅色，深色实测同样干净但没有进测试（布局不随主题变化，加进去只是把这项检查的开销翻倍）。

**一条实跑出来的链，修到底为止。** 用本机 Qwen 在问答页提一个问题，失败。逐层量下来是四件事叠在一起：

1. **循环白烧步数。** 模型连续 6 次要求读同一个不存在的证据编号，每次都被守卫拦下、记一条 `step_limit`，然后继续下一步——注释写的是「force the answer」，代码却只是 `continue`。8 步预算烧光后才被迫作答，那一步失败时已经没有重试余量。改成任何退化步骤（空的或重复的检索词、不存在或已读过的编号）直接把下一步标成必须作答。实测从「6 次无效读 + 2 次作答」变成「1 次检索 + 1 次无效读 + 3 次作答尝试」。
2. **分类的超时预算掐断了作答。** `timeoutMs` 一个字段管两件事：分类必须快，不能拖住采集，内置本机 profile 的 5 秒是按它定的；而作答是用户正在等的长文，2B 模型 5 秒写不完。网关侧给结构化生成加了 30 秒下限（状态探测那边本来就有个 5 秒上限，同一种按用途收窄的做法，这次是按用途放宽），profile 设得更高仍按自己的值。
3. **provider 内部还有一层同样的 5 秒。** Qwen 的推理助手对分类和生成用同一个计时器，读的是 profile 的值，连错误文案都写着 classification。改成由调用方传入预算，分类照旧、生成用 30 秒下限。实测作答步骤不再是 `timed_out`。
4. **模型不知道 `read` 该填哪个数。** 证据行长这样：`[3] DEC-0167 命名优先采用业界通用口径（关键词命中）`——一行上两个数字，编号在前、标题自带的编号在后，提示里从没说过哪个是 `read` 要的。改成在指令里点名当前可读的编号。实测模型改要 `index=3`（有效编号）并真的读到了全文，不再空转。

**到此为止仍然失败，原因由应用自己记着。** 循环现在是干净的「检索 → 读全文 → 作答」，作答步骤有 30 秒预算也能跑完，但返回空输出。「日志」里这一步的留痕写得很清楚：`errorCode: output_limit`、`Qwen output reached the 1024-token limit before completing valid JSON`、`usage: 输入 4182 token / 输出 1024 token`。

也就是说不是超时、不是循环、也不是模型"不会答"：它**一直在写，写满 1024 个输出 token 也没把那段 JSON 收尾**，于是整段作废。两个常量在这里同时顶住了——`QWEN_MAX_STRUCTURED_OUTPUT_TOKENS = 1_024` 是输出上限，`contextSize: 4_096` 是上下文窗口，而这一步的输入已经 4182 token，本身就压着窗口上沿。

没有在本轮改，是因为这是用户机器上的资源取舍：放宽输出上限要同时放宽上下文，而上下文翻倍意味着 KV cache 跟着翻倍，代价落在内存上；分类（本机模型的主要用途）并不需要更大的窗口。这两个数字该怎么定，应该由知道这台机器余量的人来定，而不是在没有实测内存曲线的前提下拍一个。试过一件、没起作用、但留下了：系统提示原本从没告诉模型答案有长度上限，于是加了一句「控制在 800 字以内，超长的回答会被整段丢弃」。对这个 2B 模型没用——它照样写满 1024 token（输入已经降到 2239，说明循环那几处修对了，是输出侧顶住）。留着是因为这条约束本身是对的，而且它保护的不只是本机模型：`maxOutputTokens` 对所有后端都是 1024，此前一次成功的远端回答约 1000 字，本来就贴着这条线。

**顺带说明**：这条链上真正值得称道的是留痕本身——前几层都是靠 `model-traces` 一步步量出来的，最后一层应用自己就把原因写好了（`output_limit` + 那句 token 上限说明），我一开始按上下文溢出猜错了方向，是这条留痕把结论纠正过来的。

## 以推荐收尾的设计问答

用户给了一张真实截图：另一个仓库里的设计问答，`问题 21（修订）` 加三条 `- A: …` 选项，最后一段是「我建议 C。B 的问题是…」，用户回一个 `C`。这类交流一整天下来能有几十轮，每一轮都是一次真决策。

实测下来当时**整段不产生任何候选**，两个原因叠着：

1. **识别只看最后一段的提问措辞。** `EXPLICIT_CHOICE` 那张词表要的是「你希望 / 请选择 / 是否 / 哪个」之类，而一段好的设计问答恰恰不这么收尾——它把选项摆完、给出推荐，然后停下等人。末段是「我建议 C。…」时一个词都对不上，直接 `return null`。连「我建议 C。你怎么看？」也不行，因为「你怎么看」不在词表里。
2. **选项字母没当成编号。** `- A: 只做读取兜底…` 走的是项目符号那一支，字母留在 label 上、id 退化成 `1/2/3`。用户回的那个 `C` 之所以还能碰上，靠的是 `answer.includes(label)` 里 label 恰好是单个字母 `c`——反过来说，任何含字母 b 的回答都会命中选项 B，这条规则本身几乎对任何输入都成立。

改法：消息里有 2 条以上成列选项、且最后一段推荐了其中之一，就算一次待决策请求（信号记为 `recommends_one_option`，与 `has_choice_prompt` 分开）；项目符号自带的字母或编号提为选项 id；回答比对忽略大小写，单字符 label 不再参与子串匹配。截图原文实测：识别为 preScore 80，选项 id 正确解析成 A/B/C，`C`、`c`、`先A，记下来，完成后继续走…` 三种回答都落在正确选项上、band 为 high。

要求「有选项」而不只是「有推荐」是故意的：单独一句「我建议先抽出失效逻辑」是叙述，配上摆好的选项才是决策点——测试里专门钉了这条，否则每一段解释性文字都会变成候选。

顺带把整屏巡检的开销砍下来：它原本对页面上每个节点调 `getComputedStyle`，是全套里最慢的一项，在忙的机器上会先于其它检查超时。改成先按几何筛（溢出量在布局阶段就已知），只对真有溢出的少数节点问样式，每尺寸从十几秒降到 3 秒；另外给它加了一次整进程重试，真正的裁剪问题两次都会报，只有饿死才需要第二次。

## 待确认卡片里的 A、B、C、F

用户截图：一张「需要判断」卡片，标题是原文开头一段被拦腰截断的文字（末尾停在 `` `display ``），最下方四个选项 `A` `B` `C` `F`。原消息里只有 `A` 和 `B` 两个选项。

留痕（`model-traces`）里这次调用的原始输出是完整的：

```
decisionIntent: "self_resolved"
answerRelation: "mixed"
question:       <原文前 160 字，正好卡在语法上限，断在词中间>
optionLabels:   ["A","B","C","D","E","F","G","H"]
confidence:     0.9999999999999999
```

也就是说本机 2B 模型把**整张字母表**填满了 8 条选项上限，并给了满信心。`validateSemanticClassification` 当时的守卫是 `assistantText.includes(option)`，单个字母在 860 字里几乎必然出现：`A`、`B` 来自真选项，`C` 来自开头的「C 记下：」，而 `F` 来自 `activityFormat.util.ts:191`。标题同理——那 160 字逐字出自原文，子串检查分辨不出「引用一句话」和「把开头搬过来」。

四层都有问题，逐层量了一遍：

1. **模型自己说这里没有决策，它的抽取却填满了卡片。** `decisionIntent: self_resolved` 经 `classificationBand` 算出 band 为 `low`，路由环节已经否掉了这个判断；但 `#event()` 里 `model?.question ?? rule?.question` 让同一份判断产出的字段照样显示出来。改成：模型 band 为 `low` 时其抽取一并作废；band 不为 low 时也由规则领先——规则引的是原文整段、可以逐字核对，模型给的是它自己挑的一段。
2. **摘录校验只看「是不是子串」。** 加一条：跨空行的摘录不是一句话，是一坨原文，直接判否。这正是小模型找不到问题时的典型输出——把开头抄到长度上限为止。
3. **选项标签同理。** 改成拉丁字母数字边界：`F` 夹在 `activityFormat` 中间判否，`**A**` 两侧是星号判是。边界只对拉丁字母数字生效——中文不写空格，`处理技术债` 出现在 `先处理技术债` 里是正常摘录，对汉字套边界会把模型做对的那些也全毙掉。
4. **规则本来能接住，但没看到。** 这条消息的结构是「背景 → 问题 9 → A/B 选项 → 我建议 A → 还有一处待定…等这题定了我再问」。规则只把最后一段当问题、只往前看一段找选项，于是锁在收尾那句上，选项数为 0，才轮到模型的字母表。改成：末段没有选项时，往前最多 4 段找选项块，且中间那段推荐必须**点名**其中一个选项才算数——否则「我做了两处改动 + 我建议先补测试 + 要不要现在跑」这种进度汇报也会被配成决策。顺带把 `- **A**：…` 的强调标记剥掉，字母才能提为 id（中文全角冒号后面不写空格，原来的 `\s+` 也把它挡在外面）。

截图那段原文实测：问题为「**问题 9（契约怎么切换）**：…」、选项 id 为 `A`/`B` 且 label 是真正的方案文字、回答 `A` 命中选项、band 为 high；「我建议 A」和那句收尾备注仍留在原文栏里。

### 这个模型值不值得留

顺着这条追下去量了一轮，用仓库里那 64 条语料（`npm run evaluate:semantic`）：

| | 纯规则 | 规则 + 本机 Qwen 2B |
| --- | --- | --- |
| 真·高置信决策判为 high | 25 / 31 | **9 / 31** |
| answerRelation 准确率 | 84.4% | **7.8%** |

7.8% 不是偶然：这个模型 64 条里 53 条答 `mixed`、10 条答 `uncertain`、只有 1 条答 `answers`，而语料里 44 条的正确答案就是 `answers`。`decisionIntent` 同样偏——49 条落在 `self_resolved` 或 `information_request`。它几乎从不承认「用户回答了一个决策」，于是每次都与规则不一致，`semantic_disagreement` 把本该直接记录的 22 条真决策压成「待确认」。用户看到的「为什么都是待确认」就是这么来的。

Apple Foundation Models 在这台机器上报 `device_not_eligible`，本机侧没有更强的替代。

两件配套的事：

- **评估脚本原本跑不了本机模型。** `--provider` 只支持 Codex CLI 和 Claude Code CLI 两个 profile，于是「本机模型够不够用」这个问题语料根本没法回答。加上 `qwen` 和 `apple` 两支（API profile 仍然排除在外，那需要打开凭据库，不是这个脚本该干的事）。
- **语料本身也接不住这个故障。** 64 条样本大多是一两句短句，模型在上面抽取得还算像样；字母表和前缀搬运是 860 字的真实消息才出现的。短样本能测路由，测不出长消息上的退化。

模型要不要换、换成哪一个，是隐私取舍而不是技术取舍——除本机 Qwen 外的每一个后端都会把对话正文发出这台机器，这件事由知道自己接受什么的人来定，没有代劳。

## 采集分类的引擎自己选

上一节量出来的结论落地：模型页「当前识别引擎」下多了一个「采集分类」下拉框，两项——「只用规则，不调用模型」与「规则加模型，按下方后端顺序」，**默认第一项**。

之所以只给这一个用途开关，而不是六个用途各配一份后端：采集分类是唯一一个**无人发起**的模型调用，Claude Code 和 Codex 的每一轮对话都会走它；问答、方法论提炼、技能与工作流草案都是用户自己点出来的，看得见结果也随时能停。把这一个摘出去之后，下面那张按优先级排的后端表就恢复自由了——把远端后端拖到第一位只影响问答一类的用途，采集的正文不会因此出机器。

配套的三件事：

- 关掉时协调器压根不调用分类器，也**不记一条 failed**——什么都没问，就没有失败，`失败7d` 不该因此涨。
- 「当前识别引擎」不再去探测一个不会被调用的后端：显示「规则识别」，运行模式显示「只用规则」（`mode` 枚举新增 `rules_only`）。
- 预览样本同步改成规则一致的状态。原本预览里引擎写着「Qwen 本地模型」、运行模式「混合模式」，而新开关默认是只用规则——一个说不调模型、一个说正在用模型，正是预览该拦住的那种自相矛盾。

**装上之后实跑，又翻出两处只有实跑才看得见的问题。** 一是 `captureClassifier` 加进了快照类型却没加进快照本身——下拉框的值永远显示默认项，改了也不反映（已用 controller 测试钉住，回改即红）。二是刷新有竞态：探测本机模型要几秒，这期间再改一次设置，`semanticRefresh ??=` 会把这次请求整个丢掉，卡片于是一直显示用户已经切走的那个引擎。改成排队——正在探测时记下还有一次待办，探完再跑一遍。两处都是 CDP 连上安装好的 App、真的切一遍开关才暴露出来的。

## 问答把「必须作答」这句话截掉了

用户在日志里看到中间过程以文本发给模型，问是不是有问题。过程本身该发——ReAct 循环靠它告诉模型已经试过什么，不发就会原地打转。有问题的是**怎么拼**。

翻一条真实的 8 步会话（10 次调用，含 2 次重试），提示词长度是 143 → 4393 → 8933 → 11379 → 13902 → 14559 → 14579 → **17999**。最后这次卡在 18000 的上限上，而 `已执行的动作：` 起始于第 17740 字——也就是说被切掉的正好是那句「**这是最后一步，必须输出 action 为 answer 的结果**」。日志里那一步模型返回的是 `action: "search"`，用户拿到的是「这一轮没能从检索到的内容里得出答案」。

它不是没听话，是**没被告诉**。

代码里原本的注释写着「给证据留余量，长文档就挤不掉指令」，实现却只兑现了一半：`#evidenceBlock` 的 budget 只管**读过的全文要不要展开**，每条证据的标题和摘录一律无条件输出。8 步搜索累积 34 条命中，光摘录就顶到 17k，然后整串在尾部被 `slice(0, 18000)` 切掉。防的是「一篇长文档」，来的是「几十条摘录」。

改法是把顺序倒过来：先按对话、已执行动作、指令算出固定开销，**剩下的才给证据**；证据块自己也按预算收，读过的全文优先、然后是最新的命中，塞不下的整条不发，并且「可读的证据编号」只列真正发出去的那几条（原来会点名根本不在提示词里的编号）。测试用 7 轮搜索 × 每轮 6 条 600 字摘录把预算撑爆，断言最后一次调用里「这是最后一步」和「已执行的动作」都还在——把预算改回旧算法，这条立刻红。

顺带修了个眼睛能看见的：步骤里写着「已读全文《X · X》」，同一个标题重复两遍。笔记的顶层标题和文件名相同时，`title · heading` 拼出来就是这个样子，白占提示词字数。

## 那条问题在修好的版本上跑通了

把原题「查找跟 grill me 忽略 CONTEXT.md 相关的记录，给我一段提示词或操作，在新的工程目录进行同样的操作。」原样再发一遍（同一个后端 DeepSeek、同一个范围「全部」），这次**答出来了**：1275 字，带 `[15]` 等引用，给出了 `.git/info/exclude` 的写法、`skip-worktree` 的冻结与解禁流程和自查命令，并且明确说「没有检索到标题或内容明确为『grill me 忽略 CONTEXT.md』的记录」——该承认的地方承认了。

8 步里第 8 步返回 `action: "answer"`，**每一次调用的提示词里都带着收尾指令**（旧版本正是最后那一次把它切掉了）。提示词峰值 16488 字，没有再顶到 18000 的上限：证据块现在自己按预算收。

中间两次失败也留下了东西。第一次和第二次重跑都是 DeepSeek 连续两次返回无法解析的结构化输出、耗尽 `MAX_TURN_RETRIES` 而终止，而日志里那一条只写着「Model provider returned malformed structured JSON」，`output` 是 `null`——**唯一想知道的事情恰好没记**。Qwen 那一支早就带摘录，远端这一支没有。

补上的是按形状描述，不是原文：`diagnosticExcerpt` 在用户关掉「调用记录内容」之后仍然保留，所以它只能说形状、不能引用一个字。现在会写 `length=… opens=fence|object|array|other ends=… · 包在 markdown 围栏里 / 没收尾就断了 / 根本不是 JSON 开头`——三种情况要三种不同的修法，只说「malformed」等于什么都没说。测试里钉了「不得出现原文」这一条。

顺带修对了上一轮修错位置的重复标题。步骤里显示《标题 · 标题 > 小节》，我当时以为是「笔记顶层标题等于文件名」，改在了 `title === heading` 上；实跑一看根本不是——chunk 的 heading 本身是一条面包屑（`顶层标题 > 小节`），它的根就是笔记的 H1，也就是标题，于是 `title · heading` 拼出 `T · T > 小节`。改成拼接前先去掉面包屑里那段标题前缀。真实那条记录上，这一处白占约 100 字。

## 检索不出新东西就别再检索了

上一节留下的问题：模型宁可换词再搜也不肯多读几篇全文。翻了两次真实会话，两次都在同一个地方露馅——第 6 步「已搜索「grill」，得到 **0 条**」，然后第 7 步接着又搜了一次，第 8 步（必须作答那一步）失败时已经没有余量。

`#retrieve` 返回的 `hits` 本来就是**新增**条数，所以「0 条」是个现成的、准确的信号：这一次检索没给这轮带来任何新东西。循环里原本已经有一条同类规则——空检索词、重复检索词、不存在或已读过的证据编号，都会把下一步标成必须作答（IMP-087）。检索零收获是同一件事的另一种说法，只是一直没被算进去。

改法刻意比 IMP-087 温和一点：**只关掉检索，不关掉阅读**。命中 0 条之后（且此前已经有证据）提示词改成「检索已经给不出新结果，不要再 search：read 关键证据的全文，或直接 answer」，模型若还要 search 就按退化步骤处理。第一次检索就 0 条不触发——手上什么都没有时，换个词再搜才是对的，测试里钉了这一条。

**同一条问题在装好的版本上实跑，前后对比：**

| | 步骤 | 结果 |
| --- | --- | --- |
| 今天之前 | 搜 6 · 读 1 | 收尾指令被截断，无答案 |
| 修好提示词预算后 | 搜 6 · 读 1 | 第 8 步（强制）作答，1275 字 |
| 再加这条规则 | **搜 3 · 读 3** | **第 7 步主动作答，1191 字，还剩一步余量** |

留痕里能看到规则真的生效了：「已搜索「grill」，得到 0 条」之后那一条提示词的末段正是「检索已经给不出新结果，不要再 search」，接下来两步都是 read。同一份留痕还顺带验证了标题重复已经修好——现在是《… · 当初的设置选择（setup-matt-pocock-skills）》，不再是同一句话念两遍。

## 结构化输出失败的诊断，第一次出场就用上了

新加的形状诊断在这一轮里抓到了三条：

```
length=228 opens=object ends=other · stops before it closes
length=140 opens=object ends=other · stops before it closes
length=93  opens=object ends=object · opens and closes as JSON but will not parse
```

也就是说 DeepSeek 不是在胡说，是**写到一半被截断**。这正是 `REASONING_HEADROOM_TOKENS` 那段注释描述的情形：推理模型把输出预算花在思考上，可见的 JSON 还没写完就到顶了。

只差最后一锤：`finish_reason`。它是 API 的枚举值、不是用户内容，所以可以和形状一起记进 `diagnosticExcerpt`。补上之后，下一次再遇到这种失败，日志会直接写成 `stops before it closes · finish_reason=length`——形状说「断了」，`finish_reason` 说「是预算断的」，两句合起来就指向该调哪个数字。这一轮跑通了、没再触发 invalid_output，所以这条字段本身还没在实跑里露过面。

## 失败的调用也是花了钱的

想坐实「DeepSeek 是被输出预算截断的」，先去翻已有留痕：113 次成功的 DeepSeek `retrieval-answer` 调用里，`outputTokens` 最大 2198、思考部分最大 1999，都离 `1024 + 2048 = 3072` 的上限还远。

但这组数字证明不了什么——**成功的调用按定义就是没被截断的那些**，而失败的那些 `usage` 记的是 `{"source":"unavailable"}`。想知道的那一半恰好没记，和昨天「malformed 却不说哪里 malformed」是同一个洞。

翻代码发现网关其实早就准备好了：`#normalizeFailure` 会从错误对象上读 `usage`，记留痕时用的是 `failure.usage ?? { source: "unavailable" }`。缺的只是适配器那一头——抛错时从来没把已经算好的 usage 挂上去。

补齐三处：`ModelProviderError` 多一个 `usage` 字段；`parseStructuredJson` 接收并挂上；OpenAI 兼容适配器在「空输出」和「JSON 解析失败」两个抛错点都把 `normalizeChatUsage(...)` 传进去。之后每一次「响应回来了但用不了」的失败，留痕里都会带着真实的 token 数——正是解释截断所需要的那组数字。

**还没做完的一半**：这些 token 仍然不计入聊天气泡里那句「本轮 47.4k tokens」。问答循环捕获的是网关包装过的 `ProfiledModelGatewayError`，拿不到底层错误的 usage；而那个包装错误是整条后端链都失败之后才抛的，要报谁的用量本身就是个设计问题（求和？只报最后一个？）。没有顺手糊过去——用户看到的数字目前**少算了失败的那几次调用**，这一点如实记在这里。

**一处该说的失误**：这一轮我把 `npm run check` 接在管道里 grep，管道的退出码是 grep 的，于是 `&&` 没有拦住——两条测试失败的情况下照样构建安装了。重跑干净（181 文件 / 1818 通过 / 5 跳过 / exit 0），从结果看那两条大概率还是负载下的整屏巡检，但那次输出只留了尾部，**我无法指名道姓说是哪两条**。装机的源码与重跑绿的源码一致，所以安装本身没问题。

### 补上 usage 之后第一次失败，直接推翻了我的假设

装好之后跑同一条问题，第 4 次调用失败，留痕这次写全了：

```
usage: 输入 4692 · 输出 2201 · 其中思考 181 · 合计 6893
诊断: length=4365 opens=object ends=object · opens and closes as JSON but will not parse · finish_reason=stop
```

**`finish_reason=stop`，不是 `length`。** 模型是自己写完停下的，根本没被预算截断；思考只花了 181 token，可见部分约 2020 token、4365 字符。我原本正准备去调 `REASONING_HEADROOM_TOKENS`——那会是一个把力气花在错误地方的改动，而且改完还会误以为修好了。

真正的样子是：一段**又大又「看起来完整」的 JSON**（开头是 `{`、结尾是 `}`），却解析不了。4365 字符远超一个 step 对象该有的体积。最像的成因是长 `answer` 字符串里带了没转义的换行或引号——DeepSeek 把一段 markdown 直接塞进 JSON 字符串。

所以又补了最后一块：失败时把**原文本身**也带上，走 `output.visibleText`——这个字段受「调用记录内容」开关约束，关掉就不落盘，和只说形状的 `diagnosticExcerpt` 各司其职。这正是 IMP-094 里写下的那条后路（「若将来确实需要原文样本来定位，应该走受 contentMode 约束的 output 字段」），现在用上了。下一次同类失败，日志里就能直接看到那 4365 字符长什么样，再决定是容错解析、还是换 JSON 模式、还是别的。

顺带记一笔：同一轮第 1 次调用状态是 `timed_out`、耗时 120000ms（留痕上限），而 DeepSeek profile 的超时是 30 秒。这一条还没查，先记在这里。

## 那个 120 秒超时

留痕：`2026-09-15T10:48:05Z`，DeepSeek，`retrieval-answer`，`status: timed_out`，`providerMs: 120000`，而这个 profile 的超时是 30 秒。

先把能确定的钉死：

- **120000 不是真实耗时，是上限。** `clampTiming` 的 `MAX_TIMING_MS` 就是 120000，`startedAt` 紧挨着被包装的调用，所以真实耗时 **≥120 秒**。
- **超时机制本身没问题。** `withProviderDeadline` 是一个 `setTimeout(timeoutMs)` 和调用赛跑，定时器回调直接 `reject`，不依赖 fetch 是否理会 abort。对 `generate` 取的是 `max(profile.timeoutMs, 30s)` = 30 秒。
- 所以**定时器迟到了至少 90 秒**。一个纯 `setTimeout` 迟到只有一种原因：主进程事件循环在那段时间被占住了。
- 那 120 秒窗口里（10:46:05 → 10:48:05）**一条模型调用留痕都没有**，超时记完之后下一次调用 722ms 就成功了。也就是说卡住的是没有留痕的那一段。
- `node-llama-cpp` 是 `await import` 进**主进程**的；应用在 10:44 前后刚被我重启过，本机模型那时还没热起来（重启后第一条 Qwen 分类要到 10:51）。

**到此为止，剩下的我证明不了。** 具体是谁占住了事件循环——本机模型加载、1.33 GB 权重的 SHA-256 校验、还是当时机器本身的负载——现有留痕说不了。硬猜一个去改，就是今天上午"以为是输出预算截断"那个错误的重演。

所以这一轮只做一件事：**让下一次自己说清楚**。`withProviderDeadline` 现在记下定时器自己迟到了多久，迟到超过 1 秒就写进诊断：

```
Model provider attempt timed out after 30000ms; the deadline itself fired
90000ms late, so the main process was blocked and the elapsed time is not
the provider's
```

这一句把两种完全不同的故障分开了：**端点慢**（预算到点就触发，耗时约等于预算）和**进程被占住**（预算到点触发不了，耗时远大于预算）。前者该调超时或换后端，后者该查主进程里谁在阻塞——修法南辕北辙，而此前日志里两者长得一模一样。顺带把预算数值写进了诊断：原来那句 `Model provider attempt timed out` 连自己等了多久都没说。

**顺带记一条新的偶发**：`assistant-panel.test.tsx` 的「sends a cited decision to its own page」在满负载下失败过一次（找不到引用按钮），单独跑和重跑都过。整屏巡检那条老偶发之外，这是今天第二条，都出现在机器忙的时候，暂未深究。

## 一批问题不是一组选项

开机先查昨天那几处埋点有没有触发：25 次调用全是 Qwen 分类、全部成功，问答一次没跑过，所以「失败原文」「finish_reason」「定时器迟到」三条都还没露面——没法据此动手。

转头看待确认队列，昨天的修复在生产里是对的：五条候选**没有一条**出现字母汤，选项都是真文字，`recommends_one_option` 也正确命中了一条「我倾向 B」。但翻出一个新的，而且是同一类误导换了个来源。

两条候选（12:37 和 12:49，都来自 clarai 的评审对话）里，助手一口气问了**七个彼此独立的设计问题**，每条自带一句「建议…」。规则把它们解析成了**一道题的七个互斥选项**，每个「选项标签」是一整段两百字的话。选项 3 的标签还在 `` `{ _id, name` `` 中间被冒号切断，label 和 description 各拿走半截。

这跟 A/B/C/F 是同一种错——把没人提出过的选择摆给用户——只是来源从模型换成了规则。

**先量再改。** 把已有的真选项和这两批问题清单放一起数了两个信号：

| | 自带提问 | 自带建议 |
| --- | --- | --- |
| 真选项：问题 9 的 A/B | 0 | 0 |
| 真选项：问题 21 的 A/B/C | 0 | 0 |
| 真选项：规则/模型 | 0 | 0 |
| 真选项：12:20 那条 | 0 | 0 |
| 问题清单 12:37 | 5 / 7 | 7 / 7 |
| 问题清单 12:49 | 3 / 7 | 2 / 7 |

分得干干净净。**选项不会推荐自己**——一条自带「建议…」的条目，是一个问题外加它的拟答，不是一个待选项。所以规则是：条目自己在提问（还是 / 是否 / 要不要 / 问号），或者自己在给建议，满两条就判定这个块是一批问题、不是一组选项。

要满两条是故意的：一条真选项的正文里偶然出现「还是」很正常，测试里专门钉了这种情况不被误伤。第一版我按「过半」定门槛，12:49 那条（3/7）漏掉了——是把真实数据摆出来才发现门槛定在了错的维度上，不是拍脑袋调数字。

**两条真实原文回放**：修复前 7 个选项，修复后都是 `options: []`，问题文本原样保留，读者看到的是"助手问了七件事"加自己的回答。

顺带说明这类候选**仍然会进队列**（`has_choice_prompt` 依旧命中），只是不再伪装成单选题。这是对的：助手确实在等人回话。

## 98% 的「失败」不是失败

审计留痕里 `stage: "failed"` 一共 340 条，其中 336 条是 `pair_not_found`。它在用户发言时找不到待配对的助手轮次就记一条——**而每个会话的第一句话都会触发它**。

先按会话把 5000 条留痕重排成时间线，分清楚这 336 条到底是哪一种：

| | 条数 |
| --- | ---: |
| 这个会话从来没存过待配对（正常） | **330** |
| 存过却没拿到（真丢） | **6** |

那 6 条的存取间隔是 24.8 小时到 2.8 天，全部越过 24 小时的待配对有效期——是用户隔天回到旧会话，助手那一轮已经作废。**真丢的决策一直存在，被 330 条噪声埋着。**

所以这不是改个措辞的事：`consume()` 把「从来没有」和「有过但没了」合并成了同一个 `null`，调用方只能一律记成失败。改成让它说明原因（`absent` / `expired` / `unreadable`），正常那条走新的 `user_prompt_unpaired` 阶段，另外两条才算失败。

### 差点把真丢的那 6 条也一起吞掉

改完跑测试，一条老用例红了：过期会话拿到的是 `absent` 而不是 `expired`。

原因是**定时清理会先把过期文件删掉**，`consume` 再去拿只剩 ENOENT——分不出「从来没有」。生产里清理每小时跑一次，24 小时过期的待配对几乎总是先被删掉。照我原本那版改，那 6 条真丢会从「混在噪声里」变成「彻底不记录」，比现状更糟。

修法是把记录点挪到损失真正发生的地方：**清理时逐条报告自己删掉了哪个待配对**，CLI 把它记成 `failed` / `pair_not_found`。这比原来更全——留痕里 `pending_saved` 651 条对 `user_prompt_matched` 437 条，那 214 条差额里从没回来过的会话，以前一条记录都没有。

回调只传 client / sessionId / turnId / capturedAt，不带 `assistantText`：审计库从不存正文，类型上就不给它机会。

### 顺带让失败数说实话

`pair_not_found` 原本在 `NON_TERMINAL_ERROR_CODES` 里（不计入 `failures7d`），因为它以前大部分是噪声。现在它只剩「捕获到的一轮过期作废」这一个含义，是终态，移出该集合。界面上的失败数会从 4 变成 10——多出来的正是此前看不见的那 6 条。

三条守卫都做了变异验证：改坏 `absent` 分支、拿掉清理的报告，对应用例分别变红。

### 更正：差点在上一层重演同一个错

上面那版改完，我本来要把「清理删掉的过期待配对」一律记成 `failed` / `pair_not_found`。先算了一下它会是多少：

| 客户端 | 存了待配对 | 配上 | 配对率 |
| --- | ---: | ---: | ---: |
| claude-code | 482 | 425 | **88.2%** |
| codex | 168 | 12 | **7.1%** |

合计 213 条没配上。`failures7d` 会从 4 跳到 213。

而这 213 条里绝大多数根本不是故障：**待配对是每个助手轮次都无条件存的**，`onStop` 里没有任何决策判定——所以每个会话的最后一轮必然存一条、必然等不到回答。把「对话结束了」记成失败，和把「会话第一句话」记成失败是同一个错误，只是换了一层。

改成新阶段 `pending_expired`，不计入失败。它照样值得记：正是它让上面这张表算得出来。

### Codex 这一侧的配对几乎没在工作

7.1% 对 88.2%，而且 codex 的 592 条 `hook_received` 里有 **256 条之后什么都没记**（占其钩子流量 43%），claude-code 只有 21 条。

成因目前证明不了——我没有 Codex 真实 payload。但落点是确定的：会话 id 已被 `hook_received` 证明有效，所以只可能是 `onStop` 缺 `cwd`，或 `onUserPrompt` 缺 `prompt`，两处各自成因唯一。这两个 return 此前什么都不记。

补了两个阶段 `stop_cwd_missing` / `prompt_text_missing`，都不算失败——**在知道 Codex 是不是本来就会在内部轮次触发 Stop 之前，不该先给它定性**。下次实跑日志会直接说是哪一侧。

## IMP-100 那个 120 秒超时：是钥匙串

重装后应用冻死，SIGTERM 无反应，AppleEvent 超时。采样给出的图景很干净——**2247 个采样点全在同一条栈上，CPU 时间冻在 13.84 秒，当前 0% CPU**：不是死循环，是同步阻塞。

```
node::fs::FileHandle::CloseReq::Resolve()   ← 读完密文文件的回调
  → （JIT 帧，应用自己的 JS）
    → SecItemCopyMatching → SecKeychainItemCopyContent
      → CSSM_DecryptDataFinal → mach_msg（等 securityd）
```

栈顶是一次**文件关闭的 promise 回调**，这正是 `credential-vault.get()` 的形状：读密文文件 → 回调里 `decryptString`。诊断由栈形自证。

昨天 IMP-100 写的是「具体是谁占住的（本机模型加载？1.33 GB 校验？机器负载？）现有留痕证明不了」。**三个猜测全错**：是 `safeStorage.decryptString()`。它只在主进程可用、且是同步 API；ad-hoc 签名每次构建都变，钥匙串条目的 ACL 认的是上一个二进制，于是 macOS 要授权——而要画那个弹窗的主线程，正是被这次读取堵住的那条。

### 没有修掉阻塞，修的是它的不可见

阻塞挪不出主线程：`safeStorage` 只在主进程可用，`utilityProcess` 拿不到它。真要修得把解密搬进另一个 Electron 进程、明文经 IPC 传回——为「每次更新一回」的事件不值当，而且扩大了密钥的处理面。

应用本身没有日志文件，这是有意为之（能落盘的东西都走内容无关、有上限的留痕），为这个新开一个日志文件是新增隐私面。

所以改的是**今天真正失败的那个工具**：安装脚本关闭超时后采一次样，命中 Security 框架的帧就直说是钥匙串授权在等、并声明什么都没替换。拿真实卡死的进程验过：命中 True，对正常进程 False。

一条「没有正常退出」让我查了二十分钟；下次它自己会说。

### 留痕窗口：条数上限抢在时间上限前面

文档写「7 天、最多 5,000 条」，实测 5001 条只覆盖 6 天——每天约 833 条，条数先到，时间上限从来没生效过。本轮新增的三个阶段还要再往里挤约 67 条/天。

条数上限本该是保险丝，不该是常态约束。抬到 10,000，7 天的说法才成立。

顺带量到一处已知天花板，这次不动：5001 条 JSON 只有 **1.4 MB，却占 20 MB 磁盘**——一条一个文件，283 字节的内容占满一个 4 KiB 块，放大 14 倍。改成追加式日志能省下 18 MB，但一条一文件正是让 bridge 进程和桌面进程各自无锁原子写入的原因，换掉要引入跨进程锁。20 MB 不值这个代价。

### 自查：我这轮的新代码差点让钩子不再 fail-open

`pruneExpired` 里报告损失的那个 await 直接放在 `Promise.all` 中——回调一抛异常，整个清理失败，进而让触发它的 `consume` / `save` 失败，钩子就不再是纯观察者了。CLI 那侧确实带了 `.catch`，但存储层不该信任调用方。已包住并钉了用例（变异验证过）。

### 暂停的安装会漏掉 333 MB

`stop_app()` 抛错时脚本没有任何清理——`try/except` 只覆盖换装之后的步骤。今天那次暂停就把一份 333 MB 的暂存副本留在了 `/Applications` 下一个随机名目录里，而消息只说「什么都没替换」，没说「留下了东西」。

两处修改都拿今天这个真实卡死现场端到端验过：新消息如实说出是钥匙串授权在等，新一轮的暂存副本被自己清掉，`/Applications/Decision.app` 全程未被触碰。

## transcript 长消息不能退回旧轮次

2026-09-20 继续检查采集链路时，在合成回归中复现两处错配：最新用户背景或助手消息超过 8,000 字就被整条忽略，读取函数会返回旧问题、旧背景；新的用户消息已经出现但尚无助手正文时，仍会返回上一轮的问题。两种情况都可能把下一次回答关联到错误的决策。

现在长助手消息保留末尾 8,000 字，长用户消息保留开头 8,000 字，任务背景进入暂存时仍裁到 4,000 字并标记截断；新的用户正文清空旧的问答配对。两个 transcript 读取入口共用同一轮次提取逻辑，保留 64 KiB 读取上限。回归覆盖 Claude 与 Codex 两种消息结构，并沿 Stop → 暂存 → UserPromptSubmit 验证当前问题、回答与背景。

验证：修复前新增的三个读取回归均失败，修复后 `npm run quality` 通过（182 个测试文件、1,836 项通过、5 项跳过，类型检查与 64 条合成语义门通过）。这是代码路径上证实的错配，尚不能解释此前 Codex 整体配对率偏低。

### 实际运行的还是旧 bridge

继续核查发现，`/Applications/Decision.app` 内的 bridge 仍把过期清理回调记为 `failed / pair_not_found`，而且没有 `stop_cwd_missing`、`prompt_text_missing`、`pending_expired`。因此，近期审计没有新阶段并不能证明客户端字段正常；旧构建的过期清理记录也不能当作「用户确实回来但未配上」统计。此次只核对匿名阶段和制品代码，没有保存真实对话正文。

已重新构建，通过隔离打包冒烟，并用仓库安装脚本更新本机应用，健康检查通过。随后直接调用安装后的 bridge，在临时目录回放 Codex 与 Claude 的长消息和缺字段输入：两条问答均保留当前问题与截断背景，缺字段阶段如实记录，Hook stdout/stderr 均为空，未连接真实运行端点或写入真实 Vault。旧 App 保留在安装脚本输出的临时备份目录；整体配对率仍需用更新后的真实观察判断。

## 审计写入减少串行等待
