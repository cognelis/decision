# 本地语义识别

Decision 只观察 Claude Code 和 Codex 已经发生的原生交互。它不注册问答 MCP，不替换 `AskUserQuestion` / `request_user_input`，不向模型注入指令，也不把任何响应写回客户端。Hook 收到事件后只做有限文本读取、私有落盘和短连接通知；即使 App、磁盘或分类器失败，Hook 也会静默放行原生流程。

## 它识别什么

普通文本捕获分为四层：

1. 采集当前 assistant 文本和下一条同会话用户输入；
2. 判断 assistant 是否把选择、批准或方向判断交给人类；
3. 判断用户输入是回答、回答后继续追问、无关新任务还是无法确认；
4. 从原文中定位问题、选项和答案片段。

这是一项受约束的语义识别，而不是读取 LLM 的隐藏思维过程。模型只参与第 2、3 层并为第 4 层提供建议。所有正式字符串都必须通过枚举、长度和原文包含校验；保存的答案始终是完整用户原文。

原生问答工具成功事件已经包含结构化问题、选项和答案，因此直接进入原有捕获路径，不调用语义模型。

## 提供者与路由

桌面 App 每次判断前重新读取模型后端配置，按用户可调整的优先级依次尝试所有已启用后端。首次运行只启用 Apple 和 Qwen；远程 API、Codex CLI 与 Claude Code CLI 都默认关闭，不会因为“检测到”而自动发送内容。

可用后端：

1. **Apple Foundation Models**：Apple Intelligence 提供的系统级设备端语言模型。Decision 通过随 App 打包的 Swift helper 使用 guided generation；helper 不监听端口，不访问 Obsidian，也不使用 Private Cloud Compute。
2. **Qwen3.5-2B / 4B**：Apple 模型设备不支持、未开启、资源未就绪或运行异常时的本地 GGUF 备选。由 `node-llama-cpp` 在 Electron main process 内加载，不需要 Ollama 或 LM Studio。
3. **OpenAI Responses**：使用严格 JSON Schema、空工具列表和 `store: false`。
4. **Anthropic Messages**：使用 Messages 结构化输出，不配置工具。
5. **OpenAI 兼容 API**：明确选择 Responses 或 Chat Completions。地址必须是 HTTPS；只有 `localhost`、`127.0.0.1` 或 `::1` 可以使用 HTTP。跨地址重定向不会被跟随。“JSON 输出”另有两档：默认“严格 Schema”发送 `response_format.json_schema`；“JSON 对象”发送 `response_format: {"type":"json_object"}`，并把 JSON Schema 连同“只输出 json 对象”的要求写进 system prompt。DeepSeek 只接受后者（其文档未提供 json_schema，且要求提示中出现 json 字样与目标结构），设置页的「DeepSeek」预设会一并填好地址、协议与这一档；其它同样不支持严格 Schema 的兼容服务可以手动选择。
6. **Codex CLI / Claude Code CLI**：使用客户端现有登录状态发起一次无工具、无会话、只读的结构化判断。它们通过本地进程启动，但模型请求通常仍会发送到对应服务商，因此界面明确标记为远程模型调用。
7. **规则识别**：所有已启用模型后端都不可用、超时或输出无效时立即接管。

模型页「采集分类」可以把这一整条链从采集路径上摘掉（设置项 `captureClassifier`，**默认「只用规则，不调用模型」**）。选规则时协调器不调用任何分类器，也不记失败——什么都没问，就没有失败；「当前识别引擎」显示「规则识别」、运行模式显示「只用规则」。其余用途（问答、方法论提炼、技能与工作流草案）不受影响，仍按下面的后端顺序调用，所以把远端后端排到第一位只影响这些用途，被采集的对话正文不会因此离开本机。

每个后端失败都会留下独立 attempt 日志，然后网关继续尝试下一项。启用、禁用、排序、模型名、超时和客户端路径都在下一次判断生效；不需要重装 Hooks。后端“测试”使用固定无业务样本，并记录为 `provider-health-check`，不会写入候选、理由、Obsidian 或 SQLite。

所有 HTTP 后端的输出上限都在可见输出之外多给 2048 token 的思考预算：DeepSeek 的 `max_tokens` 和 OpenAI Responses 的 `max_output_tokens` 都把思维链算进同一份额度，按可见 JSON 的长度设上限会让推理模型把额度耗在思考上、返回空 `content` 加 `finish_reason: "length"`；抬高上限对不思考的模型没有代价，它们照样在自己的停止符处结束。

同一后端顺序也用于显式发起的通用结构化生成。目前已启用的方法论、技能草案、工作流草案和检索问答分别使用 `methodology-extraction`、`skill-drafting`、`workflow-drafting` 和 `retrieval-answer` 用途；每种用途都有独立的严格 JSON Schema、输出长度限制和逐后端调用留痕。原则、技能与工作流都支持人工编写：这些路径不进入模型网关，只记录“人工录入 / 不调用模型”或“人工整理 / 不调用模型”，并复用相同的 Schema 校验和候选审核边界。人工原则不会自动关联复盘证据；用户也可以先明确选择 1–5 条完整复盘，再用零模型人工整理表单建立带真实来源的候选，证据关系只来自这次人工选择。已采纳原则基于采用后新复盘建立修订草案时同样不调用模型，且只有明确应用后才更新稳定原则。人工实践资产仍保留来源原则快照和显式发布边界。Apple Foundation Models 仍只参与普通文本语义识别，通用生成会跳过它并继续尝试 Qwen、API 或终端后端。生成或人工编写的结果必须经过 Schema 校验和人工确认后才能成为已采纳原则或实践资产；只有用户随后在资产详情中明确确认发布，才会写入 Codex 或 Claude Code 的 Skill 目录，创建草案本身不会直接改变 Hooks 或客户端内容。

普通文本会同时得到规则档位和可用模型档位：

| 规则 | 模型 | 最终处理 |
| --- | --- | --- |
| 高 | 高 | 高：进入理由流程 |
| 高 | 中或低 | 中：进入待处理 |
| 中 | 高或中 | 中：进入待处理 |
| 低 | 高或中 | 中：进入待处理 |
| 低 | 低 | 低：丢弃 |
| 任意 | 不可用 | 使用规则结果 |

模型不能单独触发高置信弹出理由面板。包含有效回答又继续提出新问题的 `mixed` 输入至少进入中置信待处理，且完整输入会作为答案保存。超过 15 分钟才恢复处理的配对最高也只能进入待处理，避免重启后突然弹出过时决策。

Qwen 首次使用允许最多 30 秒完成冷启动，后续单次分类仍受 5 秒限制；结构化生成（问答作答、原则提炼等用户在等的调用）另有 30 秒下限，profile 设得更高时仍按它自己的值。分类在后台异步执行，不阻塞 Claude Code 或 Codex 的原生交互。瞬时运行失败会先尝试下一个已启用后端，再回退到规则识别；30 秒后在下一次状态检查或配对分类时自动重新探测本地模型，初始化失败的运行资源不会被永久缓存。

待处理面板打开一次即可连续处理当前队列。忽略后直接显示下一项；记录后先进入理由流程，完成、跳过或稍后补充理由后自动返回下一项。面板优先展示完整决策原文、用户回答和问题相关上下文，未确认内容仍只保存在私有 `candidate-spool`。

## 本地模型选择与安装

- 4B Q4_K_M：3,013,027,808 字节，约 3.01 GB。固定提交 `4168f45a16a1290d65a4ec0fa312ae917a4c15d6`，SHA-256 `13c16f426047e2de38cd075bdade4a7bcbc8c774384876f677740cda65f8a983`。

## Obsidian 全库检索的独立嵌入消费方

“Obsidian”工作区是专用嵌入模型的独立消费方。它直接调用 `QwenEmbeddingProvider`，不经过 `ProfiledModelGateway`，因此 Vault 笔记和搜索词不会发给远程 API、Codex CLI、Claude Code CLI，也不会写入 `model-traces`。这条链路不创建网络监听；模型权重仍必须通过上面的准备命令显式安装，缺失或校验失败时只保留明确标记的关键词结果，界面不会把降级描述成语义成功。

每个 Vault 的派生数据库固定为 Decision `userData/obsidian-search/vaults/<identity>/index.sqlite`，其中 `identity` 是规范绝对 Vault 路径精确表示的 SHA-256。Windows 的规范表示先把路径分隔符统一为 `/`；其它平台直接使用规范路径。数据库 `meta` 还绑定同一个身份：带其它身份的库以及已有行但尚未绑定身份的旧库都不会被当前 Vault 读取。数据库与决策库 SQLite、`semantic-vectors.sqlite` 分离，主文件及 WAL/SHM 权限为 `0600`；只保存 Vault 相对路径、标题、章节、用于关键词摘要的片段正文和本地向量，原始 Markdown 仍是事实源，绝对路径和身份都不进入 Renderer。

索引只覆盖当前 Vault 中符合边界的 Markdown，不含本应用自己的 `Decision Journal`（见下文）；配置、回收站、版本控制和依赖目录按 ASCII 大小写不敏感排除，同时跳过符号链接、非普通文件、附件和超过 5 MiB 的笔记。扫描器按笔记惰性产出，在每次文件系统等待前后检查取消，并按文件已知剩余大小分配最多 64 KiB 的读取块，不预分配整篇上限或保留整个 Vault 正文。增量同步按内容哈希跳过未变化笔记，并以 16 个片段为一批嵌入。

查询按 SQLite iterator 流式读取片段，关键词路和语义路各自只保留前 200 个候选，并每处理 128 个片段协作式让出主线程；RRF 只在这两个有界集合内定义，截断之外不承诺精确名次。后台同步期间旧结果保持可用；只有完整扫描且没有诊断、跳过、模型、笔记或索引失败时才推进最近成功同步时间。索引中状态约每 800 ms 刷新，稳定状态仍约每 5 秒低频刷新。嵌入模型稍后安装时，下一次搜索会探测到资源并自动排队强制重建，不要求删除数据库。

退出时立即开始取消 Obsidian 工作、停止 watcher，并关闭嵌入资源和数据库；这条关闭链与其它语义清理并行。smoke shutdown marker 只在 Obsidian 关闭成功后写入，进程先退出但 marker 缺失或无效会让冒烟失败。手动“重建全库索引”只影响当前身份对应的可重建数据库，不等同于重建决策库，也不会删除、移动或格式化 Markdown。

笔记检索与决策检索合并在「知识」一页：同一个搜索框驱动两侧，决策走 `DecisionContextService`，笔记走全库索引，两张列表各自滚动。全库索引在目录级排除项（`.obsidian` / `.git` / `node_modules` 等）之外，还整体跳过本应用自己写入的 `Decision Journal/`：决策、原则、实践资产和偏好想法都有各自的结构化检索，重复索引只会让同一份材料经两条无关路径各出现一次。跳过在遍历阶段生效：全库遍历不打开 Vault 根下的这个目录，文件监听也不理会其中的改动，App 每写一次决策或结果不再触发一次全库重扫；目录更深处同名的读者文件夹照常索引。旧版本建立的索引会在下一次同步时被 `prune` 自动清掉，不需要手动重建。代价是决策不再进笔记索引，`openObsidianNote` 的"必须在索引内"校验因此打不开它们——引用改走 `openVaultDocument`，只依赖 `resolveNotePath` 的 Vault 边界校验。结果只向 Renderer 返回标题、Vault 相对路径、章节、裁剪摘要和 `keyword` / `semantic` / `hybrid` 类型。打开笔记时 Main 进程再次验证该相对路径仍在当前索引和 Vault 边界内，然后构造官方 Obsidian URI；状态和错误省略绝对路径、原始异常堆栈和笔记正文。当前边界不包括多 Vault、附件解析和生成式摘要；基于检索结果的多轮问答是下一节描述的独立显式功能，不改变本节的索引与召回链路。

## 问答助手

侧边栏「问答」是一个独立的多轮对话入口，与「知识」检索页分开；检索页本身不再内嵌回答。回答按一个受限的 Markdown 子集渲染（标题、列表、引用、代码块、粗体/斜体/行内代码），渲染成 React 元素而不是 HTML——渲染器里没有 `dangerouslySetInnerHTML`，也不引入解析器依赖。链接只保留文字、丢弃目标地址：模型不应该递给用户一个由它选择落点的链接。表格、图片和内联 HTML 不支持，按模型写下的原文显示。只有用户主动发送一条消息才会调用生成模型，检索排序和索引链路不受影响。

**agent 循环。** 一轮对话里，模型每一步只能输出一个动作：`{"action":"search","query":"…"}`、`{"action":"read","index":n}` 或 `{"action":"answer","answer":"…","citedIndexes":[…]}`。输出 search 时主进程执行检索、把结果编号后追加进证据列表；输出 read 时按该编号取出证据对应的 Vault 相对路径，读取整篇 Markdown 后替换掉原来的裁剪摘录——路径始终来自检索结果，模型只能给编号，不能自行指定文件。输出 answer 即结束该轮。一轮最多 `ASSISTANT_MAX_STEPS`（8）步，最后一步会被显式告知必须作答；重复或空的检索词、越界或已读过的编号都不执行，直接转入作答并在响应里标记 `truncated`。读取失败（笔记已删除或超出 Vault 边界）同样不中断该轮，只是这条证据继续以摘录参与作答。步数用尽仍未作答时返回一条说明而不是空结果。每一步都作为独立的模型调用留痕。一轮另有 `MAX_TURN_RETRIES`（2）次整轮重试预算，某一步生成失败时花掉一次；预算用尽即结束该轮，界面把这条提问退回输入框并从对话中移除——留在对话里它永远等不到回答，还会作为历史随下一轮发出。

**过程可见。** 一轮最多 8 次模型调用，因此每完成一步主进程就通过 `decision:assistant-progress` 推一条 `{turnId, step}`，界面实时列出"检索「X」· N 条"「读全文《Y》」。`turnId` 由发起方生成并随请求带上，事件按它过滤：来自已放弃轮次的进度描述的是没人在等的工作，直接丢弃；请求不带 `turnId` 就完全不推送。服务内所有步骤都经同一个 `record()` 出口，记录与播报不可能分叉。推送失败被吞掉——进度是附带品，不能让它把这一轮弄失败。

**边界回归。** 上述上限由一条"所有字段同时压到极值"的用例守住：7 次检索各返回 10 条极值笔记（深层路径、500 码点标题与 heading、3000 字摘要）、20k 字全文、8000 字提问，断言整个响应能通过 `assistantTurnResponseSchema.parse`。断言的是"渲染进程真的收得到"，而不是"算出来的字段看起来对"——这类越界只在 IPC 边界显形，且只在极长材料上出现，靠手点几乎撞不到。模型给出不合规步骤（例如超长检索词）不属于此类：gateway 把 `parseOutput` 失败包成 `invalid_output`，最终以 `ProfiledModelGatewayError` 走重试与 `unavailable`，不会把异常抛穿。

**标题长度。** 笔记标题与 heading 面包屑各被索引器裁到 500 码点，拼成的「标题 · heading」可达一千字符，远超步骤 Schema 的上限。证据标题因此在构造时就裁到 `ASSISTANT_MAX_TITLE_CHARS`（300，与 Schema 用同一个常量），引用标题和链接跟随的 matchReason 也随之落在各自上限内。裁剪函数含省略号在内不超过 `limit`——原先切满 `limit` 再补省略号会多出一个字符，恰好顶破等值的 Schema 上限。

**证据上限。** 检索、后继查询、链接跟随和追问携带都往同一份证据列表里追加，因此列表有统一上限 `ASSISTANT_MAX_EVIDENCE`（40），引用编号的 Schema 上限用的是同一个常量；一条答案最多带 `ASSISTANT_MAX_CITATIONS`（12）个引用，模型给出更多编号时按顺序截断。两个数字定义在 protocol 里、被 Schema 和 agent 同时引用：编号一旦超出 Schema 允许的范围，会在 IPC 边界校验失败、把一轮已经付过 token 的工作整个作废，而这类越界只有在追问携带满 12 条之后才会出现，正是最不容易在开发中撞到的路径。所有追加都经同一个 `appendEvidence()` 出口，新增证据来源不会绕过上限。

**瞬时失败。** 一轮最多 8 次调用，撞上一次瞬时失败的概率是单次调用的 8 倍，而失败会把这一轮已经付过 token 的检索全部作废。因此每一步的生成失败最多重试一次，重试额度按**整轮**计（上限 2 次）而不是按步：后端只是抖了一下时，前两步各能被一次重试救回；后端确实宕了时，第一步用掉一次重试就返回 `unavailable`，不会被追问八次。中止不算失败，已中止的轮次不重试。非 `ProfiledModelGatewayError` 的异常一律上抛，不被重试吞掉。

**追问不重来。** 一轮开始时，先把本次对话历史里所有 `citations` 按 Vault 相对路径去重、重新编号后作为初始证据（最多 12 条）——这份材料本来就随请求送达，重搜同一片地只会花掉用户的 token 而得不到新东西。检索时的去重集合包含这些条目，因此新检索命中同一份材料不会重复入列。首轮没有引用，行为与从前一致。

**开销可见。** 一轮最多 8 次模型调用、单篇全文进 prompt 可达 4k 字，按 token 计费的远程后端上这笔钱必须看得见。服务累加每一步 `usage` 的 `inputTokens` / `outputTokens`，随回答挂在消息上，界面显示"本轮 12.3k tokens（输入 11.8k · 输出 500）"。未报告用量的步骤单独计数：只要有一步没报告，文案改为"本轮至少 …；N 步未报告用量"——下限不是账单，不能印成确切数字。所有步骤都没报告时该字段整体省略，而不是显示 0：那会是一个我们没有依据的断言。

**链接跟随。** 读完一篇笔记的全文后，主进程解析正文里的 `[[链接]]`（`[[名称]]`、`[[名称|别名]]`、`[[名称#小节]]` 都归一到"名称"，去重后最多跟 3 个），逐个按名称检索并**只接受笔记名完全一致的命中**——近似命中会安静地从错误的笔记作答，比不跟链接更糟。命中的笔记以「《X》链接到」作为 matchReason 追加进证据，该次 read 步骤的 `hits` 记录带出的条数。只对笔记生效：决策正文里的方括号不是 Vault 链接。Vault 里的链接是用户自己写下的"这两篇有关"，比检索能算出的任何关键词重合都更可信。

**中断。** 发送按钮在运行中变成「停止」，点它按 `turnId` 调 `cancelAssistantTurn`；主进程按同一个 id 找到该轮的 `AbortController` 并 abort，未知或已结束的 id 是空操作——答案落地那一刻点停止不应该报错。Agent 循环在每步开始、模型调用抛错时、以及检索和读全文返回后各检查一次信号，返回独立的 `cancelled` 状态而不是错误：停止是用户的选择，不是故障。步骤先记录再检查信号，因此已经执行过的检索会如实出现在 `cancelled` 的 `steps` 里。界面收到 `cancelled` 后把这条提问退回输入框供修改，而不是在对话里留下一条没有回答的提问。

**生命周期。** 决策与原则会带上是否仍然成立：仓库给出 `lifecycleState` 时直接用，否则由 `current` 为假或存在 `supersededBy` 判为「已被后续决策取代」，仅有未能解析的 `unresolvedSuccessorIds` 时判为「可能已有后续决策，未能确认」。这个标注同时出现在模型看到的证据行和界面上的引用条目里，system prompt 明确要求带标注的证据不能当作现行结论直接作答。笔记没有生命周期，该字段省略。检索到非现行的决策时，主进程还会按 `successors` 里的 `recordId` 把取代它的记录一并拉进证据，`matchReason` 写成「取代了《X》」——只知道一条决策过时、却说不出现在的结论是什么，对提问的人没有用。后继查询显式使用 `includeOutOfScope: true`（替代品的相关性来自它替代的那条，与范围筛选无关），每次检索最多花 3 次后继查询，且只跟一层：后继自己若也被取代，会带着自己的标注出现，由模型决定要不要继续检索。把一条已被取代的决策当成现行结论回答，是这个工具最不该犯的错误，因此它既不依赖模型自觉，也不只停留在界面提示。

**证据与提示预算。** 决策库一侧走 `DecisionContextService`，固定 `includeOutOfScope: false`；Obsidian 一侧走全库检索的裁剪片段。每次检索每侧最多 5 条，按相对路径去重，编号在整轮内连续且不复用。请求形状只有 `systemPrompt` 与 `userPrompt` 两个字符串（各 20k 上限），因此对话历史被序列化进 `userPrompt`：最近 12 条消息、每条裁到 800 字，未读证据裁到 480 字，读取的全文裁到 4k 字。证据段有独立预算（18k 减去对话长度再留 1k 余量）：按最近读取优先展开全文，放不下的读过的证据退回摘录，因此再多的全文也挤不掉指令。检索范围由用户在界面选择（全部 / 决策库 / Obsidian），模型不能自行越出该范围。

**模型与送出本机的判定。** 可选模型是所有已启用且支持结构化生成的后端；`apple` 只提供分类、没有 `generate`，既不参与问答也不出现在列表中。未显式指定时使用优先级最高的一个；显式指定后只使用该 profile，失败即如实报告而不回退。`apple` 与 `qwen` 在本机完成，其余（远程 API 与两个 CLI 后端）视为会把内容交给服务商。这个判定作为 `leavesDevice` 随 provider 返回，界面据此标注，但不再拦截：曾经的 `needs_remote_consent` 逐次确认已按用户要求移除，选中一个远端后端即视为授权。

**检索评测。** 其余测试量的都是**形状**——字段在上限内、边界不炸、步骤有序——没有一条能回答"问一个问题，到底能不能找到答对的那篇"。`retrieval-evaluation.test.ts` 补的就是这个：24 篇合成 Vault（含 16 篇干扰笔记）、10 条标注问题，量 recall@5 与 MRR。实测 recall@5 = 1.0、MRR = 0.9，阈值各下调一档设为 0.9 / 0.8——是**要守住的下限，不是要达到的目标**。语料必须大于结果窗口：8 篇取 5 条时随机就有约 62% 的 recall，那种数字什么也不测；24 篇取 5 条把随机拉到约 21%。范围也划清：这里的向量是合成的，量的是**关键词**通路（切片、索引、查询），语义排序需要真实 Qwen 权重，属于 `check:semantic` 那类按需开启的评测。"查不到的问题是否返回空"同理不在此评——所有 chunk 同向量会让语义路径匹配全库，那测的是桩不是产品。

**反馈。** 每条回答下可以标「有用 / 没用」，标「没用」时另给一个**选填**的说明框——决策来源反馈要求必填理由，那对一次深思熟虑的来源判断是对的，对聊天里的一次评价是错的：一键给不出的评价没人会给。记录写入 `<userData>/assistant-feedback.json`（目录 0o700、文件 0o600、临时文件+rename 原子写，最多 500 条，写入串行化以免两次快速评价互相覆盖），字段只有 `turnId`、评分、问题原文、选填说明和**引用的 Vault 相对路径**——不存回答正文，也不存摘录：那些内容在 Vault 里，这里再存一份就是多一个泄漏点。同一 `turnId` 再次评价替换原判断而不是叠加。评分失败不影响回答本身。

**导出。** 决策与笔记本来就是用户 Vault 里的 Markdown，已经可携带，重建 SQLite 索引也只依赖它们；**唯一不可携带的是对话本身**——它只存在于渲染进程的 `localStorage`。所以「导出」把当前这段对话写成 Markdown，经系统保存对话框由用户选位置，默认不落在 Vault 里：对话不是记录，放进决策旁边会让它看起来像记录。导出内容保留每条引用的标题与 Vault 相对路径，导出的文件因此仍指回来源，而不是一份断了根的聊天记录。文件以 0o600 写入。

**整理成记录。** 回答下方的「整理成记录」把这条回答**作为草稿**交给既有的「主动记录」表单，由用户过目、编辑并显式保存——助手本身仍然不写入任何东西。关键在来源声明：记录的 `sourceForm` 只有 `user_original`（用户原话）和 `user_paraphrase` 两个值，**没有"模型写的"这一档**，所以带草稿保存时强制记为 `user_paraphrase`，即使用户一字未改直接保存也是如此：永久记录里的来源声明必须为真。引用的标题与路径作为「依据」填入 rationale，那是事实而非模型措辞。

**计费单价。** 模型后端可以填货币与输入/输出的每百万 token 单价，填了才把用量折算成金额显示在回答下方。**不内置价目表**：厂商改价后写死的表会安静地给出错的数字，而错得安静比没有更糟。三个字段必须填全才生效，缺一不折算——两项凑出来的数字读起来像精确值，其实不是。

**留痕与边界。** 一轮内所有调用共用同一个 `requestId`（即 `turnId`），因此审计日志里一轮就是一组，而不是只能靠时间戳拼起来的八条孤立记录；「日志」页在出现多种用途时提供按用途筛选，否则助手一开跑就会把其它调用淹掉。每一步按 `retrieval-answer` 用途写入既有 `model-traces`，保留期、条数上限、目录与文件权限和正文开关都与其它模型调用一致。对话不写入 Obsidian Markdown 或 SQLite，也不产生候选、理由或原则采用关系。为了切换侧栏页面和重启后还能接着上一轮问，对话保存在渲染进程的 `localStorage`（键 `decision.assistant.sessions.v2`）：最多 10 段对话、每段只留最近 40 条消息（与单轮请求上限一致），落在 Electron 的 userData 目录，未额外加密。工具栏的下拉可切换，标题取自开启该段对话的那个问题。「新对话」只是把当前这段收起来另开一段，不再销毁它——这曾是唯一的重新开始方式，代价是上一段永久消失；要真正抹掉得点「删除此对话」，那才是不可恢复的操作。升级时会把旧的单对话键 `decision.assistant.session.v1` 读进来作为第一段并随即删除该键，不让读者的上一段对话在升级中静默丢失。**远程模型的确认标记不写入其中**——确认针对的是当下这位用户的这一次对话，从存储里复活它等于拿另一天的一次点击把材料发给服务商，所以恢复出来的对话会再问一次。读取时按 Schema 解析而不是强转，旧版本或被手改的内容退回空会话。引用由程序核对：模型只能给出证据编号，标题与路径由主进程回填，越界编号丢弃、重复编号折叠。引用条目可点击打开原文，走 `openVaultDocument`：它按 Vault 相对路径打开任意一篇 Markdown，不要求该路径在笔记索引内，因此决策和笔记都能打开。路径始终来自检索结果而非模型，仍经 `resolveNotePath` 的绝对路径、越界、符号链接和常规文件校验。

当前边界：不支持流式输出、不在两个来源之间做跨库去重（只按路径去重），助手自身不写入任何记录，也不参与事前原则核对；「整理成记录」写入的是用户在表单里确认过的内容，不是助手的输出。

## 布局测量的超时

四个 Electron 布局测试各给子进程 30 秒预算，而套件级 `testTimeout` 是 20 秒——vitest 永远先赢这场赛跑，测试**不可能**观察到子进程真正超时。单独跑 59 条 31 秒全过，混在全量里要 360 秒并随机挂掉不同的几条，报出来的只有一句 "Test timed out in 20000ms"：一条关于测试框架的消息，从来不是关于布局的。因此这四个文件把 `testTimeout` 提到 90 秒——等待者的耐心必须长过它等待的预算，否则失败信息永远指错地方。会随机变红的套件会教人忽略失败，那比没有守卫更糟。

## 进程接缝

`DecisionApi`（渲染端可调用的）与 `DecisionIpcOperations`（主进程必须应答的）是两份手写的、描述同一批约 95 个操作的接口。TypeScript 只在两者被接线的地方才发现不一致——那已经太晚，而对一个还没接线的操作则永远发现不了。因此另有一条断言逐名比对两个接口，并要求每处分歧都出现在**具名的例外表**里（渲染端独有的是推送订阅与理由队列操作，主进程独有的是走队列自身通道的延迟理由操作）；例外表里已经不成立的条目同样会让测试变红——一份活得比它所豁免的东西更久的例外表，会开始悄悄豁免别的东西。实测过：从主进程接口删掉一个操作，断言会点名那个操作。



Renderer 能力清单、preload 桥接和主进程 handler 是三份必须一致、却各自独立编辑的东西，任何一处漏掉都能通过类型检查和全部单元测试，然后在运行时静默失效——"点问答没反应"就是这个形状。三条断言分别守住三段：`RENDERER_METHOD_NAMES` 与手写清单一致；preload 暴露的键**恰好**等于该清单且对象被冻结、每个方法只触达 `IPC_CHANNELS` 里命名的通道；除两个只由主进程推送的通道（`snapshotChanged`、`assistantProgress`）外，每个通道都注册了 handler。三条都以"删掉一个桥接方法 / 把 handler 注册到错误通道"实测过会变红——不会在对应缺陷上失败的守卫没有价值。

## 复盘提醒

决策可以安排复盘日期，但到期这件事原本只能通过托盘 tooltip 里的一个**合并数字**（候选 + 待补理由 + 到期复盘）传达，且需要悬停才看得见——它说不出"有决策到期了"。现在到期会发一条系统通知，托盘 tooltip 也把「N 条待复盘」与其它待办分开写。

两条规则防止它变成噪音：同一条决策的同一个到期日**只提醒一次**（记录在 `<userData>/review-reminders.json`，0o600、原子写、最多 500 条），以及设置里关掉后连查询都不做。启动时也检查一次，否则关着应用期间到期的决策要等下一次快照刷新才被发现。写入失败不吞掉通知本身——宁可下次重复提醒一次，也不要因为记账失败而彻底沉默；存储损坏同理按空处理而不是永久静音。`reviewRemindersEnabled` 是对设置 v3 的**追加**字段（带默认值），不升版本：版本号留给读不动旧文件的改动。

## 设置页诊断

设置页“语义识别”是只读的当前路由状态，显示：

- 当前实际提供者：第一个可用的已启用模型后端，或规则识别；
- 可用性：可用、Apple 智能当前不可用、Apple Intelligence 未开启、资源未就绪、模型未准备、校验失败或运行时不可用；
- 当前模式：混合识别；
- 最近 7 天处理数、高置信数、中置信数和终止采集、落盘或路由的失败数。未配对 Hook、模型超时、规则回退，以及已落盘、只是没能当场交给 App 的配对（App 下次读取 spool 时处理）不算失败。

它不会显示阈值、运行令牌、问题、答案或项目路径。后端配置在下一次判断生效；分类中提供者失败时按顺序继续尝试下一项，全部失败后降级到规则。

设置页“模型调用记录”单独显示 Decision 自己发起的模型判断。每个后端尝试一条记录，包括实际提交的 system/user prompt、提供者返回的可见文本、通过校验的结构化结果、模型与 prompt/schema 版本、耗时、状态以及 Token 来源。Qwen 使用模型运行时的 token meter，标记为 `runtime_measured`；Apple Foundation Models 没有可靠 Token API 时明确显示“Token 不可用”，不会用字符数伪装。

模型输入输出正文默认开启记录，只影响新的调用，可在设置页关闭。关闭后仍保存无正文的 attempt 元数据和原有 `capture-audit` 聚合信息。用户可以删除单条记录、同一次请求的全部后端尝试，或二次确认后清空全部记录。

设置页“模型后端”支持：

- 添加 OpenAI、Anthropic 或 OpenAI 兼容 API；
- 保存模型名、服务地址、协议和超时，并用系统加密保存 API 密钥；
- 自动检测 Codex / Claude Code 的可执行文件、版本、登录状态和所需安全参数，也允许填写绝对客户端路径及模型名；
- 测试、启用、停用和排序所有后端，删除用户添加的远程 API 后端；
- 查看测试耗时、模型版本、Token 来源和稳定错误码。

API 密钥不会返回给渲染进程，也不会进入模型调用记录、Markdown、SQLite、错误正文或命令行参数。编辑已有 API 后端时留空密钥表示继续使用现有密钥；删除该后端会同时删除对应的加密凭据。停用 CLI profile 不会卸载客户端，也不会退出其账号。

## Codex 与 Claude Code 客户端调用

客户端诊断会检查可执行文件、语义版本号、登录状态和当前版本是否具备全部安全参数。显示“当前版本缺少安全调用能力”时应先更新对应客户端；Decision 不根据猜测的最低版本号放行。

Codex 使用固定的 `exec --ephemeral --json --ignore-user-config` 调用，输出受 JSON Schema 约束，沙箱为只读，批准策略为 `never`。它在一次性空目录中运行，关闭 shell、Web 搜索、Apps、子 Agent 和记忆生成；问题正文只经 stdin 提交，不出现在进程参数中。

Claude Code 使用固定的 print mode、`--safe-mode`、空 `--tools`、`--disallowedTools "mcp__*"`、`--no-session-persistence` 和 `--permission-mode dontAsk`。Decision 不使用 `--bare`，因为需要显式而可验证地关闭工具、MCP、会话持久化与交互授权，同时保留客户端自身认证和网络连接。

两个客户端都：

- 只继承认证、代理、证书、语言和临时目录所需的最小环境；
- 在私有一次性空目录中运行，完成后删除目录；
- 使用无 shell 的绝对可执行路径，并限制 stdout、stderr、超时和响应体积；
- 超时或取消时终止完整进程组；
- 设置 `DECISION_PROVIDER_CHILD=1`。所有 Decision 被动 Hook 在读取 stdin、transcript 或落盘前看到该标记就立即退出，因此不会递归采集模型判断；
- 只保存最终可见结构化结果与服务商报告的 Token，不保存 Codex reasoning 事件、Claude session id 或客户端内部会话。

客户端登录、订阅、额度、模型可用性和服务端数据保留仍由 OpenAI / Anthropic 账号与服务条款决定。“本地客户端”只描述调用入口在本机，不代表推理在本机。

## 本地数据与保留

- `semantic-pair-spool`：保存当前 assistant 文本和下一条用户输入；未配对内容 24 小时过期，已配对未完成内容最多 7 天，路由成功后删除正文。
- `candidate-spool`：中置信候选最多 100 项、默认 7 天；确认前不写 Markdown 或 SQLite。
- `capture-audit`：默认 7 天、最多 10,000 条（条数是保险丝，实测每天约 900 条，真正生效的是 7 天）；只保存阶段、置信档位、耗时、稳定错误码和 HMAC 指纹，不保存正文、cwd、原始会话/轮次 ID、transcript 路径或异常堆栈。
- `model-traces`：默认 7 天、最多 1,000 条；目录 `0700`、单文件 `0600`，每条记录原子写入，损坏文件自动隔离。它可能包含裁剪后的模型输入和可见输出，仅保存在本机 Application Support，不写入 Obsidian、SQLite、iCloud 或 Decision 自建遥测。
  - 调用详情优先展示后端诊断、错误类别、退出码、服务商请求编号，以及同一请求的相关记录；可查看耗时、Token 明细、Prompt/Schema 版本和已保存的输出 Schema。新的生成调用还保留应用侧超时配置、请求输出上限、提示词长度与脱敏客户端路径。
  - 关闭输入输出正文记录后，上述元数据仍保留；应用校验诊断只保留安全字段路径与错误类型，不保留被拒绝的值或自定义校验消息。“复制排障信息”排除输入和输出正文。旧记录未保存的参数不会推测或回填。
- Obsidian Markdown：只有经过理由流程处置的正式决策，仍是唯一事实来源。
- `index.sqlite`：知识库记录的全文检索和派生状态，可以删除后从 Markdown 重建。
- `local-decisions.sqlite`：用户明确选择“仅本机保留”的完整决策，是独立的本机事实来源，不进入 Obsidian，不参与知识库、原则或助手的默认检索。它不能当缓存清理；重建索引不访问此文件。请随 Application Support/Decision 应用数据备份。知识页的“仅本机保留”支持搜索、分页、多选转入知识库或不保留；成功转入后移出本机列表，失败项保留供重试。
- “不保留”不保存决策正文；本机记录删除后仅留下不含正文的编号与处置标记，防止恢复队列重放时重新创建。历史上已放弃的内容不会回填。

语义识别的模型输入只包含裁剪后的当前问答对，不包含完整 transcript；检索问答是唯一会把多条历史记录送进模型的路径，其输入是用户显式提问时检索到的片段，边界与确认要求见“问答助手”。Apple 和 Qwen 推理都在本机完成；Qwen 推理不创建网络监听。API 或 CLI 后端只有在用户明确配置并启用后，才把这份裁剪后的 system/user prompt 与输出 Schema 发给所选服务商。服务商是否保留请求由对应账号、端点和服务条款决定；Decision 无法替 OpenAI 兼容服务保证不保留。OpenAI Responses 请求和 OpenAI 兼容 API 选 Responses 协议时的请求都会显式设置 `store: false`，但这不替代服务商自己的数据政策。

## 评估

运行确定性回归报告：

```bash
npm run evaluate:semantic -- --report-only
```

强制质量门槛：

```bash
npm run evaluate:semantic
```

门槛为 high precision ≥ 95%、high + medium recall ≥ 90%。未达到时第二条命令返回非零。报告还包含问答关联准确率、问题/答案原文可定位率、置信混淆矩阵以及语言和客户端切片。

截至 2026-08-13，固定 64 条合成回归集的规则基线为：high precision 100%、high + medium recall 100%、关系准确率 84.4%，问题与答案原文可定位率均为 100%；中文和英文召回均为 100%。31 条 high 标签中有 25 条直接判为 high，6 条只有隐式确认措辞的建议被保守限制为 medium；11 条 medium 和 22 条 low 均保持原档。关系准确率不是路由门槛：剩余差异主要来自信息请求被正确判为 low 后，规则评估器不再继续判断其用户文本是否回答了该信息请求，以及无法仅靠词面确认的改写回答。

截至 2026-09-15，同一套语料下本机 Qwen 2B（`builtin-qwen`）的数字是：31 条 high 标签只有 9 条判为 high（其余 22 条被 `semantic_disagreement` 压成 medium），关系准确率 7.8%。它 64 条里 53 条答 `mixed`、10 条答 `uncertain`、只有 1 条答 `answers`，而正确答案是 `answers` 的有 44 条；`decisionIntent` 有 49 条落在 `self_resolved` 或 `information_request`。也就是说在这套语料上，本机 2B 模型的判断不仅没有增益，还把规则本来判对的高置信决策成批压进待确认队列。语料本身也有盲区：样本大多是一两句短句，长消息上的抽取退化（把开头抄到长度上限、选项标签填成整张字母表）它测不出来。

显式评估一个已经启用的 profile：

```bash
npm run evaluate:semantic -- --provider builtin-qwen --report-only
npm run evaluate:semantic -- --provider builtin-apple --report-only
```

本机 profile 直接在本地推理，不产生任何网络调用。再往下是会真实调用外部客户端的两个：

```bash
npm run evaluate:semantic -- --provider builtin-codex --report-only
npm run evaluate:semantic -- --provider builtin-claude-code --report-only
```

这会真实调用所选客户端一次/样本，可能消耗订阅额度或产生费用；不会自动启用 profile，也不会更改设置。报告按 provider 汇总准确率、中位延迟、输入/输出 Token、费用（客户端有报告时）和 Token 不可用次数。API 后端可以把离线预测 JSON 交给 `--predictions` 评估，命令行评估器不会从 Electron 加密存储中提取 API Key。

仓库当前的 64 条完全合成、脱敏语料是实现级回归基线；通过上述门禁只说明这些已知行为没有退化，不等同于产品激活结论。阈值调整和大范围启用前需要至少 500 条按来源、语言和表达类型分层的脱敏标签语料，并用从未参与调参的保留集验收。候选队列中的确认/忽略会成为后续标签来源，但普通对话不会为了评估而长期保存。

查看评估命令帮助：

```bash
node scripts/evaluate-semantic-classifier.mjs --help
```

## 恢复与移除

- **Apple `device_not_eligible`**：不是故障；准备 Qwen 后重启 App，或继续使用规则。
- **`model_missing`**：运行 `npm run prepare:model`。
- **`checksum_failed`**：准备脚本会删除不可信的正式文件并重新下载；不要手工绕过校验。
- **`runtime_unavailable` / 超时**：当前输入自动走另一提供者或规则；30 秒后自动重新探测，也可通过重启 App 立即重新探测。
- **CLI `not_found` / `not_executable`**：在“模型后端”中填写绝对客户端路径；保存后重新测试。
- **CLI `logged_out`**：在原客户端完成登录；Decision 不代管登录。
- **CLI `unsupported`**：更新客户端，直到诊断能找到上述全部安全参数。
- **API `authentication_failed` / `authorization_failed`**：编辑后端并重新填写密钥；旧密钥不会显示。
- **API `rate_limited` / 网络错误**：当前判断继续尝试下一后端；检查账号额度、代理和服务地址后重新测试。
- **中断下载**：保留可信的 `.partial`，再次运行准备命令会续传；长度或哈希异常的 partial 会被删除。
- **移除 Qwen**：先退出 Decision，再删除上面精确路径的 GGUF；生成模型缺失时语义识别自动回到 Apple、其它已启用后端或规则；嵌入模型缺失时决策库和原则召回自动回到关键词。删除模型不会影响 Obsidian Markdown、候选、SQLite 或 Hooks。
- **索引 SQLite 损坏**：在设置页重建；语义 spool 和审计收据不是事实来源。`local-decisions.sqlite` 是本机记录的主存储，不能通过重建知识库索引恢复，也不会自动清空；损坏时须保留原文件并从应用数据备份恢复。
- **问答没有可选模型**：只启用 Apple 时会出现，因为它不提供结构化生成。启用 Qwen 或任一 API / 终端后端即可；检索本身不受影响。
- **回答说证据不足或没有引用**：不是故障，是约定行为。助手只能使用它检索到的片段，够不到答案时必须直说；换个说法追问，或把检索范围调成「全部」。
- **回答标注「用完了检索步数」**：一轮最多 8 步（检索、读全文各算一步）。把问题问得更具体，或先在检索页确认相关材料确实存在。

集成诊断与重装：

```bash
BRIDGE="/Applications/Decision.app/Contents/Resources/bridge/decision-bridge"
"$BRIDGE" install --dry-run
"$BRIDGE" doctor
"$BRIDGE" install --apply
```

重装只替换带 Decision 标识的被动 Hook，并清理历史 MCP，不修改 Claude Code/Codex 的原生询问行为。

## 2026-10-12：短批准与冲突裁决

普通文本识别新增“确认”“批准”“执行”“执行吧”等短批准，以及批准后追加任务的 mixed 情况；只有前文确实留下待决事项时才匹配。编号不能仅因出现在 `PR①` 等任务身份里被当成选择项。

“合并了”“已提交”等纯完成状态不作为新授权，也不调用模型。模型明确判为无决策且用户另开任务或关联不明时，缺乏答案证据的规则候选会被排除；有明确批准、匹配选项或短答案证据时，仍保留 medium，避免模型错判把真正批准丢掉。待决排查计划中的工具选择、部分范围批准也保留。语义提示更新为 `semantic-v2`。

同一组真实回归样本（57 条明确标注）中，当前组合从“漏 1、误 9（1 条 high）”改善为“漏 0、误 1（仅 medium）”。这是修复验证，不是新的盲测；剩余案例为流程状态夹带下一步指令，仍需人工确认。记录见 [improvement.json](benchmarks/decision-recognition-real-2026-10-12/improvement.json)。

## 模型计费与 DeepSeek 峰谷规则

后端配置保留原有固定输入、输出单价，并支持缓存命中输入价。DeepSeek 峰谷模式提供六档每百万 token 单价：

| 类型 | Flash 空闲 | Flash 高峰 |
| --- | ---: | ---: |
| 缓存命中输入 | ¥0.02 | ¥0.04 |
| 缓存未命中输入 | ¥1 | ¥2 |
| 输出 | ¥4 | ¥8 |

参考价核对于 2026-10-12，只有明确点击“填入 Flash 参考价”才会填写；价格可手工修改，选用其他模型时不自动套用 Flash 价格。规则来源：[DeepSeek 官方价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)。

高峰采用北京时间周一至周五 09:00–12:00、14:00–18:00，边界按半开区间处理。周末（含调休上班日）全天空闲；2026 年默认节假日参考[国务院公布的放假安排](https://www.gov.cn/zhengce/zhengceku/202511/content_7047091.htm)，日历日期和年份可编辑以核对服务商口径。未覆盖的年份在工作日高峰窗口显示空闲到高峰的费用范围，不假装已获知该年节假日。

OpenAI 兼容后端会读取 DeepSeek 的 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens`；输入总数已包含缓存命中部分，计价先拆命中与未命中，不能重复相加。输出 token 已包含推理 token，费用也不再额外加一次推理用量。缓存统计缺失且两种输入价不同，显示全命中到全未命中的估算范围；输入/输出统计不足则不计价。

新调用把价格配置快照保存在调用记录的 profile 元数据里，关闭正文留存也会保留；更换价格不改变这些调用的价格依据。旧记录缺少快照时，按当前配置估算，并在详情标明。时段依据本机记录的完成时间减去总耗时估算请求开始时间，可能与服务商收到请求的时刻有差异；金额不是账单或充值余额扣减证明。
