# Decision

Decision 是一个面向 Windows 与 macOS 的本地优先决策平台。它不会替代 Claude Code 或 Codex 的提问界面；你仍在终端原生界面中完成选择。Agent 可以在提出重要选项或建议前，通过只读 MCP 工具核对本地已采纳原则，也可以把用户明确表达的决策、偏好或想法写入本地决策目录；原生问答结束后，Decision 再通过被动 Hook 记录问题与答案，并独立弹出理由面板。

## 下载与构建

从 `v1.1.0` 开始，GitHub Release 默认同时提供：

- Windows x64：`Decision-<version>-win-x64-Setup.exe`；
- Apple Silicon macOS：`Decision-darwin-arm64-<version>.zip`。

两个公开制品都不要求购买商业证书：Windows 安装器为 unsigned，macOS App 使用 ad-hoc 签名且不做 Apple 公证。首次运行可能出现 SmartScreen 或 Gatekeeper 提示，请先核对同一 Release 中的 SHA-256，再按[发布说明](docs/release-notes.md)使用系统图形界面继续；不要全局关闭系统安全能力。

源码构建统一使用 Node.js `>=22.19.0 <26` 和 npm，推荐 Node.js 22 LTS。Windows x64 不需要 Xcode；Apple Silicon macOS 还需要 macOS 26 SDK 与 Xcode Command Line Tools。构建不需要 API Key、签名证书或维护者机器上的固定目录。

```bash
git clone https://github.com/cognelis/decision.git
cd decision
npm ci --ignore-scripts
npm run setup:electron
npm run check
npm run make
```

`npm run make` 会按当前系统生成对应原生制品：Windows 位于 `out/make/squirrel.windows/x64/`，macOS 位于 `out/make/zip/darwin/arm64/`。Qwen 模型权重不进入仓库或安装包；只有需要本地 Qwen 后端时才显式运行 `npm run prepare:model`。完整构建、校验和可选签名边界见[发布文档](docs/release.md)。

布局检查使用独立受管进程组运行：超时先终止本次测试进程组，未退出则在 500 毫秒后强制结束整组。测试脚本的窗口与预览服务器清理最多等待 1 秒，关闭卡住时按失败退出；普通退出、终止信号和测试父进程消失都走同一清理流程。测试套件结束时也会取消仍在运行的探针，不影响已安装的 Decision App。

## 工作方式

1. Claude Code 或 Codex 使用自己的原生问答能力；
2. 在提出重要选项或建议前，Agent 可以调用 `consult_decision_principles`，读取最多 3 条与当前问题相关的已采纳原则、适用条件和注意事项；
3. 用户明确评价本次核对后，Agent 才可以调用 `record_decision_consultation_feedback`，把“有帮助 / 不相关 / 可能误导”匿名计入聚合校准；Agent 不得自行推断评价；
4. 用户明确要求沉淀一项决定、长期偏好或个人想法时，Agent 可以调用 `record_decision_journal_entry`；明确的长期指令本身即构成授权，不必为了同一次记录再次确认，但不得从用户行为中猜测稳定偏好；
5. 原生问答工具完成后，`PostToolUse` Hook 优先静默复制结构化的问题、选项和答案；
6. 如果 Agent 用普通文本把选择、批准或方向判断交给用户，`Stop` Hook 会在本地分析最近一轮的决策请求，下一次同会话的 `UserPromptSubmit` 再与用户回答配对；
7. 桌面 App 在后台联合本地规则与本地语义模型评分：只有规则和模型一致时才会高置信进入理由流程，分歧或语义补召回进入“待处理”，低置信丢弃；
8. 捕获结果先写入仅当前用户可读的本地暂存队列，再尝试通知 App，Hook 始终静默成功退出；Agent 不等待 Decision，可以继续运行；
9. 理由面板展示只读的问题、答案和相关上下文，允许完成理由、跳过、稍后处理或不记录；完成时还可以顺手写下“预期结果”（所选方案带说明时，可一键以说明起稿再改）——趁选择刚做完、结果还没出来时写，复盘时拿它对照实际结果，避免事后按结果改写预期（预期本身不算理由，只写预期不能完成）；如果以前也回答过同一个问题（忽略大小写、全半角、空白与句末标点），面板会列出最近几次的答案、是否与这次相同，以及当时的复盘结论和经验，在写下理由前就能看到上次那样选的结果（首页“补充理由”弹窗同样会列出）；如果这次的选择与上次复盘“低于预期”的那次相同，会直接点明；
10. 只有经过理由流程处置的内容才写入 Obsidian Markdown，SQLite 随后更新派生索引。

事前核对使用本地关键词与向量混合召回，不调用生成模型、不选择答案、不写入决策或原则采用关系，也不会打开主窗口；专用向量模型未准备时自动退回关键词匹配。App 不可用时工具明确返回不可用并放行原生流程。磁盘或投递异常同样不会改变 Claude Code/Codex 的原生 UI 或执行节奏。Decision 不注册问答工具、不注入 `SessionStart` 指令，`Stop` 也只作为观察者运行，不会阻塞 Agent。

## 数据模型

Obsidian Markdown 是唯一事实来源。默认目录为：

```text
<Obsidian 仓库>/Decision Journal/decisions/YYYY/MM/
<Obsidian 仓库>/Decision Journal/preferences/
<Obsidian 仓库>/Decision Journal/ideas/YYYY/MM/
```

主动记录只设三种一等类型：决策、偏好和想法。手动或线下决策沿用既有决策 Markdown、结果回填和复盘；偏好与想法使用独立笔记。线下交流是来源，不是第四种记录类型；复盘是决策生命周期事件，也不是新类型。每条记录默认 `private`，并区分用户原文、用户转述和机器归纳。上下文只摘录必要内容，不保存完整 transcript、会议录音或聊天原文。

偏好要求单独记录适用条件、例外、强度和证据成熟度；字段完整时成为有效偏好，否则进入待澄清箱。想法可以快速进入待澄清箱，补充“为什么值得保留”后再转为有效。偏好和想法维护当前摘要，每次修订必须填写变更原因并追加上一版快照；实质上变成另一条记录时应新建并通过后续版本关系表达，不覆盖历史。偏好与想法会参与事前核对，但只作为与已采纳原则分开的一组「你自己记下的立场」返回：它们不进入 `matches`，不改变「有没有相关已采纳原则」这个结论，每条都带身份说明（偏好允许例外、未经方法论流程确认前不是原则；想法尚未形成承诺），并保留例外与未决问题；响应里的 `boundary.noPreferencePromoted` 明确声明本次没有把任何偏好当作规则。

每条决策笔记保存决策问题、候选方案、用户答案、任务背景、约束与考虑、采集来源、理由原文、判断依据、预期结果、后续结果和人工确认的复盘结论。多问题原生问答会拆成多条记录，并通过 `batch_id` 和 `question_index` 保留关联。

SQLite 位于 Decision 的应用数据目录，只用于本地全文检索、语义向量、历史待补理由状态、内容指纹和其它可重建索引。删除 SQLite 后可以完全从 Markdown 重建；SQLite 更新失败不会删除已写入的 Markdown。新选择“稍后处理”的项目保留在私有 capture spool，不依赖 SQLite；当前 UI 会合并展示本地待补项与历史 Markdown 待补项。

未处置的捕获事件保存在私有 `capture-spool` 目录中。每个事件独立原子写入；用户提交理由后，处置内容也会先写入仅当前用户可读的恢复日志。选择“稍后处理”时保留事件和 `deferred` 标记，直到理由最终补完；完成、跳过或不记录后删除事件和处置正文，仅在 spool 中保留不含业务内容的 SHA-256 语义键、采集模式和时间回执，用于一次性跨模式去重。“稍后处理”和“不记录”都不会写入 Markdown 或 SQLite。

中置信结果保存在独立的私有 `candidate-spool` 中，最多 100 项并默认保留 7 天。它们在用户确认前不是正式决策，不写入 Markdown 或 SQLite；App 未运行时也不会因候选而被主动启动。忽略后删除候选正文，只留下不含业务内容的去重收据。

普通文本的完整问答对只在私有 `semantic-pair-spool` 中保留到分类和路由完成；未完成配对 24 小时过期，并由后续 Hook 至多每小时主动巡检删除，已配对内容最多保留 7 天。独立的 `capture-audit` 仅记录阶段、耗时、置信档位、稳定错误码和经过安装级随机盐 HMAC 后的指纹，不包含问题、答案、项目路径、原始会话 ID 或异常堆栈；默认保留 7 天且最多 10,000 条。

事前原则核对只在私有 `decision-consultation-metrics.json` 中保存聚合计数：调用、命中/未命中、强/弱匹配数量、客户端来源、匹配耗时，以及按“有帮助 / 不相关 / 可能误导”、来源和结果强度汇总的匿名评价。每次核对只在内存中保留最多 30 分钟的一次性随机回执，最多 256 个，评价后立即消费，App 重启即全部失效；回执本身不落盘。指标文件不保存问题、候选选项、上下文、项目名、原则编号、反馈回执或逐次调用/评价事件；指标写入失败也不会延迟或阻断客户端。方法论“分析”中的试算使用相同匹配逻辑，不计入真实调用次数；关闭弹窗后输入不会持久化，只有用户主动评价时才增加一个匿名分类计数。

模型判断另存到私有 `model-traces`：每个后端尝试一条，默认保留 7 天且最多 1,000 条。它不进入 Obsidian 或 SQLite；正文记录可关闭或从设置页清理。

主动记录的未完成表单会作为独立草稿保存在本机，关闭后再次打开可继续填写；正式保存成功后清除，也可主动清空。问答回答转存的预填稿不会覆盖手写草稿。记录决策时可同时选择复盘日期；保存后直接打开决策详情，偏好与想法则定位到对应卡片。

偏好与想法的修订支持补充适用条件、例外、保留理由和下一步验证，并明确选择待澄清、有效或已归档状态；有效记录必须满足其类型的必要条件。归档后可通过修订恢复，每次仍要求变更原因并保留旧版快照；卡片的“修订历史”可展开核对原因与修订前内容。

决策详情和首页复盘会显示已记录的预期结果。首页回填实际结果时可选择“保存并继续复盘”，在同一弹窗完成后续判断；已复盘决策的“用于提炼原则”会直接打开证据选择器并选中本条，不自动调用模型。

## 本地语义识别

Decision 本质上做的是“采集 + 决策意图识别 + 问答关联 + 受限结构提取”。模型只参与语义判断和片段建议；Hook 配对、边界限制、原文定位、最终路由及持久化仍由确定性代码控制。

桌面 App 每次判断前按设置页优先级尝试所有已启用后端。首次运行默认：

1. Apple Foundation Models：macOS 系统自带、完全在设备端运行的系统语言模型；
2. Qwen3.5-2B：Apple 模型不可用时使用的本地 GGUF 备选；
3. 规则：所有模型都不可用、超时或异常时的无模型降级。

设置页还可以显式添加 OpenAI Responses、Anthropic Messages、OpenAI 兼容 API，或启用检测到的 Codex CLI / Claude Code CLI。它们默认关闭；启用后会把裁剪后的当前问答发送给相应服务商。DeepSeek 走「OpenAI 兼容」这一档：在编辑界面点「DeepSeek」预设即可填好服务地址 `https://api.deepseek.com`、Chat Completions 协议和 JSON 输出方式，模型输入框提供 `deepseek-flash`、`deepseek-v4-pro` 等候选，API Key 与其它远端后端一样默认由系统加密能力保存、不回传界面。服务地址可以照服务商文档填：带版本段的（如 `https://api.moonshot.cn/v1`、`http://localhost:1234/v1`、`…/api/paas/v4`）原样使用，不带的（如 `https://api.openai.com`）自动补 `/v1`；地址或模型不存在（HTTP 404）时测试结果写“配置无效”。一个后端失败时会留下独立调用记录并继续尝试下一项，不会影响 Hook 或原生客户端。模型页每个后端名字下面会写“调用记录：N 次 · X tokens”，按本机保留的模型调用记录汇总（默认最近 7 天）；没被调用过的后端不写，排顺序或估成本时可以参考。token 只按上报了用量的调用计：部分调用没上报时写作“至少 X tokens”，一次都没上报（例如 Apple 的系统模型）时只写次数。

采集分类默认**不调用模型**：模型页「当前识别引擎」下的「采集分类」下拉框默认「只用规则，不调用模型」。它是唯一无人发起的模型调用——每一轮对话都会走它——而固定语料实测本机 2B 模型在这个用途上不如纯规则（详见[本地语义识别文档](docs/semantic-recognition.md)）。选「规则加模型」才会按上面的顺序调用后端。其余用途（问答、方法论提炼、草案）不受这个开关影响。

Codex CLI 和 Claude Code CLI 的模型输入框均支持候选和手动输入，留空使用客户端默认模型。进入模型设置或点击「刷新模型候选」时，App 优先使用现有 CLI 的 access token 向对应官方服务请求目录（Codex 使用 CLI 原生 `/backend-api/codex/models?client_version=…`，Claude 使用 `GET /v1/models`），不使用 App 的候选缓存，也不发送用户消息或执行推理。现有登录凭证不支持该接口、无法读取、已失效，或查询失败时，依次回退至 CLI 目录和本机缓存；界面明确标注「服务端直查」「CLI 目录（可能含内部缓存）」或「本机缓存」。Claude 在 macOS 上可读取默认 CLI 钥匙串凭证，其他平台和自定义配置目录使用该目录的凭证文件；无法读取时继续回退。API Key 或第三方提供商模式不混用本机订阅 OAuth 凭证，继续使用 CLI 目录。凭证仅在主进程内存中使用，只发送到固定官方 HTTPS 地址，禁止重定向；不复制、不保存、不刷新 CLI 登录令牌，不修改客户端账户。候选缓存只保存模型标识和名称，重启或重建索引不会清除。服务端模型目录仍不保证每个模型都有推理权限；CLI 目录也不保证绕过其内部缓存。

本机验证（2026-10-12）：两种 CLI 的现有 OAuth 凭证均可用于服务端模型目录直查。Codex 凭证未过期，但查询公开 `/v1/models` 被以缺少权限为由拒绝（HTTP 403）；同一凭证查询 CLI 原生目录返回 HTTP 200，共 10 个模型、7 个可显示模型。请求采用已安装 CLI 的版本、当前账号标识和 Decision 自身的客户端标识，不改登录状态，也不读取旧模型列表冒充服务端结果。原生目录遵循 [Codex 0.161.0 官方实现](https://github.com/openai/codex/blob/rust-v0.161.0/codex-rs/model-provider/src/models_endpoint.rs)，后续接口变化或认证失败仍回退 CLI 目录和本机缓存；[Sign in with ChatGPT 的公开模型接口](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)属于不同的认证接入路径，不能假定现有 CLI 凭证具有其权限。Claude 查询方式参考 [Claude 模型目录](https://platform.claude.com/docs/en/api/models/list)。

模型不能单独触发高置信弹出理由面板。规则和模型一致为高置信；分歧、混合回答或模型补召回最多进入中置信候选；模型不可用时保留原有规则结果。原生工具问答继续走结构化路径，不经过语义模型。

Qwen 权重不包含在 `.app` 中。首次准备会明确下载约 1.33 GB 的生成模型和约 639 MB 的专用多语言嵌入模型：

```bash
npm run prepare:model
npm run prepare:model -- --check
```

文件固定为 `Qwen_Qwen3.5-2B-Q4_K_M.gguf` 和 `Qwen3-Embedding-0.6B-Q8_0.gguf`，存放在系统的 Decision 应用数据目录（macOS 通常为 `~/Library/Application Support/Decision/models/`，Windows 通常为 `%APPDATA%\Decision\models\`）；清单固定精确字节数、下载提交和 SHA-256，加载前会再次验证。两者采用 Apache-2.0 许可证，本地运行不需要 Ollama、LM Studio、订阅或云端 API。

决策库搜索会先保留精确关键词结果，再用 1024 维本地向量补充含义相近的记录（知识页的“决策语义”开关只控制这一半；笔记检索在本机向量可用时始终是关键词加语义的混合，不受该开关影响）；纯语义命中会明确标记“语义相关”，且限制补充数量。已采纳原则也使用同一索引参与事前核对和原则建议。向量索引位于应用数据目录，可增量更新、可随全文索引重建；嵌入模型缺失、校验失败或运行异常时，搜索和原则召回都会自动退回原有关键词逻辑。

## 模型后端与调用记录

“模型后端”按列表顺序路由。OpenAI、Anthropic 和 OpenAI 兼容后端可配置模型、HTTPS/本机回环地址、协议、超时和 API Key；密钥默认使用操作系统加密能力，仅保存在主进程私有目录，不会返回界面、进入日志或写入 Obsidian / SQLite。

「通用设置 → 密钥存储」提供默认关闭的「本地密钥模式」，同时适用于模型 API Key 和 PR 平台令牌。开启后以明文保存在本机应用私有目录（目录 `0700`、文件 `0600`），不再调用系统钥匙串，因此无需反复输入系统密码。切换会迁移已有凭据，首次从系统加密切换时可能仍需授权；关闭后重新使用系统加密。密钥不会写入 Obsidian 仓库或返回界面。

Codex 与 Claude Code 后端复用客户端现有登录状态。设置页会显示实际路径、版本、登录状态和安全调用能力，也允许配置绝对路径与模型名。两者都在一次性空目录中以无 shell、无工具、无会话持久化模式运行；Codex 固定为只读沙箱并拒绝批准，Claude 固定为 safe mode、空工具和 `dontAsk`。模型正文只从 stdin 提交，子进程标记会让 Decision Hooks 在读取任何内容前退出，避免递归采集。停用它们不会卸载客户端或退出账号。

“模型调用记录”按每个后端 attempt 保存模型输入、可见输出、结构化结果、模型版本、耗时、状态和 Token 来源。正文记录可关闭；关闭后只记录元数据。记录默认保留 7 天、最多 1,000 条，可按单条、同一请求或全部清理。列表上方按当前用途筛选合计调用次数、未成功次数、token 与平均耗时；在模型页给后端填了单价的调用，再折算成金额，没填价的注明“N 次未计价”。有未成功的调用时，旁边多一个“只看未成功（N）”开关，勾上后列表和合计都只算失败、超时、取消等未成功的调用，排查问题时不用在成功的记录里翻找。Apple 无可靠 Token API 时明确显示不可用；Qwen 使用运行时计数；API / CLI 使用服务商报告值，不用字符数伪造。

完整的数据边界、固定安全参数和故障恢复见 [本地语义识别文档](docs/semantic-recognition.md)。

## 决策库

“决策库”顶部提供统一的“主动记录”入口，可选择决策、偏好或想法，并按类型逐步展开必要字段；来源可标为现在手动记录、线下交流、会议或个人观察；在 PR 评论里做出的决定从评审页的「PR 讨论」记录，来源为「PR 评论」并保留评论链接（见 [PR 列表与评审](#pr-列表与评审)）。保存偏好或想法后会切换到“偏好与想法”视图，支持搜索、按类型和状态筛选、归档，以及填写变更原因后修订。标题、正文及各类补充字段会在提交前按保存接口的规则校验；超限内容保留供修改，并提示具体字段。保存过程中暂时锁定表单和关闭入口，避免重复提交或误丢修改；失败后原稿仍可编辑重试。Renderer 只接收结构化记录，不接收 Vault 路径或扫描诊断。

决策视图提供最多 200 条本地决策历史，支持搜索问题、答案、理由、上下文、预期结果、后续结果、复盘经验和项目，并可按理由状态、来源、复盘进度或复盘结论（如“低于预期”）、记录时间和项目筛选（项目下拉列出全部项目及各自条数，只有一个项目时不显示；从周期回顾点开某个项目时自动选中）；在知识页按 / 可直接聚焦搜索框，搜索框内按 Esc 可清空关键词；决策搜索框内按 Enter 或 ↓ 跳到第一条结果（Vault 笔记搜索框按 ↓ 进入结果），列表中用 ↑/↓、Home/End 移动，Enter 打开详情或笔记，第一条上按 ↑ 回到搜索框。筛选或关键词导致没有匹配结果时，空状态会明确提示并提供“清除关键词与筛选”一键复位；待补理由、待写预期、需处理这类待办筛选被逐条处理到空时，则会说明已经处理完（仍有来源、时间、项目等其它筛选时注明只是“当前筛选下”处理完），而不是“没有匹配结果”。首页概览中的“待确认”“需复盘”“近 7 天记录”“全部决策”数字卡片可以直接点开对应的候选处理、复盘收件箱或知识页决策视图，数量为零的待办卡片保持只读；“最近决策”列表中的每一条也可以点开，在知识页中查看详情。首次使用且尚未接入任何客户端、也没有任何决策时，首页会显示“前往接入”引导；接入或记录第一条后自动消失。短中文关键词使用安全的本地模糊匹配，较长关键词使用 SQLite FTS 相关性排序。点击任一记录可以查看最终选择、决策理由和当时上下文，也可以人工关联最多 5 条这次实际采用的已采纳原则、安排复盘日期、记录实施结果，再用“优于预期、符合预期、部分符合、低于预期、暂无法判断”完成结构化复盘并补充经验。详情中列出的已采用原则可以直接点开，跳到方法论页的该条原则详情（自动切到它所在的状态筛选）；如果这条决策后来被用作某条原则的证据，详情里还会出现“由此沉淀的原则”，同样可以点开——它与“采用的方法论”是相反的两个方向，一个是这次用了哪些原则，一个是这条记录支撑了哪些原则。原则关联不会由模型自动猜测；已归档原则保留既有历史关联，但不能再新增。到期或已有结果但尚未复盘的决策进入首页“复盘收件箱”，不会主动打开 App 或弹出窗口；卡片内每条直接给出它当前缺的那一步——没有结果的是“回填结果”，已有结果未复盘的是“完成复盘”——可以就地填写并保存（⌘/Ctrl+Enter 同样等于保存），保存后重新读取仍然到期的条目；结果还没出来时，“回填结果”弹窗里可以直接推迟到一周、两周或一个月后再复盘（已写了结果说明时不提供推迟），卡片顶部会提示推迟到了哪天，点错了可以直接“撤销”恢复原来的复盘日期；也可以照旧点开进入决策详情。原则关联、复盘日期、结果和复盘先原子写回原 Markdown 笔记，再刷新可重建的 SQLite 索引；Markdown 文件路径不会暴露给渲染进程。

决策视图还可以按记录时间筛选“近 7 天”“近 30 天”：窗口按今天及此前的自然日计算，与首页“近 7 天记录”同一口径，首页的这张数字卡片点开后直接落在已筛好的近 7 天列表上。有关键词时，列表里命中的词以荧光底色标出（偏好与想法、Vault 笔记和快速跳转的结果同样如此）；标记通过 CSS 高亮范围实现，不拆分文字，复制和辅助技术读到的仍是原文。决策详情分为两栏：左栏按时间讲这次决定——问题、最终选择、理由、当时上下文、预期，再到实际结果与复盘；右栏是进度（记录、理由、预期、实际结果、复盘、沉淀原则六步，轮到你且已到期的一步用琥珀色标出）、复盘计划和两个方向的原则，适用范围与关联放在左栏末尾。理由仍待补的决策可以在详情里直接写下理由原文并保存，与首页“补充理由”走同一条写回路径。还没有预期的决策可以在记录实际结果之前补写“预期结果”（写回笔记的预期结果段，早期没有这一段的笔记会在“后续结果”前补上）；一旦记录了实际结果就不再允许写入或修改预期，避免按结果改写预期。“复盘”筛选中的“待写预期”会列出还没写预期、结果也还没出来的决策，配合 ← / → 可以逐条补完。同一问题（忽略大小写、全半角、空白与句末标点）以前也做过决定时，右栏会列出那几次的答案和日期，并标明与这次是否一致，点开即切换到那一条。关联原则时，本地匹配认为相关的已采纳原则排在前面并说明原因，但不会替你勾选。详情标题栏可以在当前列表中逐条查看上一条和下一条（也可用 ← / →）；打开任何编辑器时逐条查看暂停，未保存的内容不会被切走；补完的记录因此离开筛选列表时，“下一条”就是补位上来的那一条。标题栏还可以把这条决策复制为 Markdown（问题、选择、理由、上下文、预期、结果与复盘，只含记录里已有的部分），贴进 PR 描述或消息；筛选栏末尾的复制按钮则把当前筛选出的整张列表按同样格式放在一个“决策记录（N 条）”标题下，例如先按项目和近 7 天筛好，再整体贴进 PR 描述。

## Vault 笔记检索

全库笔记检索与决策检索共用侧边栏「知识」页的同一个关键词框，结果分成上方的决策列表与下方的「Vault 笔记」卡片。它递归纳入当前配置 Vault 中的普通 Markdown 笔记；App 自己写入的 `Decision Journal` 目录整体排除在笔记索引之外——那些内容已经是决策、偏好想法与原则，由各自的视图负责，重复进笔记索引只会让同一条记录出现两次。`.obsidian`、`.trash`、`.git`、`.hg`、`.svn`、`node_modules` 等目录按 ASCII 大小写不敏感排除，符号链接、非 Markdown 附件和超过 5 MiB 的单篇笔记也不进入首版索引。它不会把普通笔记解析成决策，也不会改变决策检索的查询、排序或重建生命周期。

每个 Vault 使用其规范绝对路径精确表示的 SHA-256 身份，数据库位于 `userData/obsidian-search/vaults/<identity>/index.sqlite`。数据库内部还持久化同一身份；已有行、目录身份和当前 Vault 身份不一致时拒绝复用，防止切换 Vault 后读到其它库的派生行。身份和绝对路径都不返回 Renderer；界面只接收当前 Vault 的相对 Markdown 路径。

App 启动后在后台建立当前 Vault 的独立索引；扫描按笔记惰性产出，不在内存保留整个 Vault 正文，并在目录枚举、路径校验和按已知剩余字节自适应的分块读取之间响应取消。后续 Markdown 新增、修改、移动和删除会触发合并后的增量同步。只有完整扫描结束、没有目录/笔记诊断、模型或索引失败、跳过项时，才推进“最近成功同步”时间；否则保留上一次成功值。笔记卡片在索引中约每 800 ms、稳定状态约每 5 秒低频刷新，显示覆盖、进度、跳过/失败数量并提供独立重建；已有索引在后台更新期间仍可搜索，首次索引尚无结果时搜索保持禁用。

语义召回直接使用本机 `Qwen3-Embedding-0.6B-Q8_0.gguf`，不经过云端 API、Codex/Claude CLI 或模型调用记录。模型必须由用户先运行 `npm run prepare:model` 明确准备，App 不会静默下载；模型缺失或暂时不可用时，界面会如实标记并只返回关键词命中。模型稍后准备完成后，下一次搜索会探测到它并自动排队强制重建语义向量。查询流式遍历 SQLite，关键词路和语义路各自只保留前 200 个候选，并定期让出主线程；200 名截断之外不承诺精确全局排名。点击结果会在主进程重新校验索引中的 Vault 相对路径，再使用官方 `obsidian://open` URI 打开原始笔记。

App 退出时会立即启动 Obsidian 关闭，与其它语义资源清理并行推进。只有 watcher、在途同步/搜索、嵌入资源和 SQLite 都成功关闭后才写入 smoke shutdown marker；打包冒烟在进程退出后仍找不到对应有效 marker 时会如实失败，不把快速退出伪装成清理完成。

## 问答助手

正文中有效的引用编号可直接展开该条回答的引用摘录，显示已有的失效或更新提示，并保留独立的“打开来源”入口；代码内的编号、普通 Markdown 链接和无效编号不会触发引用。

侧边栏「问答」是一个独立的多轮对话入口，紧邻首页（⌘/Ctrl+2），与检索页分开：检索页只做检索，不再内嵌回答。助手基于你自己的决策、原则、偏好与想法，以及 Obsidian 笔记作答，**只读**——不写入 Markdown、SQLite，也不产生候选、理由或原则采用关系。对话通过本机应用存储保留，完整保留每段会话，界面先显示最近 40 条、可逐批加载更早消息，支持切换和删除；会话库可按标题、正文和草稿搜索，支持重命名、收藏及只看收藏，不再因超过 10 段而自动淘汰历史。历史读取失败时显示重试入口，保留原数据，读回成功前不启动自动保存。本机保存失败时会提示未保存并提供重试；当前页面的对话仍可阅读和导出，恢复写入后提示自动消失。发送后立即锁定当前轮次，连续提交不会重复调用模型；回答期间不能新建、删除或切换对话，避免回答串入其它会话。长对话可继续追问，成功后追加到完整历史并保留原会话标题，失败或停止时保留发送前的窗口并把问题退回输入框。模型缺少回答正文，或在最终作答阶段仍返回其它动作时，按失败处理并保留问题供重试，不把应用提示写成模型的成功回答。取消检查覆盖模型配置读取前后，已取消的请求不会继续初始化，也不会把随后返回的配置故障误报为本轮失败。停止生效后不再启动下一路来源检索、后继查询或链接读取；已发出的单次存储调用需等待返回。停止请求失败会提示重试并继续等待本轮结果；仅收到实际取消结果后才显示已停止，已结束轮次的迟到错误不影响后续问答。问题上限为去除首尾空白后的 8,000 个字符；超限时保留输入、提示缩短，并阻止按钮和快捷键提交。合法的本轮问题完整进入提示词，必要时减少更早的历史，提示词总上限保持不变。回答未完成时退出应用，重启后会恢复已完成的历史，并将本轮问题放回草稿，不自动重发。同一窗口内切换侧边栏时，正在进行的回答继续执行并保存，返回问答页可查看结果或停止尚未完成的调用；输入框中尚未发送的问题按对话保存在本机，切换对话或重启后可恢复；只有草稿的对话也可新建、切换和删除，列表以“草稿”标识。

“材料范围”支持搜索决策、原则、偏好、想法和 Obsidian 笔记，勾选最多 12 份材料后仅基于这些来源回答。一次搜索最多列出 12 份：决策与原则、偏好与想法、笔记三类轮流分配名额（各有命中时不会被前一类挤掉），列表仍按这个顺序排列；找到的多于 12 份时会提示换个更具体的词。指定清单随会话保存；每轮重新读取原文，不带入范围外旧引用，不执行额外检索或跟随链接。未选择材料时不能发送，材料不可读时保留问题并提示重试，不自动扩大范围。上下文放不下全部指定来源时要求减少材料或缩短问题；原文被截取或只展示摘录时会提示本轮材料受限。

每轮问题可以“修改问题并分支”，将之前的历史复制到新会话，原问题放入可编辑草稿；每条回答也可“从此处继续分支”，保留到该回答为止的上下文。新分支沿用模型与材料范围，可自行切换模型；原会话及其后续消息、草稿保持不变，分支不会自动发起模型调用。

展开引用后可“核对当前来源”，对照回答时保存的摘录与当前原文，分别提示摘录仍可找到、未完整匹配或来源不可读。旧回答未保存完整文件快照，因此摘录匹配不代表全文未变；预览最多显示当前原文前 20,000 字符。选择“根据当前引用重新核对”会建立独立分支，限定原回答引用的材料并填入核对草稿，由用户检查后发送。

完整历史仍保存在本机应用存储，存储空间不足时保留现有保存失败提示、内存中的历史及导出入口，不会静默淘汰旧消息；旧版已截去的历史无法凭空恢复。模型调用继续只发送有界的近期上下文，完整归档不等于整段历史都发给模型。

工具栏「导出」可将当前对话及引用路径保存为 Markdown。导出期间显示进行中状态，阻止重复导出、切换、新建、删除会话和发送新问题；取消或失败后恢复操作并保留草稿，每次导出按实际结果更新提示。尚未发送的输入会另列为“未发送的草稿”，不会作为已发送问题或模型回答。覆盖已有文件时，完整写入临时文件后才替换原文件；写入或替换失败会保留原文件，便于重试。

它是一个会自己决定检索什么的 agent，而不是固定检索一次再作答：每一步模型可以选择检索、阅读已找到材料的全文或作答，需要更多材料就继续检索或阅读，够了就直接回答。跟随笔记链接时，带目录的目标按完整相对路径匹配；搜索结果出现多个同名路径时跳过，未闭合或过长的链接目标不触发查找。一轮最多 8 步，用完仍未作答则基于已找到的材料强制作答并标注；重复检索同一个词会被拦下，避免原地打转。全文读取失败时会在模型看到的证据中标明仅有摘录，排除该可读编号并拦住重复尝试；其它证据仍可读取，重新检索刷新该来源后可再次尝试。每条回答都可以展开「检索过程」，看到它实际搜了什么、各拿到几条——检索过程和结论一样可复核。过程受限时会说明读取失败、无效编号或重复动作等具体原因，不再统一显示为检索步数用完；缺少原因的旧历史使用中性提示。某一路检索不可用、只覆盖部分数据或索引尚未就绪时，会保留其余来源的结果并说明覆盖限制；偏好与想法目录内个别文件损坏或无法读取也会标为部分可用，不暴露文件路径或解析错误详情；模型会收到同样的信息，不能把这类空返回直接解释为记录不存在。

回答只允许使用检索到的证据。引用的标题与路径由 App 从检索结果填入，模型只能选择引用哪几条，越界或重复的编号会被丢弃，因此它无法编造来源。读取及引用校验同时受当前提示词的实际证据集合约束：因长度预算未展示给模型的材料，不会仅因曾被检索到就生成引用卡片或执行读取。检索范围可在「全部 / Decision 记录 / Obsidian」之间切换；追问沿用的旧引用也按本轮范围过滤，范围外材料不进入本轮证据或全文读取，旧对话文字仍保留为上下文；同一来源重复出现时使用最后一次引用的摘要和状态，并按最后使用顺序保留最近 12 条证据；本轮重新检索命中同一来源时会更新证据、保留引用编号，并使已读取的旧正文失效；「Decision 记录」覆盖这个应用自己记下的全部内容——决策、已采纳原则、偏好与想法。偏好和想法作为独立的引用类型出现，每条都附带它的身份说明（偏好是当前立场、允许例外、未经方法论流程确认前不是已采纳原则；想法尚未形成承诺、不能当作已采纳方向），这句说明同时进入模型看到的证据块和界面；适用条件、例外、未决问题等限定字段随摘录一起给出，避免偏好被读成规则、想法被读成结论。长记录在既有长度上限内为各非空字段保留片段，避免长正文把限定条件全部挤掉；字段被裁剪时显示省略号。偏好和想法的全文按记录编号读取，包含正文、限定条件、背景与补充说明；想法还包含下一步验证，追问沿用引用时也保留其身份说明。点击引用时，本机已记录的决策和已采纳原则直接跳到各自的详情页（那里才有适用范围、关系与复盘），偏好与想法跳到知识页的「偏好与想法」并高亮该条；笔记和旧格式历史决策没有对应详情页，仍在 Obsidian 中打开原文，按钮文案说明这次会打开哪一种。打开引用的错误仅对应当前会话中的最新打开操作，切换、新建或删除对话后不会显示旧请求的迟到错误。

回答模型列表区分加载中、失败和成功空列表；读取失败时可原地重试并保留草稿，只有确认列表为空时才提示启用模型。回答模型可在发送问题前切换，默认使用设置页中优先级最高的已启用后端；Apple Foundation Models 只做分类、不提供结构化生成，因此不参与问答也不出现在列表里。显式选定某个模型后，该次调用不会在失败时静默改用其它模型；恢复会话或刷新列表时，若该模型已停用或删除，会保留问题并要求重新选择，不自动改用列表首项。会把内容发出本机的后端（OpenAI、Anthropic、兼容 API 以及 Codex / Claude Code CLI）直接发送，不再逐次确认；模型选择器标出本轮内容会不会离开本机，选择本身就是授权。新回答的页脚保存接口实际返回的模型名称、型号和本机/远端标记，切换模型或重启后仍可查看，Markdown 导出也会保留；未记录这些信息的旧回答不补猜来源。模型来源在本机会话中与消息正文分开保存，使旧版读取正文时不会因不认识来源字段而丢弃回答；旧版重新保存时可能丢失来源附加信息。回答进行中显示发起该轮时选定的模型及本机/远端标记；刷新配置、重命名或移除模型不会改变这次调用的显示，结束后再使用最新列表。

回答可评价为“有用”或“没用”，补充说明最多 2,000 个字符。只有实际保存成功才显示“已记为”；失败时说明保持可编辑，并可重试。未提交说明在当前窗口内按回答轮次独立保留，评价其它回答或切换会话不会清空它，点击“记下”只提交并关闭对应说明。问答评价在本机保存问题、评级、说明和引用路径，不保存回答正文；支持完整的 8,000 字符问题，最多保留 500 条，补充说明更新同一条评价。缺少原问题或轮次编号的历史回答不提供评价入口。个别非法评价条目不会影响其它有效评价；整份文件不可读、损坏或版本不支持时拒绝覆盖原文件，恢复后可重试。

## 编码与评审中的决策上下文

Agent 可以调用只读 MCP `search_decision_context`，查询 `Decision Journal/summarize` 的历史沉淀、`decisions` 中的已记录选择与 `principles` 中的已采纳原则。三类结果分别标注，历史笔记的 `accepted` 不会因此变成“已验证原则”。普通 Obsidian 全库搜索继续是独立工作区；本功能不把旧笔记改写进 App 决策目录。

工具支持 `query` 关键词、`recordId` 精确编号、`source` 来源和 `project` 项目筛选，空 query 用于浏览。也可以传 `repositoryPath` 指定本次任务的 Git 目录，bridge 会识别原 checkout、worktree 与仓库内子目录，不使用 MCP 进程 cwd 猜测任务仓库；远端凭证和绝对路径不会发给 App。project 可显式覆盖推断项目，跨仓库探索可以省略项目和仓库限制。默认每页 8 条、最多 20 条，通过返回的 `nextOffset` 继续读取，不受决策库 200 条展示上限限制。分页反映每次读取时的文件状态。

结果包含已记内容、项目、原状态、适用条件（如有）、来源相对路径、原文摘录与行号，以及旧笔记已有的会话编号。`superseded_by` 的字符串和数组都会保留，单向 `supersedes` 也能补出反向后继；已被替代或退役的记录仍可查到，但会明确标记并附后继引用，不能作为当前约束孤立使用。没有替代标记只表示当前可读数据中未发现后继，不证明历史决定仍适用于本次任务。

查询每次从三个限定事实目录及独立范围、关系元数据重建有界内存投影，同轮并发共用扫描；不新增磁盘索引、查询日志或模型调用。单来源最多检查 5,000 个扫描项、处理 16 MiB，解析不超过 512 KiB 的笔记，事实扫描预算 4 秒，范围扫描并行且最多 2 秒。损坏、重复编号、读取失败或触及上限时明确返回覆盖不完整，部分可读结果仍可使用；空来源、没有匹配与不可用分别说明。只有公开给工具的相对来源和必要摘录会返回，不返回 Vault 绝对路径。偏好与想法暂不进入此工具。

`module`、`layer` 和 `files` 可指定当前模块、技术层次与文件集合。范围判断只比较明确记录的项目、仓库身份、层次和路径约束，返回“结构化范围匹配 / 待核对 / 明确不适用”；部分文件匹配、缺少范围或存在文字例外时仍需判断。明确不适用的相关项默认排除，`excludedByScope` 说明数量，`includeOutOfScope` 或按编号查询可以继续查看。它不会从文件名或标签自动给旧决策赋予前后端范围。

用户明确指定某条决策的适用范围后，可调用写工具 `record_decision_scope`，携带检索返回的原文哈希、范围版本和修改原因。范围独立保存在 `Decision Journal/decision-scopes/` 的 Markdown 中，并保留最多 20 个旧快照（整篇上限 512 KiB）；不改写原决策。原文变化会使旧范围进入待核对，旧范围不再参与自动排除；过期范围版本的修改请求会被拒绝。仅仅检索到一条记录不构成修改其范围的授权。

历史决策之间的人工关系通过 `record_decision_relation` 记录，可确认为冲突、替代、无关或撤销。输入必须带双方来源、编号、内容哈希、关系修订号及理由；替代关系还要明确谁是后继。关系独立保存在 `Decision Journal/decision-relations/`，保留最多 20 条修订，不修改双方原笔记。当前有效的人工判断覆盖同一对记录的早期内联关系；撤销后重新使用原文关系。原文变化或来源缺失时，关系进入待核对；新增替代链形成循环时会拒绝保存。来源已删除也可以撤销已有人工判断，避免留下无法处理的悬空关系。

对已记录的 App 决策，可以用 `record_decision_outcome` 回填真实结果、复盘结论和下次复盘日期。先通过检索读取 `outcomeState` 与内容哈希；回填按版本校验，一次保存所提供的字段，省略的字段保持原值。修改已有复盘的结果时，必须同时提供用户认可的新复盘或明确清除旧复盘。Markdown 已保存但索引失败会单独返回，避免误判为未保存而重复写入。原始选择、理由和预期不变；绑定旧笔记版本的范围和人工关系会进入待核对，不会自动重新确认。此工具仅更新 `decisions`，历史 `summarize` 和原则继续使用各自现有流程。

来源回跳使用 `open_decision_source`：先读取来源、编号和内容哈希，App 核对后向 Obsidian 请求打开原始 Markdown；移动后的笔记按编号重新定位，不接受任意路径或 URL。此入口无需全文索引已收录该笔记，也不会伪造会话跳转地址。

`prepare_decision_handoff` 根据选定的 1–10 条来源版本生成只读 Markdown 与结构化交接内容。它区分历史证据、待核对事项和当前任务提供的未决问题／验证说明／后续步骤，保留范围、替代关系、复盘和出处。来源已变化、缺失或覆盖不完整时明确提示；不会因为检索相关就把历史记录当成当前约束。交接生成不保存笔记、不创建任务、不发送消息，后续继续工作时仍需核对来源与关系版本。

桌面端可在“决策库 → 决策详情 → 适用范围与关联”直接查看与编辑范围、查找并确认关系、调整或撤销旧判断，或打开原文。“整理交接”支持当前单条决策的任务目标、待核对事项、验证说明和后续步骤，生成预览后复制。范围和关系沿用相同的版本校验；保存冲突会保留草稿，取消编辑并重新读取后再核对。

同一区域的“使用反馈”可以记录具体任务中的帮助、场景不适用、信息不足或无关，支持更正、撤回和修订历史。MCP 对应 `record_decision_context_feedback` 与 `get_decision_context_feedback`。反馈独立保存在 `Decision Journal/decision-feedback/`；固定编号与版本使重试不会重复计数。汇总区分全部未撤回观察和当前原文版本，不将计数解释为准确率，也不自动调整决策、范围、关系或检索排序。

检索可用 `relation` 筛选已确认冲突、被替代的记录或需要复核的生命周期，并返回理由、版本、最近历史及带来源的后继引用。`lifecycleState` 区分当前、被替代和不确定；当前状态不代表适用性已自动证明，冲突也不会自动挑出一个答案。原则关系继续使用方法论流程。按顺序推进的功能状态集中维护在[迭代进度](docs/iteration-roadmap.md)。

日常调用时，直接在 Codex 或 Claude Code 中说“用 decision-context 核对当前仓库的后端改动”，Agent 会按 Skill 指引调用 MCP 工具。一次调用的参数示例如下，实际目录和文件应由 Agent 根据当前任务填写：

```json
{
  "query": "事件处理与仓储职责",
  "repositoryPath": "/path/to/repository",
  "layer": "backend",
  "module": "server/src",
  "files": ["server/src/events/handler.ts"]
}
```

配套 [decision-context Skill](skills/decision-context/SKILL.md) 随安装包资源提供，可安装到 Codex 或 Claude Code 的 `skills/decision-context/SKILL.md`。它指导 Agent 在编码、评审和交接时核对适用范围、当前代码与替代关系；笔记中的指令始终只是历史证据。新工具需要使用新版 App 和 bridge；已有客户端会话可能需要重启或重新连接 MCP 才会刷新工具列表。

`consult_decision_principles` 核对已采纳原则（按文字和本机向量模型匹配，不调用生成式模型，不联网），与问题相关的用户偏好和想法另行标注返回，不当作原则；尚无可读原则时会明确说明，并提示使用上下文检索查历史记录。检索与原则核对均不自动建立原则采用关系，不替用户裁决相互冲突的历史结论。

## 方法论

“方法论”把 1 至 5 条已经记录实际结果并完成人工复盘的决策作为证据，调用当前已启用的 Qwen、API 或终端模型提炼候选原则。候选包含原则、适用条件、注意事项与证据摘要；可信度由 App 根据仍然存在的来源证据重新计算，不采用模型自报值。单条证据固定为低可信，至少三条完整证据跨两个项目且结果方向一致时才可达到高可信。

“新建原则”统一提供三种明确来源：人工编写、从复盘提炼和导入 Markdown。人工编写只要求填写标题、原则、适用条件和注意事项，不调用模型，也不会自动补造事实或建立证据关系；保存后仍是待确认候选，并单独标记为“人工录入”。人工候选可以稍后手动关联 1 至 5 条完整复盘证据并重新计算可信度；没有证据时只能在再次确认风险后作为待验证假设采纳。选择入口本身不会调用模型、写入候选或改变现有方法论。

事前核对与事后关联是两条独立链路。选择发生前，客户端 MCP 可以把尚未回答的问题、候选选项和有限上下文交给 App 做确定性文本匹配，最多返回 3 条已采纳原则及关联原因；结果只作为 Agent 当前分析的参考，不调用模型、不保存查询正文或逐次事件、不改变答案，也不自动认定用户采用了原则。选择完成后，补理由界面会再次对问题、已选答案、选项和有限上下文做本地匹配；只有用户明确点选的原则才会随决策保存，选择“稍后处理”并重启 App 后关联仍会保留。已经写下的预期结果也一样：选“稍后处理”或“跳过理由”时照样保存（稍后处理的在补完或跳过理由时写进笔记），不会因为理由没写完而丢掉。“分析”页展示不含正文的覆盖率、有帮助率和强匹配占比，并提供不落盘的本地试算与主动匿名评价；覆盖率只表示找到了候选原则，有帮助率也只代表主动反馈样本，二者都不是自动证明的准确率。

方法论内容较少时，原则列表会继续显示本地建设进度，而不是在第一条记录后留下无说明的空白。进度使用完整 SQLite 快照和全部方法论、实践资产 Markdown 计算已记录决策、完整复盘、待确认/已采纳原则与已采纳实践数量，不受决策库最近 200 条展示上限影响；同时把“复盘证据 → 原则沉淀 → 实践落地”状态和下一步操作放在同一页。审核、人工编写、继续提炼、补结果与复盘、导入 Markdown 都需要用户明确触发，读取进度本身不调用模型。

方法论页会把尚未被现有原则使用的完整复盘整理成最多 6 组“提炼建议”。分组只使用可重算的文本相似度、结果方向和项目覆盖度：相近且结果同向的复盘可以形成多证据组合，不相关或结果相反的复盘不会强行合并，单条证据明确标为探索性。建议只负责预选证据，查看建议不会调用模型；用户可以逐组生成，也可以在明确看到调用次数并确认后依次批量生成。批量结果只进入待确认列表，不会自动采纳或继续生成技能与流程。

“工作箱”是方法论页的常驻次级入口，把复盘素材、原则复验和关系核对集中展示，顶部只保留工作箱与新建原则两个操作。三条队列继续使用各自独立的确认和事实写入边界，不会因为打开或关闭工作箱而自动处理。“复盘素材”中的组合可以“稍后再看”，搁置状态以不含决策正文的 SHA-256 标识保存在 App 私有数据目录，跨重启保留并可随时恢复；出现新的完整复盘并形成新组合时仍会重新提示。已经生成过候选的证据无论候选后来被采纳还是忽略，都不会反复回到素材建议中。搁置、恢复和浏览均不调用模型，也不会自动建立原则、采纳或发布内容。

选择 1–5 条复盘证据后可以明确选择两条路径：“人工整理 · 0 次”直接进入人工归纳表单，“模型提炼 · 1 次”才调用当前生成模型。人工整理会在同一弹窗展示已选证据，并要求用户填写标题、原则、适用条件、注意事项和区分观察与归纳的证据摘要；保存后记录为“人工整理 / 不调用模型”，但仍保留真实来源编号并按证据数量、跨项目覆盖和结果一致性计算可信度。两条路径都只建立待确认候选，不会自动采纳、生成实践资产或发布客户端内容。

已有方法论也可以从最多 20 个本地 `.md` / `.markdown` 文件导入。每个文件最多 512 KiB，只读取用户明确选择的普通 UTF-8 文件，不跟随符号链接；结构化 Decision 方法论会保留可核对的来源编号，普通 Markdown 则从标题、原则、适用条件、边界与依据等章节建立候选。选择文件后只在主进程内存中建立最多保留 10 分钟的预检批次，不立即写入：界面逐条展示拆分结果、来源文件名、缺失边界、来源编号、完全重复和同原则可能重复项；可能重复项默认不勾选，只有用户明确提交的候选才写入。提交时会再次检查完全重复，预检批次只能使用一次。带编号或明确字段结构的长文可按同级章节拆成多条原则，每个文件最多 12 条、单次最多新增 60 条；普通章节不会被误拆。新导入记录会在 Markdown 中保留来源文件名和原内容（按 UTF-8 读取、去掉开头 BOM 后）的 SHA-256，不保存原文件路径；详情页可以核对来源，旧版记录则明确显示未记录文件名。缺少适用条件或注意事项时会显示“待补充”，完成补充前不能采纳。没有 Decision 复盘证据的导入候选始终标为“待验证”和低可信；关联证据时，App 会用本地确定性文本重合对最近最多 200 条完整复盘给出最多 5 条可解释建议，并支持按问题、选择、项目和复盘经验搜索。建议只负责排序和说明匹配字段，不会自动勾选；用户仍需手动关联 1 至 5 条证据。关联后 App 会重新计算可信度，但不会自动改写原则内容。没有证据时只有再次明确确认后才能作为假设采纳，不会伪装成经过结果验证的原则。

候选审核会同时展示有效证据、覆盖项目、证据来源和复盘结果方向，并用本地确定性文本分析提示高相似原则或包含对立行动信号的潜在冲突。用户可以把任意提示核对为“重复、冲突或无关”，补充最多 500 字说明，并随时修改或撤销；人工确认的冲突和重复在原则改写后仍会保留，“无关”则不再阻断质量检查。“关系核对”会跨待确认与已采纳状态整理全部未处理关系、按冲突优先并对称去重，在一个连续比较队列中逐组保存或跳过，不需要反复进入原则详情，也不会调用模型。关系结论只作为独立、对称的 Markdown 事实保存，不会自动合并、覆盖或删除原则；未核对或仍有风险的关联会让采纳经过第二次明确确认。来源决策缺失的候选不能采纳。来源决策默认折叠，用户可以按需展开核对原始选择、实际结果和复盘结论。

当图谱中的两条已采纳原则已经人工确认为“重复”时，可以成对聚焦并开始建立人工合并草案。编辑器允许继续加入最多 3 条原则，但候选必须与当前组内每一条原则都已经单独人工确认为“重复”；系统不会用 A≈B、B≈C 推断 A≈C。已经与组内至少一条原则确认重复、但仍缺少其它成对结论的候选会单独显示“已确认 / 待核对”数量；只要没有既有冲突或无关结论，用户就可以留在同一弹窗逐对判断并填写可选说明。每次判断立即保存为原有独立关系事实，全部缺失对都确认为重复后才自动加入；任一对判为冲突或无关都会停止加入，不会打开第二层弹窗或继续猜测。单次合并因此限定为 2 至 5 条来源，并在顶部并排保留全部来源、显示数量上限和完整成对关系要求；统一内容与证据核对使用双栏工作区，只允许从整组已有的完整复盘中选择 1 至 5 条证据，全程不调用模型。新草案在 Markdown 中追溯全部来源，默认仍是待确认候选；采纳时会再次核验全部来源仍为已采纳，并且最多 10 个成对重复结论都仍然成立。采纳合并原则后可以进入“整理来源”：App 会先列出仍引用任一旧来源的技能与流程，每次仅在用户明确点击后调用一次模型生成来源迁移草案。已采纳资产的内容、稳定标识和客户端发布在草案审核前保持不变；明确采纳草案后才切换到合并原则。只有不存在活动引用时才允许把整组来源作为一次有界批处理标为“已归档”；任一写入失败会自动恢复已经写入的来源，整组归档也可以恢复，不会撤销已经独立审核过的实践资产更新。

未完成的合并编辑会在输入变化 500 ms 后保存一份本机私有草稿；关闭窗口或选择“稍后继续”时会先完成保存，原则页随后显示紧凑的“继续合并”入口。恢复前 App 会重新读取当前方法论，确认 2 至 5 条来源仍存在且均为已采纳、组内每一对仍明确为重复，并且同组没有现成的待确认或已采纳合并候选；失效草稿只显示原因和丢弃入口，不会反向改写状态、自动补关系或建立候选。恢复时不再可用的证据会被移除并要求重新确认。明确丢弃或成功创建候选后会删除草稿。

方法论笔记保存在 `<Obsidian 仓库>/Decision Journal/principles/`，人工关系保存在相邻的 `principle-relations/`，继续以 Markdown 作为唯一事实来源。每条原则笔记保留来源类型、来源决策编号和创建请求信息；模型生成记录保留实际后端与模型版本，人工录入则明确记录“不调用模型”。每对原则只有一个规范化关系事实。界面只展示必要的来源内容，不向渲染进程暴露文件路径。Apple Foundation Models 当前只负责语义识别，不支持这类通用结构化生成；路由会自动继续尝试其它已启用后端。

已采纳或已归档原则的详情会汇总明确记录“采用过该原则”的历史决策，分别展示采用次数、结果回填数、完成复盘数，以及符合/优于预期、部分符合、低于预期和暂不明确的分布。采用记录可以按项目及“待结果、待复盘、已复盘、需关注”筛选；待验证摘要使用全部历史精确计数，即使明细只向渲染层返回最近 50 条，也会保留下一条待处理决策。点击摘要或任一采用记录会通过决策编号精确打开原决策，不受决策库最近 200 条列表上限影响。这个投影只表达人工建立的关联与复盘分布，用于发现原则的适用边界；它不把相关性包装成因果证明，也不会据此自动提高可信度或改写原则。

当已采纳原则出现“明确采用该原则后完成”的新复盘时，详情会提示建立人工修订候选。修订编辑器预填当前原则，并允许从原有证据和最新采用后复盘中明确选择 1 至 5 条；至少需要一条新增复盘，不调用模型，也不会把没有采用关系的其它决策混入证据。保存只产生待确认草案，原原则、历史决策关联和下游实践资产都不改变。明确核对差异并应用后，App 继续使用原原则编号，把当前内容完整保存为本地恢复点，再更新原则内容与证据；引用它的技能和流程只会进入“来源已更新”状态，不会自动重写或发布。原则详情最多保留最近 20 个完整恢复点，恢复旧版前也会先保存当前内容。

未完成的原则修订同样保存为单份本机私有草稿。关闭详情或返回详情前会先保存，原则页显示“继续修订”；草稿同时保存开始编辑时的来源快照，恢复时会重新确认来源仍为已采纳、没有现成修订候选，并重新读取采用后的完整复盘。来源正文没有变化时直接恢复；已经变化时则逐字段并排显示“开始编辑时、当前正式版本、未完成草稿”，未发生双向修改的字段确定性预选，真正冲突的字段必须由用户明确保留当前版本或草稿后才能迁移。迁移只把选择后的内容重建为当前版本上的本机草稿，不会改写正式原则或建立修订候选；不再可用的证据仍会移除。旧版草稿缺少来源快照、候选已经建立或新复盘已经失效时保持惰性，只显示原因与丢弃入口。明确丢弃或成功建立修订候选后会删除草稿。

方法论页的“复验”入口会把所有已采纳原则采用后的新增复盘集中成待核对列表，并优先显示出现偏差的原则。用户可以打开原决策、查看并建立修订草案，或明确确认这批结果下原则仍适用。确认只在原则 Markdown 中推进人工复验位置，不修改原则正文、可信度或内容更新时间，因此不会把下游技能与流程误标为来源已更新；已有修订草案时必须先处理草案，不能用确认操作跳过。这个收件箱不调用模型、不从文本猜测原则采用关系，也不把结果相关性解释为因果。

方法论页内的“分析概览”会按需读取完整的可重建 SQLite 快照，并在主进程用单遍本地聚合统计决策与项目数量、理由完整率、结果回填率、结果复盘率、预期/实际分布、最近 12 个有记录月份，以及项目和来源分布；预期/实际分布中的每一种结论都可以点开，在知识页列出以这个结论完成复盘的决策，便于集中回看“低于预期”的那些。聚合过程只读、无网络访问、不创建第二份数据库，内存只随项目、来源和月份分组数量增长。

分析页最上方是“周期回顾”（首页“最近决策”标题栏的“周期回顾 ›”可直接打开这里），可在近 7 天与近 30 天之间切换（今天及此前的自然日，与首页口径一致）：与前一个同长窗口对照新决策和完成复盘的数量，给出窗口内的理由补全比例（仍待补的几条可以直接在知识页列出、逐条补完；主动选择不记录理由的不算待补）和当前待复盘数量（与首页“需复盘”同一定义，点开回到首页复盘收件箱）；本期还有既没写预期、结果也没出来的决策时，读数下方会提示，“补写 ›”直接打开知识页的“待写预期”列表；“本期写下的经验”列出窗口内完成的复盘，结果不及预期的排在前面并展示当时写下的复盘经验（事先写过预期的，还会附上当时的预期），点开即进入该条决策；“反复出现的问题”把窗口内问题文字相同（忽略大小写、全半角、空白与句末标点）的决策归为一组，标出次数、涉及项目数以及答案是否一致，点开会在知识页按这个问题并排列出每一次决定；“本期用到的原则”按窗口内决策人工关联的次数列出已采纳原则，点开进入原则详情；另附窗口内的项目分布，点开某个项目会在知识页列出它在这段时间里的决策，项目作为可移除的条件显示在筛选栏里。回顾可一键复制为 Markdown，贴进周记或发给别人。回顾只统计本机记录，不调用模型。

方法论页内的“关系图谱”只读取已采纳原则，并用确定性关系把项目、来源决策、人工复盘结果与原则连接起来。双方都已采纳的人工“重复/冲突”结论也会作为原则间关系进入图谱，“无关”和仍处于候选状态的关系不会进入正式投影。界面支持按原则或项目搜索、按重复/冲突筛选、成对聚焦、直接打开原则详情，并从确认重复的成对视图发起人工合并草案。候选原则不会提前进入图谱；如果用户在 Obsidian 中移除了某条来源决策，原则笔记仍保留，界面会明确提示缺失引用，不会补造节点。图谱仍是 Markdown 与 SQLite 索引的只读投影；发起合并只新增方法论候选，不在图谱中维护第二份事实数据。

“技能与流程”可以从 1 至 5 条已采纳原则建立可审核草案。用户可以选择人工编写或明确发起一次模型生成：人工路径只预填来源原则中的适用条件和失败边界，不调用模型，也不会虚构执行步骤与验收标准；两条路径都只产生待确认候选，并保留来源快照和创建方式。技能草案使用独立目录中的 `SKILL.md`，工作流草案使用普通 Markdown；两者都包含使用条件、操作步骤、验收检查、失败处理和来源原则。用户可以查看、修改、采纳或忽略，未采纳草案不会被当作正式实践资产。新生成或人工校对的资产会在笔记元数据中保留当时的来源快照；界面据此逐字段展示原则标题、内容、适用条件、注意事项和可信度变化。来源被删除或取消采纳时则标为“来源不可用”。旧资产没有历史来源快照时仍可按更新时间识别变化，并会在第一次保存或重新生成后建立对比基线。

技能保存在 `<Obsidian 仓库>/Decision Journal/skills/<稳定标识>/SKILL.md`，工作流保存在 `<Obsidian 仓库>/Decision Journal/workflows/`。已采纳资产每次编辑、应用替换草案或恢复旧版前，都会在 App 数据目录保留修改前内容；详情最多展示最近 20 个恢复点，支持逐字段比较和再次确认后恢复，恢复前的当前内容也会自动形成新恢复点。来源快照属于内部审阅元数据，不会写进客户端 Skill 包。已采纳资产可以由用户在详情中明确发布到 Codex 或 Claude Code；两类资产都以客户端支持的 Skill 包写入各自的 `skills/<稳定标识>/SKILL.md`。发布前会识别同名占用、外部修改、目标丢失和符号链接风险；覆盖必须再次确认，原内容和每次 Decision 发布版本都可安全回滚。来源更新时，重新生成只创建替换草案，不修改原资产或已安装客户端内容；用户采纳替换草案后才更新原资产，并需再次明确发布。来源不可用或尚未确认更新时会暂停新发布，但已有版本仍可检查和回滚。Decision 不会后台自动发布，也不会在目标被外部修改后强行回滚。

## 首次使用

1. Windows 运行 Setup 完成安装；macOS 解压后将 `Decision.app` 放入 `/Applications`。然后启动一次。
2. 应用会优先读取 Obsidian 的最近使用仓库；未发现时使用 `~/Documents/Decision Vault`。还没有任何决策时，首页显示“开始使用 Decision”：接入 Claude Code 或 Codex、记下第一条决策（⌘N）、选择回答模型、连接代码平台四步，已完成的步骤会打勾，每步都能直接跳到对应页面；第一条决策记下后换回平常的首页。
3. 在“接入”页查看 Claude Code 和 Codex 的连接状态。
4. 在“模型”页确认当前识别引擎；如需 API 或终端后端，在后端列表中配置、测试后再启用。
5. 如有需要，在“设置”页更换 Obsidian 仓库；同一行的“在文件管理器中显示”会打开当前仓库目录（备份只需要这一个目录，索引可以从它重建），目录已被移走时按钮会明确说明而不是静默无反应。
6. 在“接入”页点“安装或修复”。
7. 重新打开 Claude Code 和 Codex，使新的被动 Hooks 与 MCP 接入生效。

安装会：

- 移除旧的 Decision MCP 配置，再注册当前事前核对与明确主动记录工具；
- 移除带 `DECISION_HOOK=` 标识的旧处理器；
- 为 Claude Code 的 `AskUserQuestion` 安装被动 `PostToolUse` Hook；
- 为 Codex 的 `request_user_input` / `AskUserQuestion` 安装被动 `PostToolUse` Hook；
- 为两个客户端安装被动 `Stop` 与 `UserPromptSubmit` Hook，用于普通文本提问的本地兜底；
- Windows 上 Hook 与 MCP 都经 cmd 运行 `decision-bridge.cmd`：Claude Code 的 Hook 不经 shell 直接启动（它的 shell 是 Git Bash 或 PowerShell，跑不了 cmd 语法），Codex 的 Hook 命令行在 PowerShell 和 cmd 下读法一致；旧版只按 cmd 语法写的 Hook 会显示为需要修复；
- Windows 安装版的 Hook 与 MCP 指向安装根目录下的 `decision-bridge.cmd`（`%LOCALAPPDATA%\Decision\decision-bridge.cmd`）：每次启动由正在运行的版本改写为转到它自己的 bridge，升级后不必重新连接；从更早的版本升级上来时，接入页会提示重新连接一次；
- 保留其它工具已有的配置、顺序和未知字段；
- 直接清理旧版 Decision 入口，并以原子写入替换为当前配置，不创建旧版备份。

安装按客户端分别进行：每个客户端先通过它的官方命令配置 MCP，成功后才以原子写入替换它的被动 Hooks 并升级接入标记。没有安装的客户端会跳过并说明；一个客户端失败或配置文件读不出来，不影响另一个接入，只有两个都没接上时才整体报错。从 Finder 或程序坞打开 App 时，会先读取登录 shell 的 PATH 来找到 `claude` 和 `codex`。原则核对工具保持只读；主动记录工具只接收用户明确表达的结构化记录。旧 MCP 不存在时移除命令会正常忽略；如果因权限、CLI 或配置错误而失败，安装会报告错误且不会把 Hooks 标记为已升级，可直接重试修复。Claude Code/Codex 的原生问答行为不会被改变。

设置页不会显示或持久保存运行令牌。令牌只存在于仅当前用户可读的运行描述文件中，并在 App 正常退出时删除。

## 理由流程

- 理由面板、待处理和设置页都在同一个主窗口里切换：窗口默认 1160×760（不超过当前显示器工作区，最小 860×620），在鼠标所在的显示器上居中，第一次显示时最大化。
- 待处理面板打开一次后会连续推进队列：忽略直接显示下一项；记录后先补充、跳过或稍后补充理由，再自动返回下一项；最后一项完成后关闭。
- 待处理面板把决策原文、用户回答和问题相关上下文作为主体，顶部只保留来源、项目、进度和“稍后”；相关选项中你选的那一项会标出“已选”（两个选项文案相同时不猜，都不标）。
- 设置页、待处理面板与理由面板共享同一套 Light/Dark 玻璃层；macOS 26 使用原生 Liquid Glass，旧系统使用 vibrancy 与 CSS 模糊降级。
- 原生问题与答案只读，不能在 Decision 中重选。
- 有相关上下文时默认显示两行预览，可展开查看“任务背景”和“约束与考虑”；截断会明确标记。
- “完成”分别保存自由输入理由原文和结构化判断依据；只选判断依据时不会伪造理由原文。
- 在理由面板任意位置按 ⌘+Enter（Windows 为 Ctrl+Enter）等同于点击“完成”；没有可保存内容时快捷键不生效。首页“补充理由”弹窗同样提供“判断依据”多选，但必须写下理由原文才能保存：待补理由写回 Markdown 时记录的是用户原文，只凭依据补全会让笔记声称存在一段从未写下的原文，主进程也会拒绝这种补全；其中同一快捷键等同于“保存补充理由”。
- 待处理面板中 ⌘+Enter / Ctrl+Enter 等同于“记录并补充理由”；“主动记录”表单填好必填项后，同一快捷键等同于“保存记录”。
- 侧边栏各页（首页、问答、知识、评审、方法论、设置）按从上到下的顺序对应 ⌘+1…6（Windows 为 Ctrl+1…6），⌘+, 直接打开设置；处理当前决策时导航锁定，这些快捷键同样不生效。按 ? 或点击侧边栏底部“键盘快捷键”可随时查看速查表。
- 快速跳转、引用跳转、主动记录保存后，会把你带到一个不是你自己点开的页面；这时侧边栏顶部出现“返回<原页面>”，点它回到原处。自己点侧边栏切页即视为重新决定位置，该入口随之消失；处理当前决策时不显示。
- ⌘+N（Windows 为 Ctrl+N）或点击侧边栏底部“主动记录”，可以在任意页面记录决策、偏好或想法；保存后直接跳到这条新记录（决策进入决策详情，偏好与想法进入“偏好与想法”并高亮）。处理当前决策时与导航一同锁定。
- ⌘+K（Windows 为 Ctrl+K）或点击侧边栏底部“快速跳转”打开跨库跳转：一个输入框同时检索决策、偏好与想法、Obsidian 笔记、原则，以及本机的问答会话与评审记录，按分组显示，↑/↓ 跨分组移动，Enter 打开决策详情、跳到“偏好与想法”并高亮该条、在 Obsidian 中打开笔记，或跳到原则详情（自动切到该原则所在的状态筛选）。原则在打开弹窗时读取一次并在本地匹配，决策、偏好想法与笔记各自走既有检索；决策先按关键词检索，关键词无结果且查询至少 2 个字符时再补一次本机语义检索，语义或综合命中的决策与笔记标为“语义命中”。其中任何一路不可用时其余结果照常显示，并标明哪一类缺失。输入“回顾”“待复盘”“待补”“待写”这类指名页面的词时，最上方的“页面”分组还会给出“周期回顾”“需复盘”“待补理由”“待写预期”，Enter 直接打开回顾或已筛好的知识页列表；“复盘”“理由”“预期”这类常见词不会触发，回车仍打开第一条记录。本机保存的 PR 评审与问答记录也在最下方的“评审”分组里（按 PR 标题或 `仓库#编号` 匹配，没输入时列最近 5 条），打开后跳到评审页的“历史评审”并选中这条。问答页的会话在它上面的“问答”分组里：按会话名称和其中问过的每一个问题匹配（会话名只是截短的第一个问题），行尾写明问了几个问题和最后更新的日期，空会话不列；打开后切到问答页并换到这段会话，回答生成中时留在当前会话。处理当前决策时与导航一同锁定。
- “稍后处理”只进入私有本地待补理由队列；跨 App 重启恢复，补完理由时才写入 Obsidian 和 SQLite。
- “跳过理由”明确保存为已跳过。
- 点击底部“不记录此次决策”即可直接删除暂存正文，不写 Markdown 或 SQLite；无需勾选或再次确认。
- Markdown 写入失败时，候选和理由保留在内存及私有恢复日志中，并提供重试；App 重启后会继续该处置。
- SQLite 更新失败时，Markdown 仍视为保存成功，设置页提示重建索引。

## 集成与诊断

实际配置位置：

```text
~/.claude/settings.json
~/.codex/hooks.json
```

设置了 `CLAUDE_CONFIG_DIR` 或 `CODEX_HOME` 时，分别改用 `$CLAUDE_CONFIG_DIR/settings.json` 和 `$CODEX_HOME/hooks.json`，与客户端自己注册 MCP 的位置一致。配置文件是符号链接（例如由 dotfiles 工具管理）时，写入链接指向的文件，保留链接本身和原有权限。App 被移动或升级到新位置后，接入页会显示“需重新连接”，点“安装或修复”即可；Windows 安装版升级时不再需要。

打包后的桥接程序支持以下命令；Windows 安装版使用安装根目录下的 `decision-bridge.cmd`（`%LOCALAPPDATA%\Decision\decision-bridge.cmd`），macOS 使用下面的入口：

```bash
"/Applications/Decision.app/Contents/Resources/bridge/decision-bridge" install --dry-run
"/Applications/Decision.app/Contents/Resources/bridge/decision-bridge" install --apply
"/Applications/Decision.app/Contents/Resources/bridge/decision-bridge" doctor
```

Hook 命令从 stdin 读取客户端事件，不向 stdout/stderr 输出业务内容，并始终以成功状态放行原生流程。

## 隐私与恢复

- SQLite 异常：App 会隔离损坏文件；可以在设置页从 Markdown 重建。
- 待处理：菜单栏和首页显示实时数量；选择“记录并补充理由”后才进入正式理由流程。点击“稍后”或关闭面板不会消费当前项，再次打开会从最早未处理项继续。
- 理由恢复日志异常：设置页会单独提示读取、损坏或隔离故障；重建 SQLite 不会清除此告警，原始捕获事件继续留在待处理队列。
- 未完成表单：人工原则、证据整理、实践资产、合并编辑和原则修订各最多保留一份本机草稿；文件与目录仅当前用户可读。合并与修订草稿包含未完成正文、来源编号和所选证据编号，不写入 Obsidian、SQLite、客户端或模型服务，只有明确创建候选后才进入正式知识生命周期。
- Obsidian 外部编辑：App 根据内容哈希重新索引，不覆盖手工修改。读不出来的笔记（例如属性被改坏，或同一 ID 有两份副本）会在设置页和偏好想法列表里点名说明，修好后自动消失；用 Windows 换行或带 BOM 保存的笔记照常读取。
- 仓库目录丢失（被移走、改名或所在磁盘没接上）：启动时保留上次的索引并在设置页说明；新的决策、偏好想法、原则和实践资产不会写进凭空建出的空目录，捕获留在恢复队列，仓库接回后重试即可保存。
- 删除 App 不会删除 Obsidian 决策笔记。
- Decision 的持久化业务数据、调用记录和凭据只保存在本机；用户显式启用 API 或 CLI 模型后端后，裁剪后的当前问答会发送给所选服务商并受其数据政策约束。
- 当 Codex 原生 `request_user_input` 未发布 `PostToolUse` 时，`Stop` Hook 最多读取本地 transcript 尾部 64 KiB，只配对同一 turn 内该工具的调用参数和成功回答。
- 普通文本识别优先使用 Hook 直接提供的最后一条助手消息；缺失时从同一受限尾部提取最近用户任务和最后一条助手文本。
- 规则评分器可以识别没有问号的选项列表、确认请求、短编号回答、肯定/否定和“先 1 后 3”一类组合顺序；也识别以推荐收尾的设计问答——`问题 N` 加逐条选项、最后一段是“我建议 C”而不是问句，选项自带的字母或编号即回答时要打的那个标识。语义模型补充改写回答、隐含选项、跨句指代和“回答后继续追问”的混合回答。
- Apple 与 Qwen 都在本机推理；Hook 不加载模型，Qwen 不创建本地网络监听，Apple helper 只使用私有 stdin/stdout JSON Lines。API / CLI 后端默认关闭，只有用户明确启用后才发送裁剪后的当前问答。
- 只有 LLM 把决策交给用户并停下来等待、且下一轮回答相关时才会采集。状态说明、客观资料请求、代码、日志、引用、反问、LLM 自己作出的决定和无关新任务会被丢弃。
- transcript 中更早的历史、未配对工具输出、transcript 文件本身及其路径不会写入暂存事件、Markdown 或 SQLite；完整 transcript 不会发送给 App。
- 服务只监听 `127.0.0.1` 随机端口，并要求每次启动生成的随机令牌。
- Electron 渲染进程启用沙箱和上下文隔离，禁用 Node 集成和外部导航。

## 本地数据迁移

当前产品只使用 `Decision` 应用数据目录、`decision` MCP 服务、`decision-bridge` 入口和 `DECISION_` 环境变量，不再保留旧品牌别名或自动目录回退。已配置的 Obsidian Vault 路径继续使用；全新安装默认使用 `~/Documents/Decision Vault`。

早期格式的笔记应在升级前完成一次性标记迁移。`node scripts/migrate-markdown-markers.mjs --vault PATH --prefix PREFIX` 默认只预览；确认来源前缀后，增加 `--apply --backup OUTSIDE_VAULT_DIRECTORY` 才写入。工具将原文件和校验清单备份到 Vault 外部，只替换结构标记，并拒绝覆盖预览后变化的文件。旧应用目录和未处理队列应完整归档，不删除或自动合并重放。迁移后的索引可从 Markdown 重建。

## 当前限制

- `v1.1.0` 默认发布 Windows x64 和 Apple Silicon macOS，不包含 Windows ARM64、Intel macOS、Linux、应用商店或自动更新。Windows 为 unsigned，macOS 为 ad-hoc 且未公证；未来可以在不改变制品契约的前提下增加 Authenticode 或 Developer ID，但当前免费发布不会因缺少证书而阻断。更新继续由用户从官方 GitHub Release 手工下载；
- 首次修改 Hook 集成配置后通常需要重启 Claude Code/Codex；模型后端排序、启停和路径配置不需要重装 Hooks；
- 远程 API 与 CLI 后端可能消耗额度或产生费用；服务端保留策略由对应提供商和账号配置决定；
- 识别器会从常见编号列表和经过原文定位的模型建议中恢复选项；无法可靠提取时答案仍按完整自由输入保存；
- 本地模型用于降低漏报，但不会消除所有语义歧义；不能由模型独立触发的样本会进入中置信待处理队列；
- Vault 笔记检索当前只覆盖一个已配置 Vault 的 Markdown 正文，不索引 PDF、图片、音视频、Canvas 或其它附件，也不提供多 Vault 聚合；基于同一索引的问答在「问答」页，检索页本身只做检索；
- 当前 64 条完全合成、脱敏的回归集用于确定性基线检查；正式调整路由阈值前仍需积累至少 500 条分层、脱敏且留有保留集的真实标签语料；
- 预期/实际复盘、决策实际采用的原则、方法论采纳和技能/工作流采纳目前都由用户确认；人工录入或 Markdown 导入的原则不会自动获得复盘证据，没有证据时只代表待验证假设；事前核对依赖 Agent 按接入说明主动调用只读 MCP，目前不能强制所有原生提问在提交前暂停，也不能证明建议影响了最终答案；匿名质量评价依赖用户主动表达并受自选择和小样本偏差影响，不保存正文也意味着无法事后逐条审计，当前只用于发现明显的阈值问题，不会自动调整匹配规则或当作准确率；原则采用后的结果分布只说明人工关联下的相关性，不能单独证明原则导致了结果，也不会自动调整可信度；方法论质量检查只自动识别可解释的文本高相似和对立行动信号，可能存在漏报或误报；人工关系仍只保存两条原则之间的重复、冲突或无关结论，多来源合并限定为 2 至 5 条且要求组内每一对都已明确确认重复，不会自动推断关系组；实践资产来源迁移仍需逐项生成和审核草案，尚未提供模型语义聚类、多原则关系组或自定义图谱边；批量分析仍是确定性聚合，关系图谱只表达已确认的项目、来源决策、结果、原则以及成对人工关系；客户端发布目前只支持本机 Codex 与 Claude Code 的 Skill 目录，不会自动发布，也尚未提供跨设备同步、批量发布或第三方客户端适配；提炼分组仍使用确定性文本重合而非语义嵌入，可能漏掉表达差异很大的相关内容；事前/事后原则核对与导入证据匹配会在文本重合之外补充本机向量召回，向量不可用时退回纯文本重合，语义补充项标为“语义相近”、不计入强匹配、也不展示共同用词；匹配建议不会自动建立事实关系，用户仍需手动选择；Markdown 长文只按明确的同级编号或字段章节确定性拆分，不会猜测松散段落之间的语义边界，外部文字也不会自动视为复盘证据；
- 实践资产历史最多保留每个资产最近 20 个 App 修改前恢复点；直接在 Obsidian 中产生的外部版本不会被持续监听并逐次归档，但下一次通过 App 修改前会先捕获当时的外部内容；
- Electron Forge 的 Vite 插件仍属于实验性接口，依赖版本已锁定并纳入打包冒烟测试。

## 开发验证

```bash
npm run check
npm run quality
npm run report:semantic
npm run make
npm run smoke
npm run release:local
```

`npm run check` 是日常质量门禁，依次运行类型检查和完整自动化测试。`npm run quality` 是 CI 唯一通过入口，在 `check` 后继续执行严格语义门；`npm run report:semantic` 只生成非阻塞的确定性规则基线。`npm run check:semantic` 未达到 high precision ≥ 95% 且 high + medium recall ≥ 90% 时返回非零状态。当前 64 条合成基线已经通过该门禁，但它不替代至少 500 条分层、脱敏、带独立保留集的产品激活评估。`npm run release:local` 会在质量门之后重新制包、运行隔离冒烟，并生成当前平台主制品的 SHA-256 与 schema-v2 清单。正式发行还会先执行 `npm run audit:runtime`，并要求 GitHub 原生 Windows 与 macOS 任务都通过后才一次性创建 Release。

显式使用已启用的本地客户端 profile 评估并统计后端延迟和 Token：

```bash
npm run evaluate:semantic -- --provider builtin-codex --report-only
npm run evaluate:semantic -- --provider builtin-claude-code --report-only
```

这两条命令会真实调用对应服务，可能消耗额度；普通测试与默认评估不会调用它们。

`npm run smoke` 使用隔离的临时仓库启动打包 App，通过真实的 `Stop` / `UserPromptSubmit` 被动 Hook 验证受限 transcript 读取、语义配对、模型不可用降级、明确选择的自动捕获、理由提交、Markdown、SQLite 重建和运行文件清理；混合回答的人工复核边界由单元与集成测试覆盖。冒烟不接触真实 Obsidian 数据，也不要求下载 Qwen 权重。

通过 `npm run check`、`npm run build` 和 `npm run smoke` 后，Apple Silicon macOS 可以使用仓库中的本机安装脚本更新 `/Applications/Decision.app`：

```bash
python3 scripts/install-local-macos.py          # 仅显示源与目标，不替换
python3 scripts/install-local-macos.py --apply  # 校验、替换、重启并检查健康；失败自动回滚
```

替换过程中临时保留旧 App 用于失败回滚；新 App 启动并通过健康检查后自动删除旧版和临时目录，不保留安装备份。已有客户端 bridge 会话保持运行，新工具列表在重新连接 MCP 或新会话中生效。

## PR 列表与评审

侧边栏「PR 评审」直接展示代码平台上的 PR／MR，无需复制链接。列表上方的搜索框除了编号、标题、仓库和作者，也匹配每条的状态文字，输入“未评审”或“之后有更新”就只剩还要看的 PR。评审里还有没撤销的 P1 时，状态写成“评审完成 · 4 个问题（1 个 P1）”，输入“P1”就能先找出这些 PR；P1 被复评撤销后不再计入。列表每一条都是标题在最上，下面一行小字是仓库、编号、作者和更新时间，再下一行是状态：没撤销的 P1 用强调色标出，之后又有更新的在这一行右侧标出。历史评审列表同样排法，第二行是 PR、提交、时间和模型。平台连接方式参考 `code-meeseeks`：接入层统一处理认证、发现、分页和固定提交读取，pi 评审不依赖某个托管平台或 CLI。

点击评审页的文件数量或「查看 PR 详情」可打开目录与文件查看器。目录支持路径搜索与拖动调宽；变更视图使用 [react-diff-view](https://github.com/otakustay/react-diff-view)，支持 Unified 与 Side-by-Side，并记住展示方式。「文件内容」按需读取源提交或目标提交的完整文本，不调用模型；大文件分段显示，二进制和不可用内容明确提示。所有读取绑定评审记录中的提交 SHA，读取期间版本变化会拒绝混用；若历史记录的版本已无法重新获取，会提示重新从 PR 列表读取最新提交。平台单次响应仍受 2 MiB 上限约束。


1. 在「设置 → 链接」中点击「新增链接」，添加 GitHub、GitLab 或 Bitbucket Server / Data Center，填写名称、服务地址和访问令牌。浏览和 AI 评审仅需读取权限；手动提交评审、发布评论或合并需要相应写入权限。支持 GitHub Enterprise 与 GitLab 自建实例；可填写实例根地址或 API 基址。GitHub 需要读取 PR 与仓库内容，GitLab 需要 `read_api` / `read_repository`，Bitbucket 需要仓库读取权限。无需安装 `bitbucket-cli`。打开链接页或保存链接后，会用每个链接自己的令牌向平台确认一次身份（GitHub / GitLab 读取当前用户，Bitbucket Server 读取响应头里的登录账号），显示“已连接 · 账号 …”或平台给出的失败原因（如令牌失效的 HTTP 401、无法访问地址），也可以点「检查」重新确认。
2. 选择连接，列表自动读取「待我评审」的开放 PR；可切换「我创建的」，或查看已合并的「我评审过的 · 已合并」「我创建的 · 已合并」，并可刷新和加载更多。连接失败与空列表分别显示。点击条目加载描述、文件与源提交快照。
3. 选择已启用的模型，可补充关注点，再点击「开始评审」。远端模型会接收读取的代码和相关决策摘录；模型凭据、代理与留痕沿用现有设置。Apple 分类后端不可选。
4. 「评审过程」逐条显示模型调用、读取 diff／源码、决策检索、重试和结果生成；同一动作会从进行中更新为完成／失败，展开可查看动作或结果摘录。切换页面不丢失正在运行的评审，完成、失败或停止后仍可回看过程，并与报告一起导出 Markdown。

评审页标题行右侧提供“批准”“需要修改”和“合并”。点击后会重新读取平台状态并展示源/目标分支与提交，用户确认才提交；从评审记录里批准或合并时，这份评审若还有没撤销的 P1 问题，确认弹窗会先说一句“还有 N 个 P1 问题没有撤销”，不拦着操作；提交前再次检查提交和分支，合并仍由平台校验权限、分支保护和检查结果。GitHub 的“需要修改”要填写修改意见，并支持选择 Merge commit、Squash 或 Rebase；Bitbucket 使用带 PR 版本的参与人状态接口，不发布已有草稿评论，需代理保留 X-AUSERNAME 以识别当前账号；GitLab 的“需要修改”使用 mergeRequestRequestChanges GraphQL 接口，服务器不支持时明确报错，不以撤销批准替代。GitLab 与 Bitbucket 的合并方式遵循平台项目设置。平台操作不会自动重试；网络失败导致结果不确定时应先到平台核对。

评审请求、执行过程、评审结果与后续追问在同一聊天流展示。可直接输入问题继续讨论，也可以用 `code-meeseeks`（pr-agent）同名指令：`/describe` 生成 PR 概览（类型、摘要、逐文件说明与评审关注点），`/improve` 生成附 diff 代码块的具体改进建议，指令后面可以跟补充要求，其它输入按原文追问，追问框工具栏的“PR 概览”“改进建议”按钮直接发送这两条指令且不清空正在输入的内容。读取 PR 后的准备页先显示 PR 描述（没有描述时提示可以先生成 PR 概览），再列出这次会带上的内容（变更文件、命中规则、已有评论、评审分组；变更文件一栏写明新增和删除多少行、改了几个测试文件，有代码改动却没动测试时写“没有改测试”，参照 pr-agent 的 Relevant tests，锁定和生成文件不计），再在「选择方式」里选完整评审、PR 概览或改进建议，输入框的主按钮随之变为“开始评审”“生成 PR 概览”或“生成改进建议”，关注点对三种方式都生效；PR 概览和改进建议各走独立流程（参照 pr-agent）：整个 PR 放得下就一次读完；放不下时，PR 概览分最多 3 块写逐文件说明（远端模型和 CLI 各块同时写）、再用一次调用汇总类型、摘要和关注点，逐文件说明表保证每个文件都出现（模型漏掉的列为“未单独说明”）；改进建议对变更最多的最多 3 组各提最多 3 条（远端同时进行），程序核对每条引用的原代码确实是本次变更的新代码（引用不存在的代码或只改旧代码的直接丢弃），再由一次复核调用对照 diff 按 0–10 打分（只加注释、文档、类型标注或日志的记 0 分），保留 5 分以上的最多 6 条并按分数排序，9 分以上标“高”、7 分以上标“中”；分块或复核失败时写明，不会整条回答失败。不评审直接生成时只携带 PR 描述、diff 与命中的评审规则，不带评审报告，结果存为「历史评审」里的一条问答记录（标为“PR 概览”或“改进建议”），同样可以继续追问和导出；支持停止回答、失败重试和 Markdown 回答，每条回答可一键复制为 Markdown（例如把 PR 概览贴进 PR 描述），也可以在弹窗里确认措辞后作为普通评论发布到 PR（不绑定代码行；只针对该记录的提交，PR 有新提交或已关闭时拒绝发布；发布过的回答标为“已发布到 PR”，不再重复提供），评审记录也能整份复制为 Markdown；追问使用所选模型，携带本次提交、评审报告、已保存的工具摘录和最近六轮对话，内存或本机快照缓存里仍有同一对提交时补充原始 diff（重启后也可以），不会重新拉取或修改 PR。追问、复评、PR 概览与改进建议的材料都按所选模型的长度装配（本机模型约 1.9 万字符，远端模型与 CLI 约 10 万字符，按转义后的实际长度计算）：放不下时，对话只留最近几轮、上下文截短、diff 给每个文件留一部分并写明还有几行没列出，不会因为请求过长被拒绝。模型调用、工具动作按执行顺序排列，同一动作的状态更新原消息，参数与结果默认折叠。每次评审的 PR 提交、模型、关注点、过程、报告、追问与草稿保存在本机，可通过「历史评审」回看、导出或删除；每次最多保留 2000 条执行记录。重启后的未完成评审标为中断，不会自动重跑。历史包含代码和决策摘录；本机存储已满时从最早的记录开始让位（每次让出五分之一），其余照常保存并提示让出了几条；连最新的记录都存不下时才提示保存失败，当前记录仍可导出。

平台令牌默认由系统加密保存在主进程私有凭据库，不回传界面或写入模型提示。连接配置只保存凭据引用，更换站点必须提供新的令牌。读取使用 GET，用户确认的平台操作使用 POST / PUT；请求限定在配置的 API 站点，不跟随重定向或服务端分页链接发送令牌；默认继承系统代理。移除连接只移除本机配置，不撤销服务器令牌。

AI 评审只读：不会自动发评论、批准或合并，不执行仓库代码，也不把模型意见自动写成新决策或采用关系。评审结果里的每条问题可以“转为评论”（沿用 `code-meeseeks` 的“AI 起草、评审者确认后发布”流程）：弹窗先重新核对 PR 的提交与状态，展示源/目标分支，评审者编辑措辞后以自己的平台账号发布到问题所在的变更行——GitHub 为 PR 行评论，GitLab 为带 diff 位置的 discussion，Bitbucket 为带行锚点的评论。评论框上方可以在“编辑”和“预览”之间切换，发布前先看 Markdown 排出来的样子（近似效果，以平台显示为准；切回编辑时草稿和撤销记录都还在），发布回答和评审摘要的弹窗也一样。发布成功的问题标为“已发布为 PR 评论”并记入本机评审历史，不再重复发布；平台拒绝（例如该行已不在 diff 中、GitLab 上的重命名文件）或结果无法确认时保留草稿并说明原因，不会改发为普通评论。

准备页和评审记录的标题行里，“PR 讨论”旁边的“在平台打开”会用浏览器打开这个 PR 在 GitHub、GitLab 或 Bitbucket 上的页面（地址由已添加的平台链接拼出）。点问题下方的 `文件:行号` 会打开 PR 详情并定位到那一行（在 diff 里高亮；该行不在 diff 中时提示切到“文件内容”，切过去同样高亮并滚动到这一行）。有评审记录时，PR 详情把这份报告的问题（按复评结果改写，撤销的不显示）像平台上的行内评论一样放在各自那一行的下面；变更目录里写明每个文件有几个问题，勾选“只看有问题的文件（N）”可把目录收窄到这些文件，diff 显示不到的问题列在代码上方，可一键到“文件内容”里定位。工具栏的“‹ 问题 i / N ›”按变更目录的顺序（目录在前、再按名称，同一文件按行号）逐个跳到上一个或下一个问题，跨文件时自动切换文件，首尾循环；键盘上按 N / P 效果相同（在搜索框里输入时不触发）。每条问题还可以“复评”（沿用 `code-meeseeks` 的复评闭环）：用所选模型只针对这一条、结合它所在文件的 diff、PR 描述与命中的评审规则重新判断，给出“保留”“取代”或“撤销（误报）”及理由。取代时附一条可直接发布的替代评论，之后“转为评论”即以替代文本起稿；撤销的问题划线显示并收起发布入口，可再次复评改判。复评结果随评审历史保存在本机；较早的评审会按原提交重新读取 diff，PR 已更新时明确拒绝。复评只读，不修改报告里的原问题，也不会自动发布。不同意某条问题时可以点“不采纳”，写下原因（可选）：它像撤销的问题一样划线收起，不再计入待处理、批量发布和问题清单；以后在同一平台连接下评审这个仓库时，最近不采纳的问题和原因（远端模型最多 20 条，本机模型 5 条）会告诉审查者不再报同类问题，核验时与之同类的候选打 0 分、移到“核验未通过的候选问题”（Greptile 用团队对评论的反馈过滤评论的做法）。准备页“这次会带上”写明有几条，点“查看”逐条列出（原因、来自哪次评审），可以就地撤回（同一问题在各次评审里的不采纳一起撤回）；在问题下面“撤回”也可以，删除那份评审记录时它的不采纳一并不再参考。模型仍然报出以前不采纳过的同一问题（同一文件、同一标题）时，标题旁标出“以前不采纳过”并写明当时的原因，再点“不采纳”会预先填好这个原因。发布成 PR 评论的问题则反过来：以后评审这个仓库时，最近发布过的问题标题（按发布时的文案，同样远端 20 条、本机 5 条；在这个仓库的任何一次评审里不采纳过的同一问题不算，撤回不采纳后恢复）会告诉审查者团队在意这类问题，有同类问题照常报告；核验时与之同类的候选不会只因为看起来是小问题而打低分，其它标准照旧。准备页“这次会带上”同样写明有几条。优先级有统一口径，写在给模型的系统提示里：P1 是合并后会直接造成安全漏洞、数据丢失或损坏、崩溃或主要功能不可用；P2 是特定条件下出错（边界输入、并发、失败路径、资源泄漏、明显的性能退化）；P3 是影响小或触发条件苛刻的缺陷，以及让后续修改容易出错的隐患；拿不准时取较低一级。报告里优先级显示为彩色标签（P1 强调色、P2 警示色、P3 灰），和 PR 详情里一致。报告开头的结论旁列出各优先级的问题数，已发布的评论数靠右；完成评审的文件数、模型调用与 token、命中的规则收在下面一行小字里，评审限制逐条带警示标记。问题超过 3 条且优先级不止一种时，列表上方有“全部 / P1 / P2 / P3”切换，可以先只看 P1；有问题已经发布为评论或被撤销后，还会多一个“待处理 N”，只看还没发布、也没撤销的，逐条处理时不用在已处理的问题里翻找，全部处理完时写明“都处理过了”。还没复评的问题有两条以上时，“全部复评（N）”会逐条复评它们（显示“正在复评 i / N”，停止按钮随时中断，任何一条失败就停下），适合在批量发布前先把误报筛掉。问题有两条以上还没发布时，问题列表上方会出现“批量发布为 PR 评论（N）”：勾选要发的（默认全部，已发布和撤销的不列出），核对平台状态后逐条发布到各自的行上，每条都与单条发布走同一套保护（只针对这次评审的提交、PR 有新提交或已合并、已关闭时拒绝）；任何一条失败就停下，说明是哪条、前面已发布几条，已发布的不会再次提供。需要改措辞的问题仍用单条的“转为评论”。在 GitHub 和 GitLab 上，新版本一侧的问题转为评论时可以“插入建议修改”：把这一行现在的代码放进一个 suggestion 代码块（光标停在行尾），改成修好的写法后发布，作者在平台上一键就能应用到这一行。评审记录“更多”菜单里的“发布评审摘要到 PR”会起草一条普通评论：问题统计加上每条问题及其 `文件:行号`（按复评结果改写，撤销的不列），改好后再发布。“追问”把这条问题的标题和 `文件:行号` 填进追问框（接在已经输入的内容后面）并把光标移过去，专门问这一条。“复制”把单条问题连同 `文件:行号`、PR 与提交复制成 Markdown（取代过的问题复制替代文本），方便直接交给 Claude Code 或 Codex 去修；“更多”菜单里的“复制问题清单”则把这份评审里所有没撤销的问题按同样格式一次复制（发布过评论的也在内，评论不等于修好了），开头写明 PR 和条数。某条问题其实说的是一条团队做法时，“记为决策”会打开主动记录，按这条问题起稿（标题、说明、项目，背景里写明 PR、位置和提交），存下后以后的评审就能检索到它。追问、PR 概览和改进建议的每条回答旁边写明这次调用的 token 数（填了单价时附折算金额）。

个人评审规则沿用 `code-meeseeks` 的格式：每条规则一个 Markdown 文件，正文是追加给评审的检查要求；frontmatter 用 `applies_to` 下的 `project`（GitHub owner、GitLab 命名空间或 Bitbucket 项目 key）、`repo`（仓库名）、`target_branch`（目标分支）三个正则限定范围（未加 `^…$` 时为包含匹配，区分大小写，都省略则适用所有 PR），`tools` 须包含 `review`（省略即为 review），`priority` 越大越靠前，`enabled: false` 停用。Decision 读取 `~/Library/Application Support/Decision/review-rules/` 和已有的 `~/.code-meeseeks/agent/rules/`（含子目录，也跟随符号链接，便于链接团队共享的规则仓库；跳过隐藏目录，最多 200 个文件），每次读取 PR 时重新加载，不需重启。命中的规则最多 20 条、合计 3000 字以内，按“Ruleset N”分段放入每组评审的上下文，追问、`/describe` 与 `/improve` 也按同样的规则回答；读取 PR 后在“本次想重点检查什么？”下列出命中的规则，评审结果与导出报告也会注明；旁边的“添加规则 / 管理规则”直接打开 Decision 的规则目录，目录为空时先放入一条未启用的示例规则。规则只增加检查要求，不能突破只读、证据与定位约束；正则写错或 frontmatter 无法解析的规则会被跳过并提示，而不是套用到所有仓库。

仓库自己的规范也会带上（Claude Code 的 `/code-review` 同样先找 CLAUDE.md）：读取 PR 时从源提交读根目录的 `CLAUDE.md` 和 `AGENTS.md`，跟随文件里单独一行的 `@路径` 引用（只写了 `@AGENTS.md` 的 CLAUDE.md 不重复列出），内容相同的只留一份，最多 4 份、每份 2 万字，同一提交只读一次并随 PR 快照缓存。准备页“这次会带上”写明读到了哪几份。它们和评审规则一起交给审查者、核验和复评（本机模型最多带 3000 字，远端 2 万字，放不下时只纳入前一部分并注明），但被当作写代码时给 Agent 的指引：只按其中能在代码上核对的约定检查，角色设定、协作流程、提交与构建发布说明不作为评审依据。读取失败时提示并在下次打开 PR 时重读；子目录里的规范暂不读取。

很多决定是直接在 PR 评论里做出的，不经过 Claude Code 或 Codex。评审页 PR 标题下的「PR 讨论」用这个 PR 所属「链接」的令牌，从新到旧翻页读取平台上的评论（与下文评审参考的来源相同；每页 50 条、最多 10 页，更早的评论没读完时会提示；Bitbucket 的评论被编辑过时取最新内容，已删除的不显示），逐条显示作者、位置和正文。历史 PR 同样可以补记：列表范围选「我评审过的 · 已合并」或「我创建的 · 已合并」，点开已合并的 PR 直接进入 PR 讨论，不读取 diff。评论里做出的决定可以点「记为决策」：打开主动记录表单，以评论正文作为「最终选择」、仓库名作为项目、PR 与位置作为当时上下文预填，标题应改写成当时要决定的问题；这类记录只能是决策，来源固定为「PR 评论」。保存后笔记的 `source_client` 为 `pr-comment`，`source_event_id` 保存评论在平台上的链接，并以链接作为去重键：同一条评论只对应一条决策，再次打开讨论时这条评论显示「已记为决策 · 查看」，可直达该决策。决策库可以按「PR 评论」来源筛选，详情里的「打开原评论」只在链接位于某个已添加链接的站点与路径之下时才交给系统浏览器打开。项目取仓库名，与之后评审同一仓库时的决策检索口径一致，PR 里定下的做法会作为历史决策回到下一次评审。Decision 不会在后台轮询评论，也不会自行判断哪条评论算作决定。

读取 PR 时还会取回平台上最近 20 条已有评论（GitHub 的行内评审评论、GitLab 的非系统备注、Bitbucket 的评论动态，每条截到 300 字，同样来自 `code-meeseeks` 的做法）：每组只带上组内文件的行内评论和不针对具体行的评论，并要求模型不重复已被指出的问题；规则与已有评论按每组剩余的上下文空间截取，不会让评审因上下文过大而失败。已有评论读取失败只提示，不影响评审。源码读取固定在 PR 源提交，支持 fork；Bitbucket 从目标仓库读取该提交，不额外要求作者个人 fork 的访问权限。平台返回 401、403 或 429 时停止本轮工具及模型调用，并显示对应原因；评审前后重新核对源与目标提交，引用的决策也复核版本。变化时明确提示重新核对。结论只能引用已经读取的变更行和实际检索到的决策。决策按目标仓库名和文件范围检索，历史选择、适用条件、例外及替代关系仍需结合实际代码判断；偏好与想法不进入这条检索链。深度评审的规则与决策审查者还会读到记在其它项目下的决策：排在本项目的之后，评审过程与报告里标为“其它项目（项目名）”，只有原文点名了本仓库、属于跨仓约定或通用工程做法时才作为依据，前端与后端的决策不互相套用；明确记录过范围、判定不适用的仍然排除。

当前一次最多 100 个文件、单次平台响应最多 2 MiB、40 条决策证据。完整评审参照 pr-agent 与 Claude Code 的做法，把整个 PR 当作一个整体来读，不再一个文件、一页 60 行地看（调研、评估与取舍见[PR 评审流程调研](docs/pr-review-research-2026-09-30.md)）：程序按所选模型一次能读的长度把变更装成“评审分组”——远端模型和 CLI 一组约 4.8 万字符，大多数 PR 一组就能读完；本机模型上下文只有 4096 token，一组约 4000 字符。同一目录的文件排在一起，测试文件紧跟被测文件；小文件整份合组，超过一组容量的文件在 hunk 之间切开（单个 hunk 就超过时才在 hunk 内切），最后一段与后面的文件同组。每组开跑前还会读取组内文件在源提交上的内容，给每个 hunk 上方补 3 行、再往上 10 行内找到所在函数或类的开头就补到那里、下方补 1 行（pr-agent 的动态上下文，改进建议同样补）；补进来的行只作上下文，问题仍只能定位到变更行；补上的行最多占这组容量的三成，按 hunk 的顺序补到放不下为止，之后的 hunk 只给原 diff（本机模型的小组也能补上一部分），源码读不到的文件按原 diff 评审并在报告里写明。PR 需要分几组读、所选模型不是本机模型时，先用一次调用写出整个 PR 的梗概（做了什么、按模块的主要改动、需要跨文件核对的地方），各组都带上它（Claude Code 同样先概括改动再评审）。每组还带上 PR 其它变更文件的清单（本机模型最多约 800 字符，远端约 8000 字符，列不完时写明还有几个），并可以用 read_diff 读取别组文件的变更、用 read_file 读源码核对：定义、调用或配置可能改在别的文件里，模型会先核对，而不是因为当前组看不到就报缺陷。每组最多 6 次模型调用（含重试）、各自最多 10 分钟，一组超时只记为这组没评完，其它组照常进行。远端模型和 CLI 最多 3 组同时评审（pr-agent 同样并行处理各块），结果仍按分组顺序汇总，执行记录里每一步标明来自第几组，PR 列表里写“评审中 · 已完成 k/n 组”（有组没评完时另外写出几组）；本机模型逐组进行，后一组带上前几组的结论。一组失败或 PR 有新提交时不再开始新的组，已经在评的组照常评完。准备页选完整评审时可以勾选“深度评审”（Claude Code 的并行审查者）：每组再派一位审查者，专门核对团队评审规则、仓库规范与仍然适用的历史决策，每条问题都要写明依据哪条规则或哪条决策（只是缺少结构化范围的决策，由它按原文、项目和适用条件判断是否适用，适用且变更行明确违背时照常报问题，只违背约定、没有直接功能影响的定为 P3；已被替代、有冲突或拿不准的仍只作待核对事项），和只找缺陷与安全问题的审查者同时进行，两边的问题一起去重、核验；模型调用约多一倍，报告和导出写明“深度评审”，两位审查者的结论在摘要里分开列出。开始前显示分组数（随所选模型变化）；可以随时停止。各组的问题汇总后先合并重复（同一文件同一侧 3 行以内、标题相同的算一个，保留更高的优先级和两边的决策引用），再逐条核验：按 Claude Code 的 0–100 置信度标准和它的误报清单（变更前就有的问题、看似缺陷其实不是、吹毛求疵、编译器或 lint 能发现的问题、泛泛的质量意见、有意为之的行为变化、不在变更行上的问题、规则或规范点名但代码里显式忽略的问题），把问题连同它附近的 diff（放得下时是整个文件的 diff）和它引用的决策明细交给模型打分（依据决策或仓库规范的问题与评审规则点名的问题同档计分，但要核对决策确实点名了它、适用条件在本次变更中成立），本机模型每次 3 条、远端每次 8 条（最多 3 次同时进行）；低于 80 分的不列入问题，放进报告下方可展开的“核验未通过的候选问题”，写明分数和理由，也写进导出的报告；核验调用失败时问题照样保留并提示“没能完成核验”。大 PR 可以只评审一部分文件：准备页“这次会带上”的文件卡片里点“选择文件”，按目录或逐个勾选，底部实时显示已选文件数和约多少组（单个文件就要占多组时标出“大文件 · 约 N 组”）；没选的文件不计为未完成，报告摘要写明“另有 N 个文件未选入这次评审”。这个选择按 PR 记住，PR 有新提交后，仍在其中的文件保持选中。再次评审或追问同一个 PR 时，若上次（同一平台连接下）填过关注点，输入框上方会写出“上次对这个 PR 的关注点：…”，点“沿用”即填入，不必重打。PR 在上次评审之后有了新提交时（从评审记录点“重新评审最新提交”），准备页会逐个文件比较这次和上次的改动（读取时给每个文件的 diff 算一个摘要），提示“有 N 个文件的改动变了或尚未评审”，并可一键“只评审这些”。上次评审用的就是同一个提交时，准备页会写明“上次评审（时间 · 状态）就是这个提交”：同一提交上的几次评审合起来还有文件没评审的（没选上或没完成），列出没评审的文件并提供“只评审这些”；都评审过的，提醒再评审会重新调用模型，但不拦着（换模型或关注点时正需要）。上次没评审到的文件（没选上或没完成）也算在内；只有目标分支前进、源提交没变时同样逐个文件比较：有的平台按目标分支重算 diff，改动可能随之变化；目标分支变动会让行号变化，这时所有文件都算变了，照常整份评审。重新评审完成后，报告里多一个可展开的“上次评审的 N 个问题”：同一 PR 上一次在别的提交上的评审找到的问题（撤销的不列，取代的用替代文本）。每次评审只对它完整评审过的文件说话：上一次若只评审了部分文件、中途被停止或有分组失败，它没评完的文件沿用更早那次评审的问题；已发布为 PR 评论的问题会一直跟下去（后来的评审被要求不重复已有评论，不说话不代表修好了），直到某次复核判定它已不存在。同一个问题被几次评审报过时只列最近那份报告：各次评审的报告按同一文件、同一标题（复评改写过标题的，新旧两个标题都算）、行号最近一一配对（一次评审的所有报告一起按距离从近到远分配，不会被先到的一条抢走），所以同一次评审里的两条同名问题始终是两个问题；任何一份报告发布过评论，这个问题就算已发布。复核结论先看这次评审自己的，其次是同一提交上重跑做的（读的是同一份代码，结论直接显示）；否则看其它提交上最近一次的结论，判为已不存在的不再列出。这次评审和同一提交上重跑的评审（读的是同一份代码）各自按就近配对，同一个问题以较新的那次为准：被撤销为误报的，之前的报告不再列出；这次评审自己又报出并保留的写“这次评审又报了”，不进摘要，也不再计入“有改动”和复核；重跑发布过的算已发布（后来的评审已经完整看过这个文件、不再提它的除外）。同一提交的另一次评审（早于或晚于这次都算）已经把某条问题发布成评论时，这次评审里最近的那一条（同一文件、同一标题、行号相差不超过 3 行，一条评论只对应一条）写明“同一提交的另一次评审已发布”，不再提供“转为评论”。问题不全来自最近一次评审时，标题写“之前评审的问题”，每条注明来自哪个提交；这次评审又报了之前报过的问题，标题后标出“之前也报过”。各条问题写明放到这次的提交上是什么情况——所在文件没改动的“应当还在”，文件已不在变更里的直接写明，有改动的可以点“复核有改动的 N 个”逐条交给所选模型判断（沿用复评，并告诉模型这条来自较早的提交、行号可能已经移动）：“仍然存在”“已不存在”，或“仍然存在，位置或表述有变”并附按当前代码改写的说明；当时已发布为 PR 评论的会标出来，方便去平台上关掉对应评论。复核逐条进行，可随时停止，结果随这次评审保存在本机。之后从“更多”菜单起草评审摘要时，会在末尾写上“上次评审的问题：已不存在 a 个，仍然存在 b 个”并逐条列出，只写有结论的（复核过的，或所在文件没改动的），这次又报出同名问题的也不重复写，方便作者知道哪些评论已经解决。导出报告和“复制为 Markdown”则带上整节“上次评审的问题”，没复核的也写明当前状态。PR 概览和改进建议不受影响，仍看整个 PR。锁定文件（`package-lock.json`、`yarn.lock`、`pnpm-lock.yaml`、`Cargo.lock`、`go.sum` 等）和 `*.min.js`、`*.min.css`、source map 不计入评审分组，也不放进 PR 概览、改进建议与问答所带的 diff（改为告诉模型省略了哪些文件）；准备页会列出这些文件，报告摘要写明未送模型的数量，它们不算作未完成。评审进行中可以照常点开别的 PR 或历史评审来看（一次仍只跑一个评审，别的评审、追问和平台操作要等它结束）：停止按钮只在正在评审的那份记录里，其它地方的输入框上方写明哪个 PR 正在评审，点“回到正在进行的评审”即可回去；评审在你看别处时结束，那里会写“「某 PR」评审完成 · N 个问题”，点“查看结果”即可回去。评审结束时如果窗口不在前台，会发一条系统通知说明结果与问题数（窗口在前台时不打扰）；“全部复评”和“复核之前评审的问题”跑完或停下时同样如此，点通知回到这份评审。在应用里切到别的页面时，侧边栏的“评审”入口会标出状态：评审进行中是一个跳动的强调色圆点，结束后换成绿色圆点表示有新结果，回到评审页后消失（悬停和读屏也会说明）。报告的统计行和导出的 Markdown 写明这轮模型调用报告的 token 总数；在模型页给所选后端填了单价时，一并折算成金额（与问答相同）。有调用失败或后端没报告用量时，写作“至少 … tokens”。一次模型响应可包含最多 3 个只读动作，完成报告须单独提交。每组最多重试两次模型调用或格式错误，仍计入调用上限并保留已读进度；取消不重试。模型服务限流（HTTP 429）时先等一会儿再重试（约 2 秒、4 秒，错开各组），梗概、核验、PR 概览和改进建议的单次调用也同样最多等两次；执行记录写明“服务限流，N 秒后重试”，等待中停止会立即结束。过程只展示实际动作和有界结果摘录，不展示模型隐藏思考。PR 快照按源/目标提交缓存：同一对提交的 diff 不会变，内存中保留最近 20 个 PR，并写入本机 `pr-review-cache` 目录（最多 60 个，重启后仍在；删除平台连接时一并清除它的缓存）。再次打开读过的 PR 时先立即显示缓存内容，后台只用 1 个请求核对提交是否变化——没变就直接可用，有新提交才重新读取 diff 并提示；核对不打断浏览，PR 列表与历史列表里可以用 ↑/↓ 逐个切换（历史列表的搜索也匹配评审问题的标题和追问过的问题）；PR 列表的更新时间变了而提交没变时只重读已有评论。PR 列表加载后会按顺序在后台预读前 5 个 PR，打开某个 PR 时再预读它后面的两个；列表里评审或问答过的 PR 若之后又有新提交或新评论（平台更新时间晚于记录时间），状态后会标出“之后有更新”，列表更新时间没变的不发任何请求，遇到 401/403/429 立即停止。同一提交的文件内容也只读取一次（评审翻页与文件查看器共用）。这与 `code-meeseeks` 的本地 git 镜像思路相同，但不复制整个仓库、不需要 git 凭据；单次响应仍受 2 MiB 上限约束，超大 diff 不会像本地 git 那样完整计算。评审过程只保存在内存，超过 30 分钟未核对的快照需重新读取，报告请主动导出。模型调用记录遵循既有正文开关和保留期。

没有发现问题不表示 PR 获得批准。未读文件、二进制或截断 diff、来源失败、上下文裁剪和步骤耗尽均保留不完整提示，评审不执行测试。实现使用锁定的 `@earendil-works/pi-agent-core` 0.86.1，通过结构化动作复用模型网关，不加载仓库扩展、自动发现的 Skill、shell 或文件写工具。

分组评审会把当前组完整 diff 固定放入每次模型请求，程序依次推进所有分组，模型仅补查需要的上下文并提交本组结论。重复或失败的补查会触发本组收尾；已完成的问题立即保留，后续失败或取消不会清空它们。界面分别显示已读取和已完成评审的文件，普通历史窗口裁剪不自动把结果标成“部分完成”；未完成分组、不可读文件或必要证据缺失仍明确标记。过程保留最近 2000 条事件，导出报告附最近 200 条过程；问题合并保留最多 200 条，超过上限明确提示。
