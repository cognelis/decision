# Decision

Decision 是一个面向 Windows 与 macOS 的本地优先决策平台。它不会替代 Claude Code 或 Codex 的提问界面；你仍在终端原生界面中完成选择。Agent 可以在提出重要选项或建议前，通过唯一的只读 MCP 工具核对本地已采纳原则；原生问答结束后，Decision 再通过被动 Hook 记录问题与答案，并独立弹出理由面板。

## 下载与构建

从 `v1.1.0` 开始，GitHub Release 默认同时提供：

- Windows x64：`Decision-<version>-win-x64-Setup.exe`；
- Apple Silicon macOS：`Decision-darwin-arm64-<version>.zip`。

两个公开制品都不要求购买商业证书：Windows 安装器为 unsigned，macOS App 使用 ad-hoc 签名且不做 Apple 公证。首次运行可能出现 SmartScreen 或 Gatekeeper 提示，请先核对同一 Release 中的 SHA-256，再按[发布说明](docs/release-notes.md)使用系统图形界面继续；不要全局关闭系统安全能力。

源码构建统一使用 Node.js `>=22.13.0 <26` 和 npm，推荐 Node.js 22 LTS。Windows x64 不需要 Xcode；Apple Silicon macOS 还需要 macOS 26 SDK 与 Xcode Command Line Tools。构建不需要 API Key、签名证书或维护者机器上的固定目录。

```bash
git clone https://github.com/cognelis/decision.git
cd decision
npm ci --ignore-scripts
npm run setup:electron
npm run check
npm run make
```

`npm run make` 会按当前系统生成对应原生制品：Windows 位于 `out/make/squirrel.windows/x64/`，macOS 位于 `out/make/zip/darwin/arm64/`。Qwen 模型权重不进入仓库或安装包；只有需要本地 Qwen 后端时才显式运行 `npm run prepare:model`。完整构建、校验和可选签名边界见[发布文档](docs/release.md)。

## 工作方式

1. Claude Code 或 Codex 使用自己的原生问答能力；
2. 在提出重要选项或建议前，Agent 可以调用 `consult_decision_principles`，读取最多 3 条与当前问题相关的已采纳原则、适用条件和注意事项；
3. 用户明确评价本次核对后，Agent 才可以调用 `record_decision_consultation_feedback`，把“有帮助 / 不相关 / 可能误导”匿名计入聚合校准；Agent 不得自行推断评价；
4. 原生问答工具完成后，`PostToolUse` Hook 优先静默复制结构化的问题、选项和答案；
5. 如果 Agent 用普通文本把选择、批准或方向判断交给用户，`Stop` Hook 会在本地分析最近一轮的决策请求，下一次同会话的 `UserPromptSubmit` 再与用户回答配对；
6. 桌面 App 在后台联合本地规则与本地语义模型评分：只有规则和模型一致时才会高置信进入理由流程，分歧或语义补召回进入“待处理”，低置信丢弃；
7. 捕获结果先写入仅当前用户可读的本地暂存队列，再尝试通知 App，Hook 始终静默成功退出；
7. Agent 不等待 Decision，可以继续运行；
8. 理由面板展示只读的问题、答案和相关上下文，允许完成理由、跳过、稍后处理或不记录；
9. 只有经过理由流程处置的内容才写入 Obsidian Markdown，SQLite 随后更新派生索引。

事前核对使用本地关键词与向量混合召回，不调用生成模型、不选择答案、不写入决策或原则采用关系，也不会打开主窗口；专用向量模型未准备时自动退回关键词匹配。App 不可用时工具明确返回不可用并放行原生流程。磁盘或投递异常同样不会改变 Claude Code/Codex 的原生 UI 或执行节奏。Decision 不注册问答工具、不注入 `SessionStart` 指令，`Stop` 也只作为观察者运行，不会阻塞 Agent。

## 数据模型

Obsidian Markdown 是唯一事实来源。默认目录为：

```text
<Obsidian 仓库>/Decision Journal/decisions/YYYY/MM/
```

每条笔记保存决策问题、候选方案、用户答案、任务背景、约束与考虑、采集来源、理由原文、判断依据、后续结果和人工确认的复盘结论。上下文只摘录最近用户任务与当前 assistant 轮次，合计最多 6,000 个字符，不保存完整 transcript。多问题原生问答会拆成多条记录，并通过 `batch_id` 和 `question_index` 保留关联。

SQLite 位于 Decision 的应用数据目录，只用于本地全文检索、语义向量、历史待补理由状态、内容指纹和其它可重建索引。删除 SQLite 后可以完全从 Markdown 重建；SQLite 更新失败不会删除已写入的 Markdown。新选择“稍后处理”的项目保留在私有 capture spool，不依赖 SQLite；当前 UI 会合并展示本地待补项与历史 Markdown 待补项。

未处置的捕获事件保存在私有 `capture-spool` 目录中。每个事件独立原子写入；用户提交理由后，处置内容也会先写入仅当前用户可读的恢复日志。选择“稍后处理”时保留事件和 `deferred` 标记，直到理由最终补完；完成、跳过或不记录后删除事件和处置正文，仅在 spool 中保留不含业务内容的 SHA-256 语义键、采集模式和时间回执，用于一次性跨模式去重。“稍后处理”和“不记录”都不会写入 Markdown 或 SQLite。

中置信结果保存在独立的私有 `candidate-spool` 中，最多 100 项并默认保留 7 天。它们在用户确认前不是正式决策，不写入 Markdown 或 SQLite；App 未运行时也不会因候选而被主动启动。忽略后删除候选正文，只留下不含业务内容的去重收据。

普通文本的完整问答对只在私有 `semantic-pair-spool` 中保留到分类和路由完成；未完成配对 24 小时过期，并由后续 Hook 至多每小时主动巡检删除，已配对内容最多保留 7 天。独立的 `capture-audit` 仅记录阶段、耗时、置信档位、稳定错误码和经过安装级随机盐 HMAC 后的指纹，不包含问题、答案、项目路径、原始会话 ID 或异常堆栈；默认保留 7 天且最多 5,000 条。

事前原则核对只在私有 `decision-consultation-metrics.json` 中保存聚合计数：调用、命中/未命中、强/弱匹配数量、客户端来源、匹配耗时，以及按“有帮助 / 不相关 / 可能误导”、来源和结果强度汇总的匿名评价。每次核对只在内存中保留最多 30 分钟的一次性随机回执，最多 256 个，评价后立即消费，App 重启即全部失效；回执本身不落盘。指标文件不保存问题、候选选项、上下文、项目名、原则编号、反馈回执或逐次调用/评价事件；指标写入失败也不会延迟或阻断客户端。方法论“分析”中的试算使用相同匹配逻辑，不计入真实调用次数；关闭弹窗后输入不会持久化，只有用户主动评价时才增加一个匿名分类计数。

模型判断另存到私有 `model-traces`：每个后端尝试一条，默认保留 7 天且最多 1,000 条。它不进入 Obsidian 或 SQLite；正文记录可关闭或从设置页清理。

## 本地语义识别

Decision 本质上做的是“采集 + 决策意图识别 + 问答关联 + 受限结构提取”。模型只参与语义判断和片段建议；Hook 配对、边界限制、原文定位、最终路由及持久化仍由确定性代码控制。

桌面 App 每次判断前按设置页优先级尝试所有已启用后端。首次运行默认：

1. Apple Foundation Models：macOS 系统自带、完全在设备端运行的系统语言模型；
2. Qwen3.5-2B：Apple 模型不可用时使用的本地 GGUF 备选；
3. 规则：所有模型都不可用、超时或异常时的无模型降级。

设置页还可以显式添加 OpenAI Responses、Anthropic Messages、OpenAI 兼容 API，或启用检测到的 Codex CLI / Claude Code CLI。它们默认关闭；启用后会把裁剪后的当前问答发送给相应服务商。一个后端失败时会留下独立调用记录并继续尝试下一项，不会影响 Hook 或原生客户端。

模型不能单独触发高置信弹岛。规则和模型一致为高置信；分歧、混合回答或模型补召回最多进入中置信候选；模型不可用时保留原有规则结果。原生工具问答继续走结构化路径，不经过语义模型。

Qwen 权重不包含在 `.app` 中。首次准备会明确下载约 1.33 GB 的生成模型和约 639 MB 的专用多语言嵌入模型：

```bash
npm run prepare:model
npm run prepare:model -- --check
```

文件固定为 `Qwen_Qwen3.5-2B-Q4_K_M.gguf` 和 `Qwen3-Embedding-0.6B-Q8_0.gguf`，存放在系统的 Decision 应用数据目录（macOS 通常为 `~/Library/Application Support/Decision/models/`，Windows 通常为 `%APPDATA%\Decision\models\`）；清单固定精确字节数、下载提交和 SHA-256，加载前会再次验证。两者采用 Apache-2.0 许可证，本地运行不需要 Ollama、LM Studio、订阅或云端 API。

决策库搜索会先保留精确关键词结果，再用 1024 维本地向量补充含义相近的记录；纯语义命中会明确标记“语义相关”，且限制补充数量。已采纳原则也使用同一索引参与事前核对和原则建议。向量索引位于应用数据目录，可增量更新、可随全文索引重建；嵌入模型缺失、校验失败或运行异常时，搜索和原则召回都会自动退回原有关键词逻辑。

## 模型后端与调用记录

“模型后端”按列表顺序路由。OpenAI、Anthropic 和 OpenAI 兼容后端可配置模型、HTTPS/本机回环地址、协议、超时和 API Key；密钥使用操作系统加密能力，仅保存在主进程私有目录，不会返回界面、进入日志或写入 Obsidian / SQLite。

Codex 与 Claude Code 后端复用客户端现有登录状态。设置页会显示实际路径、版本、登录状态和安全调用能力，也允许配置绝对路径与模型名。两者都在一次性空目录中以无 shell、无工具、无会话持久化模式运行；Codex 固定为只读沙箱并拒绝批准，Claude 固定为 safe mode、空工具和 `dontAsk`。模型正文只从 stdin 提交，子进程标记会让 Decision Hooks 在读取任何内容前退出，避免递归采集。停用它们不会卸载客户端或退出账号。

“模型调用记录”按每个后端 attempt 保存模型输入、可见输出、结构化结果、模型版本、耗时、状态和 Token 来源。正文记录可关闭；关闭后只记录元数据。记录默认保留 7 天、最多 1,000 条，可按单条、同一请求或全部清理。Apple 无可靠 Token API 时明确显示不可用；Qwen 使用运行时计数；API / CLI 使用服务商报告值，不用字符数伪造。

完整的数据边界、固定安全参数和故障恢复见 [本地语义识别文档](docs/semantic-recognition.md)。

## 决策库

“决策库”提供最多 200 条本地决策历史，支持搜索问题、答案、理由、上下文、后续结果、复盘经验和项目，并可按理由状态、来源与复盘进度筛选。短中文关键词使用安全的本地模糊匹配，较长关键词使用 SQLite FTS 相关性排序。点击任一记录可以查看最终选择、决策理由和当时上下文，也可以人工关联最多 5 条这次实际采用的已采纳原则、安排复盘日期、记录实施结果，再用“优于预期、符合预期、部分符合、低于预期、暂无法判断”完成结构化复盘并补充经验。原则关联不会由模型自动猜测；已归档原则保留既有历史关联，但不能再新增。到期或已有结果但尚未复盘的决策进入首页“复盘收件箱”，不会主动打开 App 或弹出窗口。原则关联、复盘日期、结果和复盘先原子写回原 Markdown 笔记，再刷新可重建的 SQLite 索引；Markdown 文件路径不会暴露给渲染进程。

## 方法论

“方法论”把 1 至 5 条已经记录实际结果并完成人工复盘的决策作为证据，调用当前已启用的 Qwen、API 或终端模型提炼候选原则。候选包含原则、适用条件、注意事项与证据摘要；可信度由 App 根据仍然存在的来源证据重新计算，不采用模型自报值。单条证据固定为低可信，至少三条完整证据跨两个项目且结果方向一致时才可达到高可信。

“新建原则”统一提供三种明确来源：人工编写、从复盘提炼和导入 Markdown。人工编写只要求填写标题、原则、适用条件和注意事项，不调用模型，也不会自动补造事实或建立证据关系；保存后仍是待确认候选，并单独标记为“人工录入”。人工候选可以稍后手动关联 1 至 5 条完整复盘证据并重新计算可信度；没有证据时只能在再次确认风险后作为待验证假设采纳。选择入口本身不会调用模型、写入候选或改变现有方法论。

事前核对与事后关联是两条独立链路。选择发生前，客户端 MCP 可以把尚未回答的问题、候选选项和有限上下文交给 App 做确定性文本匹配，最多返回 3 条已采纳原则及关联原因；结果只作为 Agent 当前分析的参考，不调用模型、不保存查询正文或逐次事件、不改变答案，也不自动认定用户采用了原则。选择完成后，补理由界面会再次对问题、已选答案、选项和有限上下文做本地匹配；只有用户明确点选的原则才会随决策保存，选择“稍后处理”并重启 App 后关联仍会保留。“分析”页展示不含正文的覆盖率、有帮助率和强匹配占比，并提供不落盘的本地试算与主动匿名评价；覆盖率只表示找到了候选原则，有帮助率也只代表主动反馈样本，二者都不是自动证明的准确率。

方法论内容较少时，原则列表会继续显示本地建设进度，而不是在第一条记录后留下无说明的空白。进度使用完整 SQLite 快照和全部方法论、实践资产 Markdown 计算已记录决策、完整复盘、待确认/已采纳原则与已采纳实践数量，不受决策库最近 200 条展示上限影响；同时把“复盘证据 → 原则沉淀 → 实践落地”状态和下一步操作放在同一页。审核、人工编写、继续提炼、补结果与复盘、导入 Markdown 都需要用户明确触发，读取进度本身不调用模型。

方法论页会把尚未被现有原则使用的完整复盘整理成最多 6 组“提炼建议”。分组只使用可重算的文本相似度、结果方向和项目覆盖度：相近且结果同向的复盘可以形成多证据组合，不相关或结果相反的复盘不会强行合并，单条证据明确标为探索性。建议只负责预选证据，查看建议不会调用模型；用户可以逐组生成，也可以在明确看到调用次数并确认后依次批量生成。批量结果只进入待确认列表，不会自动采纳或继续生成技能与流程。

“工作箱”是方法论页的常驻次级入口，把复盘素材、原则复验和关系核对集中展示，顶部只保留工作箱与新建原则两个操作。三条队列继续使用各自独立的确认和事实写入边界，不会因为打开或关闭工作箱而自动处理。“复盘素材”中的组合可以“稍后再看”，搁置状态以不含决策正文的 SHA-256 标识保存在 App 私有数据目录，跨重启保留并可随时恢复；出现新的完整复盘并形成新组合时仍会重新提示。已经生成过候选的证据无论候选后来被采纳还是忽略，都不会反复回到素材建议中。搁置、恢复和浏览均不调用模型，也不会自动建立原则、采纳或发布内容。

选择 1–5 条复盘证据后可以明确选择两条路径：“人工整理 · 0 次”直接进入人工归纳表单，“模型提炼 · 1 次”才调用当前生成模型。人工整理会在同一弹窗展示已选证据，并要求用户填写标题、原则、适用条件、注意事项和区分观察与归纳的证据摘要；保存后记录为“人工整理 / 不调用模型”，但仍保留真实来源编号并按证据数量、跨项目覆盖和结果一致性计算可信度。两条路径都只建立待确认候选，不会自动采纳、生成实践资产或发布客户端内容。

已有方法论也可以从最多 20 个本地 `.md` / `.markdown` 文件导入。每个文件最多 512 KiB，只读取用户明确选择的普通 UTF-8 文件，不跟随符号链接；结构化 Decision 方法论会保留可核对的来源编号，普通 Markdown 则从标题、原则、适用条件、边界与依据等章节建立候选。选择文件后只在主进程内存中建立最多保留 10 分钟的预检批次，不立即写入：界面逐条展示拆分结果、来源文件名、缺失边界、来源编号、完全重复和同原则可能重复项；可能重复项默认不勾选，只有用户明确提交的候选才写入。提交时会再次检查完全重复，预检批次只能使用一次。带编号或明确字段结构的长文可按同级章节拆成多条原则，每个文件最多 12 条、单次最多新增 60 条；普通章节不会被误拆。新导入记录会在 Markdown 中保留来源文件名和原内容 SHA-256，不保存原文件路径；详情页可以核对来源，旧版记录则明确显示未记录文件名。缺少适用条件或注意事项时会显示“待补充”，完成补充前不能采纳。没有 Decision 复盘证据的导入候选始终标为“待验证”和低可信；关联证据时，App 会用本地确定性文本重合对最近最多 200 条完整复盘给出最多 5 条可解释建议，并支持按问题、选择、项目和复盘经验搜索。建议只负责排序和说明匹配字段，不会自动勾选；用户仍需手动关联 1 至 5 条证据。关联后 App 会重新计算可信度，但不会自动改写原则内容。没有证据时只有再次明确确认后才能作为假设采纳，不会伪装成经过结果验证的原则。

候选审核会同时展示有效证据、覆盖项目、证据来源和复盘结果方向，并用本地确定性文本分析提示高相似原则或包含对立行动信号的潜在冲突。用户可以把任意提示核对为“重复、冲突或无关”，补充最多 500 字说明，并随时修改或撤销；人工确认的冲突和重复在原则改写后仍会保留，“无关”则不再阻断质量检查。“关系核对”会跨待确认与已采纳状态整理全部未处理关系、按冲突优先并对称去重，在一个连续比较队列中逐组保存或跳过，不需要反复进入原则详情，也不会调用模型。关系结论只作为独立、对称的 Markdown 事实保存，不会自动合并、覆盖或删除原则；未核对或仍有风险的关联会让采纳经过第二次明确确认。来源决策缺失的候选不能采纳。来源决策默认折叠，用户可以按需展开核对原始选择、实际结果和复盘结论。

当图谱中的两条已采纳原则已经人工确认为“重复”时，可以成对聚焦并开始建立人工合并草案。编辑器允许继续加入最多 3 条原则，但候选必须与当前组内每一条原则都已经单独人工确认为“重复”；系统不会用 A≈B、B≈C 推断 A≈C。已经与组内至少一条原则确认重复、但仍缺少其它成对结论的候选会单独显示“已确认 / 待核对”数量；只要没有既有冲突或无关结论，用户就可以留在同一弹窗逐对判断并填写可选说明。每次判断立即保存为原有独立关系事实，全部缺失对都确认为重复后才自动加入；任一对判为冲突或无关都会停止加入，不会打开第二层弹窗或继续猜测。单次合并因此限定为 2 至 5 条来源，并在顶部并排保留全部来源、显示数量上限和完整成对关系要求；统一内容与证据核对使用双栏工作区，只允许从整组已有的完整复盘中选择 1 至 5 条证据，全程不调用模型。新草案在 Markdown 中追溯全部来源，默认仍是待确认候选；采纳时会再次核验全部来源仍为已采纳，并且最多 10 个成对重复结论都仍然成立。采纳合并原则后可以进入“整理来源”：App 会先列出仍引用任一旧来源的技能与流程，每次仅在用户明确点击后调用一次模型生成来源迁移草案。已采纳资产的内容、稳定标识和客户端发布在草案审核前保持不变；明确采纳草案后才切换到合并原则。只有不存在活动引用时才允许把整组来源作为一次有界批处理标为“已归档”；任一写入失败会自动恢复已经写入的来源，整组归档也可以恢复，不会撤销已经独立审核过的实践资产更新。

未完成的合并编辑会在输入变化 500 ms 后保存一份本机私有草稿；关闭窗口或选择“稍后继续”时会先完成保存，原则页随后显示紧凑的“继续合并”入口。恢复前 App 会重新读取当前方法论，确认 2 至 5 条来源仍存在且均为已采纳、组内每一对仍明确为重复，并且同组没有现成的待确认或已采纳合并候选；失效草稿只显示原因和丢弃入口，不会反向改写状态、自动补关系或建立候选。恢复时不再可用的证据会被移除并要求重新确认。明确丢弃或成功创建候选后会删除草稿。

方法论笔记保存在 `<Obsidian 仓库>/Decision Journal/principles/`，人工关系保存在相邻的 `principle-relations/`，继续以 Markdown 作为唯一事实来源。每条原则笔记保留来源类型、来源决策编号和创建请求信息；模型生成记录保留实际后端与模型版本，人工录入则明确记录“不调用模型”。每对原则只有一个规范化关系事实。界面只展示必要的来源内容，不向渲染进程暴露文件路径。Apple Foundation Models 当前只负责语义识别，不支持这类通用结构化生成；路由会自动继续尝试其它已启用后端。

已采纳或已归档原则的详情会汇总明确记录“采用过该原则”的历史决策，分别展示采用次数、结果回填数、完成复盘数，以及符合/优于预期、部分符合、低于预期和暂不明确的分布。采用记录可以按项目及“待结果、待复盘、已复盘、需关注”筛选；待验证摘要使用全部历史精确计数，即使明细只向渲染层返回最近 50 条，也会保留下一条待处理决策。点击摘要或任一采用记录会通过决策编号精确打开原决策，不受决策库最近 200 条列表上限影响。这个投影只表达人工建立的关联与复盘分布，用于发现原则的适用边界；它不把相关性包装成因果证明，也不会据此自动提高可信度或改写原则。

当已采纳原则出现“明确采用该原则后完成”的新复盘时，详情会提示建立人工修订候选。修订编辑器预填当前原则，并允许从原有证据和最新采用后复盘中明确选择 1 至 5 条；至少需要一条新增复盘，不调用模型，也不会把没有采用关系的其它决策混入证据。保存只产生待确认草案，原原则、历史决策关联和下游实践资产都不改变。明确核对差异并应用后，App 继续使用原原则编号，把当前内容完整保存为本地恢复点，再更新原则内容与证据；引用它的技能和流程只会进入“来源已更新”状态，不会自动重写或发布。原则详情最多保留最近 20 个完整恢复点，恢复旧版前也会先保存当前内容。

未完成的原则修订同样保存为单份本机私有草稿。关闭详情或返回详情前会先保存，原则页显示“继续修订”；草稿同时保存开始编辑时的来源快照，恢复时会重新确认来源仍为已采纳、没有现成修订候选，并重新读取采用后的完整复盘。来源正文没有变化时直接恢复；已经变化时则逐字段并排显示“开始编辑时、当前正式版本、未完成草稿”，未发生双向修改的字段确定性预选，真正冲突的字段必须由用户明确保留当前版本或草稿后才能迁移。迁移只把选择后的内容重建为当前版本上的本机草稿，不会改写正式原则或建立修订候选；不再可用的证据仍会移除。旧版草稿缺少来源快照、候选已经建立或新复盘已经失效时保持惰性，只显示原因与丢弃入口。明确丢弃或成功建立修订候选后会删除草稿。

方法论页的“复验”入口会把所有已采纳原则采用后的新增复盘集中成待核对列表，并优先显示出现偏差的原则。用户可以打开原决策、查看并建立修订草案，或明确确认这批结果下原则仍适用。确认只在原则 Markdown 中推进人工复验位置，不修改原则正文、可信度或内容更新时间，因此不会把下游技能与流程误标为来源已更新；已有修订草案时必须先处理草案，不能用确认操作跳过。这个收件箱不调用模型、不从文本猜测原则采用关系，也不把结果相关性解释为因果。

方法论页内的“分析概览”会按需读取完整的可重建 SQLite 快照，并在主进程用单遍本地聚合统计决策与项目数量、理由完整率、结果回填率、结果复盘率、预期/实际分布、最近 12 个有记录月份，以及项目和来源分布。聚合过程只读、无网络访问、不创建第二份数据库，内存只随项目、来源和月份分组数量增长。

方法论页内的“关系图谱”只读取已采纳原则，并用确定性关系把项目、来源决策、人工复盘结果与原则连接起来。双方都已采纳的人工“重复/冲突”结论也会作为原则间关系进入图谱，“无关”和仍处于候选状态的关系不会进入正式投影。界面支持按原则或项目搜索、按重复/冲突筛选、成对聚焦、直接打开原则详情，并从确认重复的成对视图发起人工合并草案。候选原则不会提前进入图谱；如果用户在 Obsidian 中移除了某条来源决策，原则笔记仍保留，界面会明确提示缺失引用，不会补造节点。图谱仍是 Markdown 与 SQLite 索引的只读投影；发起合并只新增方法论候选，不在图谱中维护第二份事实数据。

“技能与流程”可以从 1 至 5 条已采纳原则建立可审核草案。用户可以选择人工编写或明确发起一次模型生成：人工路径只预填来源原则中的适用条件和失败边界，不调用模型，也不会虚构执行步骤与验收标准；两条路径都只产生待确认候选，并保留来源快照和创建方式。技能草案使用独立目录中的 `SKILL.md`，工作流草案使用普通 Markdown；两者都包含使用条件、操作步骤、验收检查、失败处理和来源原则。用户可以查看、修改、采纳或忽略，未采纳草案不会被当作正式实践资产。新生成或人工校对的资产会在笔记元数据中保留当时的来源快照；界面据此逐字段展示原则标题、内容、适用条件、注意事项和可信度变化。来源被删除或取消采纳时则标为“来源不可用”。旧资产没有历史来源快照时仍可按更新时间识别变化，并会在第一次保存或重新生成后建立对比基线。

技能保存在 `<Obsidian 仓库>/Decision Journal/skills/<稳定标识>/SKILL.md`，工作流保存在 `<Obsidian 仓库>/Decision Journal/workflows/`。已采纳资产每次编辑、应用替换草案或恢复旧版前，都会在 App 数据目录保留修改前内容；详情最多展示最近 20 个恢复点，支持逐字段比较和再次确认后恢复，恢复前的当前内容也会自动形成新恢复点。来源快照属于内部审阅元数据，不会写进客户端 Skill 包。已采纳资产可以由用户在详情中明确发布到 Codex 或 Claude Code；两类资产都以客户端支持的 Skill 包写入各自的 `skills/<稳定标识>/SKILL.md`。发布前会识别同名占用、外部修改、目标丢失和符号链接风险；覆盖必须再次确认，原内容和每次 Decision 发布版本都可安全回滚。来源更新时，重新生成只创建替换草案，不修改原资产或已安装客户端内容；用户采纳替换草案后才更新原资产，并需再次明确发布。来源不可用或尚未确认更新时会暂停新发布，但已有版本仍可检查和回滚。Decision 不会后台自动发布，也不会在目标被外部修改后强行回滚。

## 首次使用

1. Windows 运行 Setup 完成安装；macOS 解压后将 `Decision.app` 放入 `/Applications`。然后启动一次。
2. 应用会优先读取 Obsidian 的最近使用仓库；未发现时使用 `~/Documents/Decision Vault`。
3. 在“接入”页查看 Claude Code 和 Codex 的连接状态。
4. 在“模型”页确认当前识别引擎；如需 API 或终端后端，在后端列表中配置、测试后再启用。
5. 如有需要，在“设置”页更换 Obsidian 仓库。
6. 在“接入”页点“安装或修复”。
7. 重新打开 Claude Code 和 Codex，使新的被动 Hooks 与只读 MCP 接入生效。

安装会：

- 移除旧的 Decision MCP 配置，再注册当前只读事前核对工具；
- 移除带 `DECISION_HOOK=` 标识的旧处理器；
- 为 Claude Code 的 `AskUserQuestion` 安装被动 `PostToolUse` Hook；
- 为 Codex 的 `request_user_input` / `AskUserQuestion` 安装被动 `PostToolUse` Hook；
- 为两个客户端安装被动 `Stop` 与 `UserPromptSubmit` Hook，用于普通文本提问的本地兜底；
- 保留其它工具已有的配置、顺序和未知字段；
- 直接清理旧版 Decision 入口，并以原子写入替换为当前配置，不创建旧版备份。

安装会先通过两个客户端的官方命令配置只读 MCP，全部成功后才以原子写入替换被动 Hooks 并升级接入标记。旧 MCP 不存在时移除命令会正常忽略；如果因权限、CLI 或配置错误而失败，安装会报告错误且不会把 Hooks 标记为已升级，可直接重试修复。Claude Code/Codex 的原生问答行为不会被改变。

设置页不会显示或持久保存运行令牌。令牌只存在于仅当前用户可读的运行描述文件中，并在 App 正常退出时删除。

## 理由流程

- 理由岛水平居中并贴住当前显示器工作区顶部，当前尺寸约为 560×400。
- 待处理使用约 560×640 的普通面板，设置页约为 680×750，并保留 12px 顶部安全距离。
- 待处理面板打开一次后会连续推进队列：忽略直接显示下一项；记录后先补充、跳过或稍后补充理由，再自动返回下一项；最后一项完成后关闭。
- 待处理面板把决策原文、用户回答和问题相关上下文作为主体，顶部只保留来源、项目、进度和“稍后”。
- 设置页、待处理面板与理由岛共享同一套 Light/Dark 玻璃层；macOS 26 使用原生 Liquid Glass，旧系统使用 vibrancy 与 CSS 模糊降级。
- 原生问题与答案只读，不能在 Decision 中重选。
- 有相关上下文时默认显示两行预览，可展开查看“任务背景”和“约束与考虑”；截断会明确标记。
- “完成”分别保存自由输入理由原文和结构化判断依据；只选判断依据时不会伪造理由原文。
- “稍后处理”只进入私有本地待补理由队列；跨 App 重启恢复，补完理由时才写入 Obsidian 和 SQLite。
- “跳过理由”明确保存为已跳过。
- “不记录此次决策”是复选框；确认后删除暂存正文，不写 Markdown 或 SQLite。
- Markdown 写入失败时，候选和理由保留在内存及私有恢复日志中，并提供重试；App 重启后会继续该处置。
- SQLite 更新失败时，Markdown 仍视为保存成功，设置页提示重建索引。

## 集成与诊断

实际配置位置：

```text
~/.claude/settings.json
~/.codex/hooks.json
```

打包后的桥接程序支持以下命令；Windows 使用安装目录下的 `resources\bridge\decision-bridge.cmd`，macOS 使用下面的入口：

```bash
"/Applications/Decision.app/Contents/Resources/bridge/decision-bridge" install --dry-run
"/Applications/Decision.app/Contents/Resources/bridge/decision-bridge" install --apply
"/Applications/Decision.app/Contents/Resources/bridge/decision-bridge" doctor
```

Hook 命令从 stdin 读取客户端事件，不向 stdout/stderr 输出业务内容，并始终以成功状态放行原生流程。

## 隐私与恢复

- SQLite 异常：App 会隔离损坏文件；可以在设置页从 Markdown 重建。
- 待处理：菜单栏和设置页显示实时数量；选择“记录并补充理由”后才进入正式理由流程。点击“稍后”或关闭面板不会消费当前项，再次打开会从最早未处理项继续。
- 理由恢复日志异常：设置页会单独提示读取、损坏或隔离故障；重建 SQLite 不会清除此告警，原始捕获事件继续留在待处理队列。
- 未完成表单：人工原则、证据整理、实践资产、合并编辑和原则修订各最多保留一份本机草稿；文件与目录仅当前用户可读。合并与修订草稿包含未完成正文、来源编号和所选证据编号，不写入 Obsidian、SQLite、客户端或模型服务，只有明确创建候选后才进入正式知识生命周期。
- Obsidian 外部编辑：App 根据内容哈希重新索引，不覆盖手工修改。
- 删除 App 不会删除 Obsidian 决策笔记。
- Decision 的持久化业务数据、调用记录和凭据只保存在本机；用户显式启用 API 或 CLI 模型后端后，裁剪后的当前问答会发送给所选服务商并受其数据政策约束。
- 当 Codex 原生 `request_user_input` 未发布 `PostToolUse` 时，`Stop` Hook 最多读取本地 transcript 尾部 64 KiB，只配对同一 turn 内该工具的调用参数和成功回答。
- 普通文本识别优先使用 Hook 直接提供的最后一条助手消息；缺失时从同一受限尾部提取最近用户任务和最后一条助手文本。
- 规则评分器可以识别没有问号的选项列表、确认请求、短编号回答、肯定/否定和“先 1 后 3”一类组合顺序；语义模型补充改写回答、隐含选项、跨句指代和“回答后继续追问”的混合回答。
- Apple 与 Qwen 都在本机推理；Hook 不加载模型，Qwen 不创建本地网络监听，Apple helper 只使用私有 stdin/stdout JSON Lines。API / CLI 后端默认关闭，只有用户明确启用后才发送裁剪后的当前问答。
- 只有 LLM 把决策交给用户并停下来等待、且下一轮回答相关时才会采集。状态说明、客观资料请求、代码、日志、引用、反问、LLM 自己作出的决定和无关新任务会被丢弃。
- transcript 中更早的历史、未配对工具输出、transcript 文件本身及其路径不会写入暂存事件、Markdown 或 SQLite；完整 transcript 不会发送给 App。
- 服务只监听 `127.0.0.1` 随机端口，并要求每次启动生成的随机令牌。
- Electron 渲染进程启用沙箱和上下文隔离，禁用 Node 集成和外部导航。

## 本地数据迁移

从旧版升级时，Decision 会在打开 SQLite、凭据、模型或待处理队列之前迁移默认应用数据目录；历史笔记、索引、模型、加密凭据、spool 和未完成草稿作为一个整体保留。迁移失败时继续使用完整旧目录，不创建半迁移副本；新旧目录同时存在时以新目录为准且不自动合并。

既有 Obsidian vault 路径不会被自动改名或移动。只有没有历史设置的全新安装才使用 `~/Documents/Decision Vault`。旧环境变量、Hook、MCP 与 bridge 名称在整个 1.x 系列保留兼容，新名称始终优先；完整边界和冲突策略见[迁移设计](docs/superpowers/specs/2026-08-15-cognelis-migration-and-github-publication-design.md)。

## 当前限制

- `v1.1.0` 默认发布 Windows x64 和 Apple Silicon macOS，不包含 Windows ARM64、Intel macOS、Linux、应用商店或自动更新。Windows 为 unsigned，macOS 为 ad-hoc 且未公证；未来可以在不改变制品契约的前提下增加 Authenticode 或 Developer ID，但当前免费发布不会因缺少证书而阻断。更新继续由用户从官方 GitHub Release 手工下载；
- 首次修改 Hook 集成配置后通常需要重启 Claude Code/Codex；模型后端排序、启停和路径配置不需要重装 Hooks；
- 远程 API 与 CLI 后端可能消耗额度或产生费用；服务端保留策略由对应提供商和账号配置决定；
- 识别器会从常见编号列表和经过原文定位的模型建议中恢复选项；无法可靠提取时答案仍按完整自由输入保存；
- 本地模型用于降低漏报，但不会消除所有语义歧义；不能由模型独立触发的样本会进入中置信待处理队列；
- 当前 64 条完全合成、脱敏的回归集用于确定性基线检查；正式调整路由阈值前仍需积累至少 500 条分层、脱敏且留有保留集的真实标签语料；
- 预期/实际复盘、决策实际采用的原则、方法论采纳和技能/工作流采纳目前都由用户确认；人工录入或 Markdown 导入的原则不会自动获得复盘证据，没有证据时只代表待验证假设；事前核对依赖 Agent 按接入说明主动调用只读 MCP，目前不能强制所有原生提问在提交前暂停，也不能证明建议影响了最终答案；匿名质量评价依赖用户主动表达并受自选择和小样本偏差影响，不保存正文也意味着无法事后逐条审计，当前只用于发现明显的阈值问题，不会自动调整匹配规则或当作准确率；原则采用后的结果分布只说明人工关联下的相关性，不能单独证明原则导致了结果，也不会自动调整可信度；方法论质量检查只自动识别可解释的文本高相似和对立行动信号，可能存在漏报或误报；人工关系仍只保存两条原则之间的重复、冲突或无关结论，多来源合并限定为 2 至 5 条且要求组内每一对都已明确确认重复，不会自动推断关系组；实践资产来源迁移仍需逐项生成和审核草案，尚未提供模型语义聚类、多原则关系组或自定义图谱边；批量分析仍是确定性聚合，关系图谱只表达已确认的项目、来源决策、结果、原则以及成对人工关系；客户端发布目前只支持本机 Codex 与 Claude Code 的 Skill 目录，不会自动发布，也尚未提供跨设备同步、批量发布或第三方客户端适配；提炼分组、导入证据匹配和事前/事后原则核对都使用确定性文本重合而非语义嵌入，可能漏掉表达差异很大的相关内容，匹配建议不会自动建立事实关系，用户仍需手动选择；Markdown 长文只按明确的同级编号或字段章节确定性拆分，不会猜测松散段落之间的语义边界，外部文字也不会自动视为复盘证据；
- 实践资产历史最多保留每个资产最近 20 个 App 修改前恢复点；直接在 Obsidian 中产生的外部版本不会被持续监听并逐次归档，但下一次通过 App 修改前会先捕获当时的外部内容；
- Electron Forge 的 Vite 插件仍属于实验性接口，依赖版本已锁定并纳入打包冒烟测试。

## 开发验证

```bash
npm run check
npm run quality
npm run report:semantic
npm run make
npm run smoke
npm run release:local
```

`npm run check` 是日常质量门禁，依次运行类型检查和完整自动化测试。`npm run quality` 是 CI 唯一通过入口，在 `check` 后继续执行严格语义门；`npm run report:semantic` 只生成非阻塞的确定性规则基线。`npm run check:semantic` 未达到 high precision ≥ 95% 且 high + medium recall ≥ 90% 时返回非零状态。当前 64 条合成基线已经通过该门禁，但它不替代至少 500 条分层、脱敏、带独立保留集的产品激活评估。`npm run release:local` 会在质量门之后重新制包、运行隔离冒烟，并生成当前平台主制品的 SHA-256 与 schema-v2 清单。正式发行还会先执行 `npm run audit:runtime`，并要求 GitHub 原生 Windows 与 macOS 任务都通过后才一次性创建 Release。

显式使用已启用的本地客户端 profile 评估并统计后端延迟和 Token：

```bash
npm run evaluate:semantic -- --provider builtin-codex --report-only
npm run evaluate:semantic -- --provider builtin-claude-code --report-only
```

这两条命令会真实调用对应服务，可能消耗额度；普通测试与默认评估不会调用它们。

`npm run smoke` 使用隔离的临时仓库启动打包 App，通过真实的 `Stop` / `UserPromptSubmit` 被动 Hook 验证受限 transcript 读取、语义配对、模型不可用降级、明确选择的自动捕获、理由提交、Markdown、SQLite 重建和运行文件清理；混合回答的人工复核边界由单元与集成测试覆盖。冒烟不接触真实 Obsidian 数据，也不要求下载 Qwen 权重。
